Описания игр в магазине пишут люди, и иногда в них есть разметка: выделить главное жирным, добавить ссылку. Посмотрим, что Angular делает с HTML внутри данных и почему по умолчанию он такой осторожный.

## Интерполяция экранирует всё

Добавим описание в класс:

```ts app.ts
protected readonly description =
  'Команды пиратов ищут клад на острове, который <b>меняется каждую партию</b>: карта собирается из квадратных тайлов.';
```

И для начала выведем его интерполяцией — вставьте перед кнопкой:

```html
<p class="description">{{ description }}</p>
```

На странице появится `…который <b>меняется каждую партию</b>: …` — теги показаны как текст. Интерполяция всегда вставляет **текст**, а не разметку: Angular записывает значение в текстовый узел, и браузер не разбирает его как HTML.

Это не неудобство, а защита. Представьте, что описание пришло от пользователя (например, это отзыв), и там написано `<img src="x" onerror="украсть куки">`. Если бы интерполяция вставляла HTML, код злоумышленника выполнился бы в браузере каждого посетителя. Такая атака называется **XSS** (cross-site scripting, межсайтовый скриптинг) — одна из самых частых уязвимостей веб-приложений. С интерполяцией она невозможна.

## `[innerHTML]` и санитизация

Если разметку всё-таки нужно показать, используется привязка к свойству `innerHTML`:

```html app.html
<p class="description" [innerHTML]="description"></p>
```

Теперь «меняется каждую партию» выделено жирным. Но Angular не вставляет строку как есть: перед записью в `innerHTML` значение проходит **санитизацию** (sanitization) — очистку от всего опасного. Безопасные теги (`<b>`, `<i>`, `<p>`, `<a href="https://…">`) остаются, а скрипты, обработчики событий вроде `onerror` и ссылки `javascript:` удаляются.

Добавьте поле `description` и выведите его перед кнопкой через `[innerHTML]`.
:::

## Что получилось

Под ценой — описание игры с выделенным фрагментом. Консоль чистая.

## Эксперимент: попробуйте взломать магазин

Допишите в конец `description` опасную разметку:

```ts
'… тайлов. <img src="x" onerror="alert(1)"><script>alert(2)</script> <a href="javascript:alert(3)">ссылка</a>'
```

Ни одного `alert` не появится. Если посмотреть на элемент во вкладке Elements, окажется, что `<script>` исчез целиком, у `<img>` не осталось `onerror`, а ссылка превратилась в `href="unsafe:javascript:alert(3)"`. В консоли Angular предупредит:

```
WARNING: sanitizing unsafe URL value javascript:alert(3) (see https://angular.dev/best-practices/security#preventing-cross-site-scripting-xss)
WARNING: sanitizing HTML stripped some content, see https://angular.dev/best-practices/security#preventing-cross-site-scripting-xss
```

То же происходит с URL в привязках: `[href]="'javascript:alert(1)'"` даст ссылку `unsafe:javascript:alert(1)`. Даже `[src]` у нашей обложки проходит проверку URL — в последнем шаге главы вы увидите это в скомпилированном коде.

Уберите опасную разметку из описания.

::: warning
Иногда санитизацию хочется отключить: например, если нужно вставить `<iframe>` с видео. Для этого есть сервис `DomSanitizer` и его методы `bypassSecurityTrust…` — им пользуются, когда HTML пришёл из **доверенного** источника, а не от пользователя. Как получать сервисы, вы узнаете в главе про внедрение зависимостей. Правило простое: всё, что ввёл пользователь, никогда не проходит через `bypassSecurityTrust…`.
:::

## Что делать никогда

Санитизация защищает только привязки Angular. Если обойти Angular и записать HTML в DOM самому — через `element.innerHTML = …` в коде класса, — никакой проверки не будет. Пишите разметку в шаблонах и пользуйтесь привязками: тогда безопасность получается по умолчанию.
