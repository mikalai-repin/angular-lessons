Всю главу мы опирались на то, что сигналы «сами знают», кто их прочитал, а `computed` «сам находит» зависимости и не считает лишнего. В этом шаге посмотрим, как это устроено: какие данные Angular хранит о каждом сигнале и что происходит между `set` и обновлением экрана.

Как и прошлые шаги «под капот», этот необязательный.

## Граф сигналов магазина

В шаге появился файл `signal-graph.ts` с функцией `printSignalGraph`. Она обходит поля компонента, находит сигналы и печатает, что каждый из них читает и кто читает его. Функция опирается на внутреннее устройство Angular, поэтому годится только для изучения, не для приложения. Разбирать её код не обязательно, но он короткий.

::: task
Вызовите `printSignalGraph` после запуска приложения — измените `main.ts`:

```ts main.ts {4,7}
import { bootstrapApplication } from '@angular/platform-browser';
import { App } from './app';
import { appConfig } from './app.config';
import { printSignalGraph } from './signal-graph';

bootstrapApplication(App, appConfig)
  .then((appRef) => printSignalGraph(appRef.components[0].instance))
  .catch((err) => console.error(err));
```

`appRef.components[0].instance` — экземпляр корневого компонента `App`, тот самый, что Angular создал при запуске.
:::

В консоли — двенадцать строк:

```
gameIndex (signal): читает —; его читают шаблон, game
game (computed): читает gameIndex; его читают soldOut, шаблон, discount, quantity, available
soldOut (computed): читает game; его читают шаблон
discount (computed): читает game; его читают шаблон
quantity (linkedSignal): читает game, inCart; его читают шаблон
cart (signal): читает —; его читают cartSummary, cartCount, cartTotal, inCart, шаблон
cartCount (computed): читает cart; его читают шаблон
cartTotal (computed): читает cart; его читают шаблон, deliveryLeft
cartSummary (computed): читает cart; его читают эффект, шаблон
inCart (computed): читает cart; его читают quantity, available, шаблон
available (computed): читает game, inCart; его читают шаблон
deliveryLeft (computed): читает cartTotal; его читают шаблон
```

Нарисуем то же самое:

```
gameIndex ─► game ─┬─► soldOut ────► шаблон
                   ├─► discount ───► шаблон
                   ├─► quantity ───► шаблон
                   └─► available ──► шаблон
cart ─┬─► inCart ──► quantity, available
      ├─► cartCount ──► шаблон
      ├─► cartTotal ─► deliveryLeft ─► шаблон
      └─► cartSummary ──► шаблон, эффект
```

(Стрелки к шаблону есть почти у каждого сигнала: шаблон читает и `inCart`, и `cartTotal`, и сам `cart`. На схеме оставлены не все, чтобы её можно было прочитать.)

Это **граф сигналов**. У каждого узла две роли:

- **производитель** (producer) — тот, кого читают: `signal`, `computed`, `linkedSignal`;
- **потребитель** (consumer) — тот, кто читает: `computed`, `linkedSignal`, эффект и шаблон.

`computed` — и то и другое: он читает свои зависимости, а его читают другие. А шаблон компонента — такой же узел графа, как эффект: у Angular это потребитель с типом `template`.

## Как сигнал узнаёт, кто его читает

Секрет в одной глобальной переменной Angular — **активный потребитель**. Перед тем как вызвать функцию `computed`, функцию эффекта или блок обновления шаблона, Angular записывает в неё этот узел. А функция-сигнал при каждом чтении смотрит на активного потребителя и, если он есть, связывает себя с ним. Так и появляются стрелки графа. Никакого разбора кода, никакого списка зависимостей: зависимостью становится то, что действительно прочитано во время выполнения.

Теперь понятно, как работает `untracked`. Мы заглянули в исходники `@angular/core` 22.2.1: он всего лишь обнуляет активного потребителя на время своей функции, а потом возвращает прежнего. Сигналы, прочитанные внутри, не видят потребителя и ни с кем не связываются.

## Зависимости меняются

Посмотрите на строку `inCart`: он читает только `cart`. Но в его коде есть `this.game()`:

```ts
this.cart().find((item) => item.game.id === this.game().id)?.quantity ?? 0
```

Корзина пуста, поэтому `find` ни разу не вызвал свою функцию и до `this.game()` дело не дошло. Зависимости — это то, что прочитано **в последний раз**, и после каждого пересчёта Angular записывает их заново.

Проверьте: начните с непустой корзины.

```ts app.ts
protected readonly cart = signal<CartItem[]>([{ game: GAMES[0], quantity: 1 }]);
```

Теперь в консоли `inCart (computed): читает cart, game`. Верните пустой массив.

## Push-pull: что происходит после `set`

Когда изменяемый сигнал получает новое значение, Angular действует в две фазы.

**Push — разослать пометки.** Сигнал увеличивает свой номер версии и проходит по своим потребителям, а те — по своим, помечая каждого «грязным»: «твои данные, возможно, устарели». На этой фазе **ничего не вычисляется**. Пометки быстро расходятся по графу до самых его концов — эффектов и шаблонов. Эффекты встают в очередь, шаблоны просят Angular запланировать проверку.

**Pull — вычислить по требованию.** Потом кто-то читает значение: шаблон при проверке или эффект при запуске. Грязный `computed` сначала спрашивает своих производителей: «изменилась ли ваша версия?». Только если изменилась, он вызывает свою функцию. Если новый результат **равен** старому, его версия не растёт, и потребители дальше по графу пересчитываться не будут.

Последнее свойство называется отсечением по равенству, и его легко увидеть. Добавьте в `app.ts` вывод в `soldOut` и эффект, который зависит только от него:

```ts app.ts
protected readonly soldOut = computed(() => {
  console.log('soldOut пересчитан');
  return this.game().inStock === 0;
});
```

```ts app.ts
// в конструкторе
effect(() => console.log('Эффект: soldOut =', this.soldOut()));
```

Листайте игры вперёд, от первой до седьмой. `soldOut пересчитан` появится при каждом переключении: игра изменилась, `soldOut` проверил себя. А эффект после первого запуска молчит, пока не дойдёте до «Маяка»: у шести игр подряд `soldOut` равен `false`, значение не изменилось, и эффекту незачем запускаться. Уберите эксперимент.

Это та самая ловушка из шага про `linkedSignal`: связанный сигнал, который читал `soldOut()`, не сбрасывался по той же причине — его зависимость пересчиталась, но не изменилась.

Отсюда и ленивость: если `computed` никто не читает, pull не наступает никогда. Удалите из шаблона бейдж скидки — и в графе будет `discount (computed): читает —; его читают —`. Angular даже не связывает с графом сигнал, который ни разу не вычислялся. Такие связи держат только **живые** потребители — шаблоны, эффекты и `computed`, которые читают они. Поэтому ненужный вычисляемый сигнал ничего не стоит: его не пересчитывают, а производители не хранят на него ссылок.

## Шаблон и проверка компонента

Что делает помеченный шаблон? Когда потребитель-шаблон становится грязным, Angular вызывает внутреннюю функцию `markAncestorsForTraversal`. Она делает две вещи:

- сообщает планировщику обнаружения изменений: «нужна проверка»;
- ставит родительским представлениям флаг «внутри есть что обновить».

Во время проверки Angular спускается по дереву компонентов по этим флагам и обновляет **только** те представления, чей шаблон помечен грязным. Сравните с обработчиком события из главы 2: его обёртка помечает грязными сам компонент и всех его предков, и все они проверяются. С одним компонентом разницы не видно, но в главах 5 и 6, когда компонентов станет много, вы её оцените: изменение сигнала обновляет ровно те компоненты, которые его читают.

Планировщик не запускает проверку сразу. Обычно он ставит её в очередь: на ближайший кадр отрисовки (`requestAnimationFrame`) или таймер — что наступит раньше. Поэтому несколько изменений сигналов подряд дают одну проверку и один запуск каждого эффекта. Это мы и видели в шаге про `effect`.

## Имена в настоящем проекте

Мы печатали граф своей функцией, потому что у узлов в превью нет имён. У `signal`, `computed` и других есть опция `debugName`: `signal(0, { debugName: 'cartCount' })`. В настоящем проекте Angular CLI компилятор сам добавляет `debugName` с именем поля, но только в сборке для разработки. Мы проверили вывод `ngc` 22.2.1: поле `count = signal(0)` превращается в `signal(0, ...(ngDevMode ? [{ debugName: "count" }] : []))` (без служебных комментариев). Эти имена показывает Angular DevTools — расширение браузера для отладки Angular. Превью компилирует код в JIT без этого шага.
