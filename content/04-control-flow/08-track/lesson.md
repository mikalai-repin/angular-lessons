В шаге про `@for` мы сказали, что `track` помогает Angular не пересоздавать плитки, а только переставлять их. В этом шаге увидим это своими глазами: подключим наблюдатель за DOM каталога, посортируем и поищем с разными выражениями `track`.

Шаг необязательный, как и прошлые шаги «под капот».

## Наблюдатель

В шаге появился файл `dom-watch.ts` с функцией `watchCatalog`. Она подписывается на изменения DOM внутри `.grid` через стандартный `MutationObserver` и после каждого изменения пишет в консоль:

- сколько плиток **создано** заново;
- сколько **перемещено** — плитка та же, что была, только стоит в другом месте;
- сколько **удалено**;
- сколько **текстов переписано** — изменений текстовых узлов внутри плиток.

Отличить перемещённую плитку от новой просто: функция запоминает все элементы, которые уже видела.

::: task
Вызовите `watchCatalog` после запуска приложения — измените `main.ts`:

```ts main.ts {4,7}
import { bootstrapApplication } from '@angular/platform-browser';
import { App } from './app';
import { appConfig } from './app.config';
import { watchCatalog } from './dom-watch';

bootstrapApplication(App, appConfig)
  .then(() => watchCatalog())
  .catch((err) => console.error(err));
```
:::

## `track game.id`

Выберите «Сначала дешёвые»:

```
Плитки: создано 0, перемещено 8, удалено 0; текстов переписано: 0
```

Ни одной новой плитки, ни одного изменённого текста: те же двенадцать элементов `<article>` просто переставлены. Причём не все двенадцать, а восемь — остальные и так оказались на нужных местах. Верните «По умолчанию» — снова восемь перемещений.

Наберите «шах» — одиннадцать плиток удалены, «Шахматы» остались. Сотрите — одиннадцать созданы заново. Удалённые элементы Angular не хранит: если игра вернулась в список, её плитка создаётся снова.

## `track $index`

Замените в `app.html` выражение каталога на `track $index` и снова выберите «Сначала дешёвые»:

```
Плитки: создано 0, перемещено 0, удалено 0; текстов переписано: 28
```

Теперь ничего не перемещается, зато переписано 28 текстов. Для Angular ключ плитки — её номер. Плитка номер 0 до сортировки показывала «Остров сокровищ», после — «Тихую охоту». Ключ тот же, значит, «элемент тот же», и Angular переписывает в ней название, цену, наличие.

Выглядит экономно: ничего не двигали. Но подумайте, что живёт в самом элементе DOM, а не в данных: фокус, введённый в поле текст, прокрутка, запущенная CSS-анимация, состояние вложенного компонента (глава 5). С `track $index` всё это останется на месте, а игра под ним сменится. Отсюда правило из шага про `@for`: `$index` — только для списков, которые никогда не переставляются.

## `track game` и копии

`track game` — ключ сам объект. Пока объекты в массиве одни и те же, это работает как `track game.id`. Но данные часто приходят новыми объектами: например, каждый ответ сервера — новые объекты с теми же `id`. Изобразим это: в `visibleGames` замените `GAMES.filter(` на `GAMES.map((game) => ({ ...game })).filter(`, а в шаблоне поставьте `track game`. Выберите «Сначала дешёвые»:

```
NG0956: The configured tracking expression (track by identity) caused re-creation of the entire collection of size 12. …
Плитки: создано 12, перемещено 0, удалено 12; текстов переписано: 30
```

Все плитки удалены и созданы заново: ни один новый объект не равен старому. Angular в режиме разработки замечает это и предупреждает. Так же, сравнивая по ссылке, работал старый `*ngFor` без `trackBy` из врезки шага про `@for`.

## Повторяющиеся ключи

Последний эксперимент — неуникальный ключ: `track game.category`. Сортировка работает, но в консоли — предупреждение:

```
NG0955: The provided track expression resulted in duplicated keys for a given collection. … Duplicated keys were:
key "family" at index "1" and "4",
key "party" at index "2" and "3".
```

С повторяющимися ключами Angular не может однозначно сопоставить плитки, и результат зависит от порядка. Верните `track game.id` и `GAMES.filter(`.

## Во что компилируется `@for`

Мы посмотрели вывод `ngc` 22.2.1 для решения практикума. Выражения `track` становятся маленькими функциями в начале файла:

```js
const _forTrack0 = ($index, $item) => $item.id;
const _forTrack1 = ($index, $item) => $item.game.id;
```

А сам блок — двумя инструкциями: `ɵɵrepeaterCreate(…, App_For_28_Template, …, _forTrack0, …, App_ForEmpty_29_Template, …)` в блоке создания и `ɵɵrepeater(ctx.visibleGames())` в блоке обновления. Первая запоминает шаблон тела, шаблон `@empty` и функцию ключа. Вторая при каждой проверке получает новый массив и сравнивает его со списком плиток на странице. Для `track $index` и `track game` компилятор подставляет готовые функции Angular `ɵɵrepeaterTrackByIndex` и `ɵɵrepeaterTrackByIdentity`. По последней Angular и узнаёт, когда предупреждать NG0956.

## Алгоритм сравнения

Сравнение — функция `reconcile` в исходниках `@angular/core`. В упрощённом виде:

1. Идти по старому списку и новому массиву **с начала**, пока ключи совпадают. Совпал ключ — плитка остаётся; если объект при этом другой, ей передаётся новое значение (так обновляются тексты).
2. То же **с конца**.
3. Если начало нового массива совпадает с концом старого списка (или наоборот), переставить плитку — это ловит частые случаи «элемент переехал в начало» и «два поменялись местами».
4. Иначе отложить плитку в сторону по её ключу. Если ключ встретится дальше в новом массиве, плитка вернётся из «отложенных»; если нет — создать новую.
5. Плитки, которым места не нашлось, уничтожить.

Поэтому добавление в конец, удаление из середины, перестановка двух элементов обходятся почти даром, а полная пересортировка — перемещениями, без пересоздания. Всё держится на одном: ключ должен однозначно и постоянно указывать на «ту же» сущность.
