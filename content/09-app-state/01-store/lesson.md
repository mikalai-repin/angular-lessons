В главе 8 корзина переехала в сервис `CartStore`, и её стали брать все, кому она нужна: шапка, карточки, окно «Подробнее», мини-корзина. Сервис решил вопрос «как получить корзину». Эта глава — о вопросе «как с ней обращаться»: кто может её менять, что в ней хранить, что вычислять, что сохранять между запусками.

Данные, которые живут дольше одного компонента и нужны разным частям приложения, называют **состоянием приложения** (application state). В «Ходе конём» это корзина и избранное. Всё, что мы сделаем в главе, — способы держать такое состояние в порядке:

- закрытое состояние, которое меняют только методы сервиса;
- корзина, которая переживает перезапуск, — `localStorage`;
- итоги: доставка, выгода по акциям, сумма к оплате;
- промокоды `KNIGHT10` и `CHESS500`;
- правила склада: в корзину нельзя положить больше, чем есть;
- и в конце — когда сервисов на сигналах хватает, а когда берут библиотеку вроде NgRx.

## Кто может менять корзину

Откройте `core/cart-store.ts`. Методы `add`, `setQuantity`, `remove`, `clear` знают правила корзины: одинаковые игры складываются в одну позицию, количество не меньше единицы, в главе 8 к `add` добавилась аналитика. Но поле позиций открыто:

```ts core/cart-store.ts
readonly items = signal<CartItem[]>([]);
```

`readonly` защищает только само поле: другой сигнал в него не положить. А вызвать у сигнала `set` или `update` может кто угодно, у кого есть корзина. Проверим.

## Эксперимент: «Хочу 99»

Добавьте в `MiniCart` метод, который пишет в корзину в обход её методов:

```ts cart/mini-cart/mini-cart.ts
// Эксперимент: положить в корзину по 99 штук каждой игры
protected cheat() {
  this.cart.items.update((items) => items.map((item) => ({ ...item, quantity: 99 })));
}
```

и кнопку под заголовком в `mini-cart.html`:

```html cart/mini-cart/mini-cart.html
<h2>Корзина</h2>
<button (click)="cheat()">Хочу 99</button>
```

Положите в корзину «Остров сокровищ» и нажмите «Хочу 99». В мини-корзине «− 99 +» и 197 010 ₽, в шапке «В корзине: 99». На складе 12 коробок, кнопка «+» у количества дальше 12 не пускает, но корзине это безразлично: в неё записали напрямую. Аналитика ничего не узнала, правила корзины не сработали — их просто не спросили.

Ошибки нет ни в TypeScript, ни в консоли: с точки зрения кода всё законно. В маленьком приложении такую строку легко заметить. В большом — кто-то однажды напишет её в третьем по счёту компоненте «на минутку», и через полгода никто не сможет сказать, откуда в корзине взялось 99 коробок. Оставьте метод и кнопку — они пригодятся в конце шага.

## Хранилище

Сервис, который хранит состояние и сам следит за его правилами, называют **хранилищем** (store). У хранилища три части:

```
        компоненты
     читают     вызывают
       │            │
       ▼            ▼
 items, count,  add, remove,
 total          setQuantity,
 (Signal)       clear
       ▲            │
       │            ▼
       └── state ◄──┘
     закрытый signal
```

- **состояние** (state) — закрытый изменяемый сигнал. Менять его может только сам сервис;
- **чтение** — сигналы только для чтения: само состояние и всё, что из него вычисляется (`count`, `total`);
- **действия** (actions) — методы, которые меняют состояние: `add`, `setQuantity`, `remove`, `clear`. Только через них, и потому правила корзины живут в одном месте.

Чтобы снаружи состояние можно было только читать, у изменяемого сигнала есть метод `asReadonly()`. Он возвращает `Signal<T>` — тот же сигнал, но без `set` и `update`:

```ts core/cart-store.ts {1,2,4,5}
// Состояние корзины — позиции. Менять его может только сам сервис: поле закрытое
private readonly state = signal<readonly CartItem[]>([]);

// Снаружи — только чтение: у Signal нет set и update
readonly items = this.state.asReadonly();
```

Снаружи ничего не изменилось: компоненты по-прежнему пишут `cart.items()`, шаблон мини-корзины трогать не нужно. А внутри методы пишут в `state`:

```ts core/cart-store.ts {2,6}
remove(game: Game) {
  this.state.update((items) => items.filter((item) => item.game.id !== game.id));
}

clear() {
  this.state.set([]);
}
```

## Неизменяемые позиции

Закрыть `set` и `update` мало: массив позиций — обычный массив, его можно поменять на месте — `cart.items().push(…)` или `cart.items()[0].quantity = 99`. В главе 3 мы выяснили, что такое изменение сигнал не замечает: экран не обновится, а состояние испортится.

Здесь помогает TypeScript. Тип `readonly CartItem[]` — массив без методов, которые его меняют (`push`, `splice`, `sort`…). А поля позиции закроем в модели:

```ts core/models.ts {3,4}
// Позиция корзины: какая игра и сколько штук. Позицию не меняют, а заменяют новой
export interface CartItem {
  readonly game: Game;
  readonly quantity: number;
}
```

Код корзины уже написан так, как требуют эти типы: каждое действие создаёт новый массив, а изменённую позицию — новым объектом `{ ...item, quantity }`. Поэтому ни одна строка в нём не сломается.

::: task
1. В `core/cart-store.ts` сделайте позиции корзины закрытым сигналом `state` с типом `readonly CartItem[]`, а открытым полем `items` — `this.state.asReadonly()`. В действиях пишите в `state`.
2. В `core/models.ts` сделайте поля `CartItem` только для чтения.
:::

## Что получилось

Внешне ничего — магазин работает как раньше. Положите игру, поменяйте количество, очистите корзину.

Теперь нажмите «Хочу 99». В консоли превью — ошибка TypeScript:

```
TS2339: Property 'update' does not exist on type 'Signal<readonly CartItem[]>'.
```

(и ещё две TS7006 про параметры `items` и `item`: тип у них пропал вместе с методом). Код при этом запустился — ошибки TypeScript в превью запуск не останавливают, — а щелчок по кнопке даёт ошибку выполнения:

```
ERROR TypeError: this.cart.items.update is not a function
```

Корзина не изменилась. Попробуйте и два других способа — в методе `cheat`:

```ts
this.cart.items().push({ game: this.cart.items()[0].game, quantity: 99 });
this.cart.items()[0].quantity = 99;
```

TypeScript отвечает `TS2339: Property 'push' does not exist on type 'readonly CartItem[]'` и `TS2540: Cannot assign to 'quantity' because it is a read-only property`. Теперь удалите метод `cheat` и кнопку «Хочу 99».

::: warning `readonly` — проверка TypeScript, а не защита
Во время выполнения `readonly CartItem[]` — обычный массив, а поля позиции — обычные поля. `(cart.items() as CartItem[]).push(…)` скомпилируется и испортит состояние. Закрытое поле и типы только для чтения — договорённость, которую проверяет компилятор. Обходить её приходится нарочно, и в обзоре кода это сразу видно. Для состояния приложения этого почти всегда достаточно.
:::

## Что держать в хранилище, а что в компоненте

Не всё, что меняется, — состояние приложения. Строка поиска, открытое окно «Подробнее», выбранная вкладка, показ «Нет такого промокода» в следующих шагах нужны одному компоненту и живут, пока он на экране. Это **состояние интерфейса** (UI state), и место ему — в сигналах самого компонента:

| | Состояние приложения | Состояние интерфейса |
|---|---|---|
| Пример | корзина, избранное, вошедший пользователь | текст в поле поиска, открытое окно, вкладка |
| Кому нужно | нескольким компонентам, которые друг о друге не знают | одному компоненту и его детям |
| Сколько живёт | дольше любого компонента, иногда между запусками | пока компонент на экране |
| Где | сервис-хранилище | сигналы компонента |

Если сомневаетесь, спросите себя: «что должно случиться с этим значением, когда компонент исчезнет?» Если оно должно исчезнуть вместе с ним — это состояние интерфейса.

Кстати, `FavoritesStore` из практикума главы 8 уже устроен как хранилище: закрытый сигнал `ids`, вычисляемый `count`, действие `toggle` и чтение через `has`.

::: deep Под капотом: что возвращает asReadonly()
`asReadonly()` не копирует ни значение, ни сигнал. В `@angular/core` это функция-читатель, которая вызывает исходный сигнал, и к ней прикреплён **тот же узел графа** (свойство с символом `SIGNAL`, глава 3). Функция создаётся при первом вызове и запоминается в узле: второй `asReadonly()` вернёт её же. Поэтому сигнал только для чтения ничего не стоит: нет второго узла, нет пересчёта, нет лишней зависимости в графе.

Можно было бы написать `readonly items = computed(() => this.state())` — снаружи тоже `Signal`, но это отдельный узел, который читает `state` и хранит копию значения. Или геттер `get items() { return this.state(); }` — тоже реактивно, но тогда наружу уходит значение, а не сигнал, и его нельзя передать дальше как источник, например в `linkedSignal`.
:::

::: tip Если вы знаете React или Vue
Хранилище на сигналах похоже на хранилище Pinia во Vue (`state`, `getters`, `actions`) или на связку `useReducer` + контекст в React: состояние в одном месте, наружу — чтение и набор действий. В Angular для этого не нужна библиотека: сигналы дают реактивное чтение, а DI — один экземпляр на приложение.
:::
