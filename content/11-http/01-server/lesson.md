Все игры «Хода конём» до сих пор лежат прямо в коде, в массиве `GAMES` из `core/games-data.ts`. Для учебника это удобно, для магазина — нет. Цены меняются, остаток на складе уменьшается, когда игры покупают другие люди, новые игры добавляет менеджер в админке. Код в браузере покупателя об этом не узнает: он знает только то, что было в нём на момент сборки.

Поэтому в настоящем магазине данные живут на **сервере**, а приложение в браузере просит их по сети, когда они нужны. Эта глава — о том, как Angular разговаривает с сервером. К концу главы у магазина появятся:

- главная, каталог и страница игры с данными с сервера — с заглушками на время загрузки и сообщением, если сервер не ответил;
- поиск, который отправляет запрос, когда покупатель перестал печатать;
- «Игра не найдена» по ответу сервера, а не по поиску в массиве;
- избранное и корзина, которым больше не нужен список игр в коде;
- отзывы об игре, которые можно написать прямо на странице;
- каталог, который загружается с сервера порциями, — в практикуме.

А в конце главы заглянем внутрь ресурса — главного инструмента Angular для загрузки данных.

## Что изменилось в коде

Код — решение практикума главы 10. Добавились только глобальные стили в `styles.css`: `.skeleton` — серый мигающий блок размером с карточку, его показывают, пока данные грузятся, и `.error-message` — для сообщений «не удалось загрузить». Они понадобятся с третьего шага.

## API сервера

Сервер магазина отвечает на запросы по адресам, которые начинаются с `/api/`. Такой набор адресов называют **API сервера**: приложение отправляет запрос на адрес и получает ответ — данные в формате **JSON**. Вот адреса, которые понадобятся в этой главе:

| Запрос | Ответ |
|---|---|
| `GET /api/games` | страница каталога: `{ items, total, page, size }` |
| `GET /api/games/4` | одна игра или ошибка 404 |
| `GET /api/games/4/reviews` | отзывы об игре |
| `POST /api/games/4/reviews` | сохранить новый отзыв |

`GET` и `POST` — методы HTTP: `GET` просит данные, `POST` отправляет новые. У списка игр есть параметры: `q` — поиск, `sort` — сортировка (`price`, `-price`, `rating`), `page` и `size` — какую страницу каталога и по сколько игр. Например, `/api/games?sort=rating&size=4` — первые четыре игры по рейтингу. Сервер присылает не просто массив, а **страницу**: сами игры в `items` и сколько всего нашлось в `total`.

Опишем ответ типом в `core/models.ts`:

```ts core/models.ts
// Страница каталога, которую присылает сервер: GET /api/games
export interface GamesPage {
  items: Game[]; // игры этой страницы
  total: number; // сколько игр нашлось всего
  page: number; // номер страницы, с 1
  size: number; // сколько игр на странице
}
```

## Учебный бэкенд

Настоящего сервера у превью нет. Его заменяет **учебный бэкенд** — небольшая программа внутри превью. Он перехватывает запросы приложения на адреса `/api/…`, отвечает данными магазина и показывает каждый запрос во вкладке «Сеть» под превью. Данные живут в памяти: при каждом запуске кода они снова как в начале.

У настоящего сервера два свойства, которых не бывает у массива в коде: он отвечает **не сразу** и отвечает **не всегда**. Учебный бэкенд умеет и то и другое. Во вкладке «Сеть» есть список «Задержка» — сколько миллисекунд ждать перед ответом (по умолчанию 300), и флажок «Ошибка 500» — все запросы отвечают ошибкой сервера. Ими мы будем проверять, как магазин ведёт себя в плохих условиях.

## Первый запрос

Начнём с главной: пусть подборку «Хиты» присылает сервер. Для запроса пока возьмём то, что уже есть в браузере, — функцию `fetch`:

```ts home/home.ts {2,6-8}
// Хиты — четыре игры с самым высоким рейтингом. Их присылает сервер, а пока ответа нет, список пуст
protected readonly hits = signal<Game[]>([]);

constructor() {
  // Запрос к API магазина: первые 4 игры каталога, отсортированные по рейтингу
  fetch('/api/games?sort=rating&size=4')
    .then((response) => response.json())
    .then((page: GamesPage) => this.hits.set(page.items));
}
```

`fetch` возвращает промис ответа, `response.json()` — промис уже разобранного JSON. Когда он выполнится, игры попадут в сигнал `hits`.

Почему сигнал, а не обычное поле? Ответ приходит позже, не из события шаблона. Из главы 3 вы помните: в зонлесс-приложении Angular не следит за таймерами и запросами, а проверяет компонент, когда тот помечен. Изменение сигнала, который читает шаблон, такую пометку ставит. Изменение обычного поля — нет.

::: task
1. Добавьте интерфейс `GamesPage` в `core/models.ts`.
2. В `home/home.ts` сделайте `hits` сигналом `signal<Game[]>([])` и заполните его в конструкторе ответом на `fetch('/api/games?sort=rating&size=4')`.
3. В `home.html` замените `hits` на `hits()`.
:::

## Что получилось

В «Хитах» — «Шахматы «Классика»», «Глубокий космос», «Ночной экспресс» и «Го». «Глубокий космос» — из новых игр: его нет в `GAMES`, значит данные действительно пришли с сервера.

Откройте вкладку «Сеть». Там строка `GET /api/games?sort=rating&size=4`, статус `200` и время ответа. Щёлкните по ней — внизу появится тело ответа: `items` с четырьмя играми, `total: 40`, `page: 1`, `size: 4`.

## Эксперименты

**Медленный сервер.** Поставьте во вкладке «Сеть» задержку 3000 мс и перезапустите превью кнопкой ⟳. Три секунды под заголовком «Хиты» пусто, а потом карточки появляются разом. Покупатель в это время не понимает, что происходит: подборка пустая или ещё грузится? Это мы исправим в шаге 3.

**Обычное поле.** Замените сигнал обычным полем: `protected hits: Game[] = []`, в `then` — `this.hits = page.items`, а в шаблоне снова `hits`. При задержке 300 мс хиты не появятся, хотя ответ пришёл: Angular не знает, что поле изменилось. Мы проверили: поле получает четыре игры (это видно, если добавить в `then` вывод в консоль), а на экране только «Со скидкой». При задержке 0 мс хиты могут и появиться — ответ успевает прийти, пока приложение ещё запускается. Полагаться на это нельзя. Верните сигнал.

**Сервер с ошибкой.** Включите флажок «Ошибка 500» и перезапустите превью. В «Сети» — статус `500`, а на экране… ничего: «Хиты» просто пустые, в консоли ни одной ошибки. Дело в том, что `fetch` считает ответ 500 нормальным ответом: промис выполняется, а не отклоняется. Тело такого ответа — `{ message: 'Сервер недоступен…' }`, поля `items` в нём нет, и в сигнал записывается `undefined`. TypeScript тоже не помог: аннотация `page: GamesPage` — обещание, которое мы дали компилятору, а не проверка того, что пришло по сети.

Чтобы `fetch` сообщал об ошибке, нужно проверять `response.ok` самим, и делать это в каждом запросе. Выключите флажок.

::: tip
`fetch` отклоняет промис только тогда, когда ответа нет совсем: сеть недоступна или запрос отменён. Любой ответ сервера, даже 404 или 500, для него — успех.
:::

Проверку `response.ok`, разбор JSON, заголовки, повтор запроса можно написать вокруг `fetch` самим. Но в Angular для этого есть готовый инструмент — `HttpClient`. С него начнём следующий шаг.
