`fetch` справился с запросом, но в прошлом шаге мы увидели его характер: ответ 500 для него — успех, JSON нужно разбирать самим, параметры — склеивать в строку адреса. В настоящем приложении к этому добавится ещё многое: токен входа в каждом запросе, повтор при сбое, подмена сервера в тестах.

В Angular для этого есть **`HttpClient`** — сервис для запросов к серверу. Он сам разбирает JSON, считает ошибкой любой ответ не из диапазона 200–299, собирает параметры адреса из объекта. А главное — все запросы приложения проходят через одно место, и туда можно встроить общую логику: в главе 12 мы допишем к нему интерцепторы — например, лог каждого запроса, — а в главе 16 подменим сервер в тестах.

## Подключение

`HttpClient` — сервис, и, как у роутера, у него есть функция подключения `provide…()` для `app.config.ts`:

```ts app.config.ts {1,5-6}
import { provideHttpClient } from '@angular/common/http';

export const appConfig: ApplicationConfig = {
  providers: [
    // HttpClient — клиент HTTP: запросы к серверу через inject(HttpClient)
    provideHttpClient(),
    …
  ],
};
```

В отличие от роутера, сам `HttpClient` в Angular 22 доступен и без этой строки: он объявлен как сервис корневого инжектора (`providedIn: 'root'`), как наш `CartStore`. Зачем же `provideHttpClient()`? Через неё передают **настройки** клиента: `provideHttpClient(withInterceptors([…]))`, `provideHttpClient(withXhr())`. Поэтому строку обычно пишут сразу, даже без настроек, — в главе 12 в неё добавятся интерцепторы.

## Запрос

```ts home/home.ts {1,5-9}
private readonly http = inject(HttpClient);

constructor() {
  // get только описывает запрос: он уйдёт на сервер при подписке (subscribe)
  this.http
    .get<GamesPage>('/api/games', {
      params: { sort: 'rating', size: 4 },
    })
    .subscribe((page) => this.hits.set(page.items));
}
```

`get<GamesPage>(адрес, настройки)` — запрос методом `GET`. В угловых скобках — тип ответа: дальше TypeScript будет считать, что пришёл `GamesPage`. Это по-прежнему обещание, а не проверка, — но обещание дано в одном месте. `params` — параметры адреса объектом: `HttpClient` сам превратит их в `?sort=rating&size=4`.

А вот дальше непривычное. `get` возвращает не промис, а **Observable** — объект из библиотеки RxJS, на которой построена часть Angular. Подробно RxJS — в главе 12, а пока достаточно трёх свойств:

- Observable — **описание** работы, а не сама работа. Вызов `get` ничего не отправляет.
- Работа начинается при **подписке** (subscription) — вызове `subscribe(…)`. Функция, переданная в `subscribe`, получит ответ.
- Подписку можно **отменить** — вызвать у неё `unsubscribe()`. Если запрос ещё в пути, `HttpClient` его прервёт.

Промис запускает работу сразу, и у самого промиса нет отмены: чтобы прервать `fetch`, нужен отдельный объект `AbortController` (мы встретим его в шаге 6). Observable запускается подпиской и отменяется отпиской. Для запроса к серверу можно думать о нём как об «обещании с кнопкой отмены».

::: task
1. Подключите `provideHttpClient()` в `app.config.ts`.
2. В `Home` получите `HttpClient` через `inject` и замените `fetch` запросом `get<GamesPage>('/api/games', { params: { sort: 'rating', size: 4 } })` с подпиской, которая кладёт игры в `hits`.
:::

## Что получилось

Внешне ничего не поменялось — те же четыре хита. Во вкладке «Сеть» тот же запрос: `GET /api/games?sort=rating&size=4`. Адрес собрал `HttpClient` из объекта `params`.

::: deep Под капотом: HttpClient и fetch
В Angular 22 `HttpClient` по умолчанию отправляет запросы через тот же `fetch` браузера: за это отвечает класс `FetchBackend`. Поэтому учебный бэкенд, который перехватывает `fetch`, видит и запросы `HttpClient`. Раньше по умолчанию использовался `XMLHttpRequest`. Он по-прежнему доступен — `provideHttpClient(withXhr())`. Например, он нужен, чтобы следить за прогрессом **отправки** файла на сервер: `FetchBackend` такое не поддерживает и в режиме разработки говорит об этом ошибкой с советом подключить `withXhr()`.
:::

## Эксперименты

**Без `provideHttpClient()`.** Уберите строку из `app.config.ts` и перезапустите превью: хиты на месте, ошибок нет. Клиент нашёлся в корневом инжекторе с настройками по умолчанию. Верните строку.

**Без подписки.** Уберите `.subscribe(…)`, оставив только `this.http.get<GamesPage>(…)`. Перезапустите превью и откройте «Сеть»: запроса нет вообще. Observable никто не запустил. Верните подписку.

**Ошибка сервера.** Включите «Ошибку 500» и перезапустите превью. В отличие от `fetch`, теперь в консоли ошибка: `ERROR HttpErrorResponse {…}`. Для `HttpClient` ответ 500 — ошибка: Observable сообщает о ней, а не присылает ответ. Мы её не обработали, и Angular вывел её в консоль как необработанную.

Обработать ошибку можно вторым обработчиком — тогда в `subscribe` передают объект:

```ts
.subscribe({
  next: (page) => this.hits.set(page.items),
  error: (error: HttpErrorResponse) => console.error(error.status, error.message),
});
```

`next` получает ответ, `error` — ошибку. `HttpErrorResponse` — класс ошибки `HttpClient`: в нём есть `status` (код ответа) и `message`. С таким обработчиком в консоли будет `500 Http failure response for /api/games?sort=rating&size=4: 500`, а «Хиты» останутся пустыми — показать ошибку на экране мы научимся в следующем шаге. Выключите «Ошибку 500».

**Ушли, не дождавшись.** Поставьте задержку 3000 мс, перезапустите превью и сразу, пока хиты не загрузились, перейдите в «Каталог». Через три секунды в «Сети» у запроса статус `200`, а не «отменён». Главной уже нет, а запрос дошёл до конца, и функция из `subscribe` всё равно выполнилась — для уничтоженного компонента. Мы проверили это выводом в консоль: сначала «Home уничтожен», потом «ответ пришёл».

Здесь это безобидно: сигнал уничтоженного компонента никто не читает. Но представьте страницу, которая при ответе показывает сообщение или переходит на другой адрес. Покупатель уже ушёл, а сообщение всплывает.

Чтобы этого не было, подписку нужно отменять, когда компонент уничтожается:

```ts
const subscription = this.http.get<GamesPage>(…).subscribe(…);
inject(DestroyRef).onDestroy(() => subscription.unsubscribe());
```

Теперь при уходе со страницы запрос в «Сети» будет «отменён». Работает, но для каждого запроса — подписка, отписка, сигнал для ответа, ещё один для ошибки и третий — чтобы показать «загружается». В следующем шаге всё это сделает за нас одна функция.

::: legacy Вы встретите в старом коде: HttpClientModule и конструктор
До появления `provideHttpClient()` клиент подключали модулем:

```ts
@NgModule({ imports: [HttpClientModule] })
export class AppModule {}
```

Сервис получали параметром конструктора:

```ts
constructor(private http: HttpClient) {}
```

И часто встречается `provideHttpClient(withFetch())` — так включали `fetch` вместо `XMLHttpRequest`, когда по умолчанию использовался `XMLHttpRequest`. В Angular 22 `withFetch()` помечена устаревшей: `fetch` и так используется по умолчанию.
:::
