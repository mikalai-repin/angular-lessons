За главу мы собрали несколько правил, которые проверили опытом, но не объяснили. При смене параметров значение ресурса пропадает, а при `reload()` остаётся. Во время повтора `error()` помнит прошлую ошибку. Устаревший запрос отменяется, а его ответ не попадает на экран. В этом шаге откроем, как устроен ресурс внутри, — и все эти правила окажутся следствиями нескольких строк кода. Шаг необязательный: для работы с ресурсами знать это не нужно.

## Журнал статусов

В коде шага — помощник `resource-log.ts`:

```ts resource-log.ts
export function logResource(
  name: string,
  resource: Resource<unknown>,
) {
  let previous = '—';
  effect(() => {
    const status = resource.status();
    // value() ресурса с ошибкой бросает исключение — читаем значение, только если оно есть
    const details =
      status === 'error'
        ? `, ошибка: ${resource.error()?.message}`
        : resource.hasValue()
          ? ', значение есть'
          : '';
    console.log(`${name}: ${previous} → ${status}${details}`);
    previous = status;
  });
}
```

Это эффект, который при каждой смене `status()` пишет в консоль переход. Каталог вызывает его для своего ресурса, страница игры — для игры и отзывов, в конструкторе. Эффект видит не каждое промежуточное значение, а то, что было на момент его запуска (глава 3), — но статусы ресурса меняются при ответах сервера, не чаще.

## Шесть статусов

| Статус | Когда | `value()` |
|---|---|---|
| `idle` | параметры — `undefined`: загружать нечего | `undefined` |
| `loading` | новые параметры, ждём ответа | `undefined` (или `defaultValue`) |
| `reloading` | `reload()` с теми же параметрами | прежнее значение |
| `resolved` | ответ получен | ответ |
| `error` | загрузка не удалась | **бросает исключение** |
| `local` | значение задано `set()` или `update()` | заданное значение |

`isLoading()` — это `loading` или `reloading`. А `hasValue()` — «не ошибка и `value()` не `undefined`». Поэтому у ресурса с `defaultValue` `hasValue()` верно даже во время загрузки: в журнале отзывов видно `— → loading, значение есть`.

## Эксперименты с журналом

Превью открыто на каталоге. В консоли:

```
Каталог: — → loading
Каталог: loading → resolved, значение есть
```

- **Поиск.** Наберите «кот»: `resolved → loading`, потом `loading → resolved`. Благодаря `debounced` — один раз, а не на каждую букву.
- **Ошибка и повтор.** Включите «Ошибку 500», смените сортировку — `loading → error, ошибка: Http failure response for …: 500`. Выключите флажок и нажмите «Повторить» — `error → reloading`, затем `reloading → resolved`. Не `loading`, а `reloading`: параметры те же.
- **Страница игры.** Откройте любую игру и отправьте отзыв: `Отзывы: resolved → local`. Ответ сервера тоже заменяет черновик через `update`, поэтому статус так и остаётся `local`. Из `local` ресурс выходит, только когда меняются параметры: мы проверили переходом на другую игру без пересоздания страницы — `Отзывы: local → loading`. С экрана так перейти нельзя (на странице игры нет ссылок на другие игры): через каталог страница создаётся заново, и журнал начинается с `— → loading`.
- **Отсутствующая игра.** Наберите в адресной строке `/games/999`: `Игра: loading → error, ошибка: Http failure response for /api/games/999: 404`.

## Как устроен resource

Мы прочитали `resource` в исходниках `@angular/core` 22.2.1 (`_resource-chunk.mjs`, класс `ResourceImpl`). Внутри три части — и все они уже знакомы по главе 3.

```
 params()  ─┐
 reload()  ─┴► extRequest  (linkedSignal)
                  │
                  ▼
               state       (linkedSignal)
              status, поток значения
                  │
        ┌─────────┴─────────┐
        ▼                   ▼
 value, error,          loadEffect
 status (computed)      (effect)
                        вызывает loader
```

**1. `extRequest` — что загружать.** `linkedSignal`, который вызывает вашу функцию `params` (у `httpResource` — функцию запроса) и добавляет к результату счётчик перезагрузок: `{ request, reload: 0 }`. Вот почему функция запроса реактивна: это обычное вычисление `linkedSignal`, и прочитанные внутри сигналы становятся его зависимостями. `reload()` увеличивает счётчик — получается новый объект с тем же `request`. Если ресурс в статусе `idle` или уже `loading`, `reload()` ничего не делает и возвращает `false`.

**2. `state` — в каком состоянии ресурс.** Второй `linkedSignal`, его источник — `extRequest`. При каждом новом `extRequest` он решает:

- `request` — `undefined` → статус `idle`;
- иначе статус `loading`, и **если `request` тот же, что был** (это `reload()`), прежний результат загрузки сохраняется.

Здесь объясняются два наших правила. Новые параметры — прежнего результата нет, `value()` — `undefined`. Перезагрузка — прежний результат остаётся. Ведь «результат» — это и значение, и ошибка: поэтому во время повтора `error()` помнит прошлую ошибку. Статус `reloading` отдельно не хранится: `status()` — это `computed`, который показывает `loading` с ненулевым счётчиком перезагрузок как `reloading`.

**3. `loadEffect` — кто загружает.** Обычный `effect`, который читает `extRequest`. Когда статус `loading`, он:

1. отменяет прошлую загрузку: у каждой загрузки свой `AbortController`, и вызов `abort()` срабатывает тем самым `abortSignal`, который получил загрузчик;
2. создаёт новый `AbortController` и вызывает ваш `loader` с `params`, `abortSignal` и прошлым статусом — внутри `untracked`, чтобы сигналы, прочитанные загрузчиком, не стали зависимостями эффекта;
3. дождавшись ответа, проверяет, **не устарел ли он**: отменена ли эта загрузка или `extRequest` уже другой. Если устарел — ответ выбрасывается. Иначе `state` получает статус `resolved` и результат.

Пункт 3 защищает от **гонки** (race condition). Допустим, ответ на «ко» пришёл позже ответа на «кот» — так бывает с настоящим сервером. Ресурс сравнит запрос загрузки с текущим и выбросит устаревший ответ. Даже если загрузчик не передал `abortSignal` в `fetch`, старые данные на экран не попадут. Отмена через `abortSignal` экономит сеть, а проверка в пункте 3 гарантирует правильный результат.

Ещё три детали:

- `value` — `computed` поверх результата. Если в результате ошибка, он бросает `ResourceValueError` с текстом «Resource is currently in an error state» — отсюда исключение `value()`. Исходная ошибка лежит в `cause`.
- При создании ресурс подписывается на уничтожение через `DestroyRef`. Уничтожение — отмена загрузки и статус `idle`. Поэтому ресурсу нужен контекст внедрения.
- `set()` и `update()` записывают в `state` статус `local` и отменяют идущую загрузку: значение, заданное в коде, важнее ответа, который ещё в пути.

## А httpResource?

`httpResource` (класс `HttpResourceImpl` в `@angular/common/http`) — тот же `ResourceImpl` с готовым загрузчиком. Загрузчик вызывает `HttpClient.request(…)` и подписывается, а на `abortSignal` вешает отписку. Отписка от `HttpClient` прерывает `fetch` — и в «Сети» появляется «отменён». Сверх обычного ресурса у `httpResource` есть сигналы `statusCode()`, `headers()` и `progress()` — код и заголовки ответа, прогресс загрузки.

## PendingTasks: Angular ждёт данные

Во втором пункте загрузки есть ещё одна строка: перед вызовом загрузчика ресурс регистрирует задачу в сервисе **`PendingTasks`** и снимает её, когда загрузка закончилась. `HttpClient` делает то же для своих запросов. `PendingTasks` — счётчик незавершённой работы приложения. Метод `ApplicationRef.whenStable()` ждёт, пока он обнулится.

Зачем? Документация `PendingTasks` называет два случая. При серверном рендеринге (глава 20) Angular строит HTML страницы на сервере и должен дождаться стабильности приложения, прежде чем отправить этот HTML. Ресурсы и запросы `HttpClient` входят в счёт — значит, сервер дождётся данных и не отдаст страницу с заглушками. А тесты (глава 16) могут дождаться стабильности, прежде чем проверять экран.

## Итого

- Ресурс — два `linkedSignal` и `effect`: что загружать, в каком состоянии, кто загружает.
- Новые параметры — новый результат с нуля; `reload()` — тот же запрос, прежний результат до ответа.
- Устаревшие загрузки отменяются через `AbortController`, а их ответы выбрасываются, даже если пришли.
- `set`/`update` — статус `local`; уничтожение компонента — отмена и `idle`.
- Ресурсы и `HttpClient` сообщают Angular о незавершённой работе через `PendingTasks`.
