В главе 11 мы несколько раз встретили **Observable**: его возвращает `HttpClient`, на него подписывается `subscribe`, его превращает в промис `firstValueFrom`. Тогда хватало правила «Observable — обещание с кнопкой отмены». Но это только частный случай: запрос к серверу присылает одно значение и заканчивается. Observable умеет больше — присылать **много значений во времени**.

Observable — класс из библиотеки **RxJS**. Angular использует её в нескольких местах: `HttpClient`, события роутера, реактивные формы. Сигналы закрыли большую часть задач, для которых раньше брали RxJS, но не все. Эта глава — необходимый минимум RxJS: чтобы читать существующий код на Angular (его много) и решать задачи, где поток событий удобнее сигнала. К концу главы у магазина появятся:

- журнал просмотров страниц для аналитики;
- быстрый поиск в шапке с подсказками, который не засыпает сервер запросами;
- «Избранное» и часы распродажи на RxJS — для сравнения с прежним кодом;
- интерцепторы: лог каждого запроса, повтор при сбое сервера и кэш, который убирает лишний запрос страницы игры;
- черновик комментария к заказу, который сохраняется сам, — в практикуме.

А в конце главы сравним сигналы и потоки: когда что брать.

## Поток значений

Сигнал хранит **текущее значение**: его можно прочитать в любой момент. Observable устроен иначе: он **присылает** значения, когда они появляются, тому, кто подписан. Прочитать «текущее значение» Observable нельзя — можно только дождаться следующего.

Удобно представлять поток на оси времени. Такие картинки называют **диаграммами потока** (marble diagrams):

```text
события роутера:
-S--R--…--E---------S--R--…--E---->
 переход на /       на /catalog
```

Каждая буква — значение (`S` — начало навигации, `R` — маршрут распознан, `E` — конец), стрелка — время. Поток может прислать три вида сообщений:

- **значение** (`next`) — сколько угодно раз;
- **ошибку** (`error`) — и после неё поток закончен;
- **завершение** (`complete`) — значений больше не будет.

Запрос `HttpClient` — короткий поток: одно значение (ответ) и сразу завершение. А события роутера — длинный поток: он не завершается, пока работает приложение.

## Подписка

Роутер сообщает о каждом шаге навигации событием: навигация началась, маршрут распознан, гарды проверены, навигация закончилась. Все события — в потоке `Router.events`. Подпишемся на него и выведем каждое событие в консоль:

```ts app.ts {1-2,7-9}
import { Component, inject } from '@angular/core';
import { Router, RouterOutlet } from '@angular/router';

export class App {
  constructor() {
    // События роутера — Observable: пока работает приложение, роутер присылает их одно за другим
    inject(Router).events.subscribe((event) =>
      console.log(String(event)),
    );
  }
}
```

`subscribe` принимает функцию, которую поток будет вызывать с каждым значением. Вызов `subscribe` — это и есть **подписка** (subscription): с этого момента поток знает о нас. `String(event)` превращает событие в строку: у событий роутера есть понятный `toString()`.

## Как устроен Observable

Observable — это обёртка над функцией, которая **запускается при подписке**. Сделаем поток сами — таймер, который раз в секунду присылает следующее число:

```ts
import { Observable } from 'rxjs';

const ticks = new Observable<number>((subscriber) => {
  console.log('Подписка: запускаем таймер');
  let n = 0;
  const timer = setInterval(() => subscriber.next(++n), 1000);
  // Функция уборки: её вызовет отписка
  return () => {
    console.log('Отписка: останавливаем таймер');
    clearInterval(timer);
  };
});
```

Функция внутри `new Observable` получает `subscriber` — того, кто подписался — и шлёт ему значения через `subscriber.next(…)`. Ошибку отправил бы `subscriber.error(…)`, завершение — `subscriber.complete()`. Возвращает она **функцию уборки** (teardown): RxJS вызовет её, когда подписку отменят или поток завершится.

Пока на `ticks` никто не подписан, ничего не происходит: таймера нет. Подпишемся, а через 3,5 секунды отменим подписку:

```ts
const subscription = ticks.subscribe((n) => console.log('Тик', n));
setTimeout(() => subscription.unsubscribe(), 3500);
```

`subscribe` возвращает объект подписки `Subscription`, а его `unsubscribe()` — **отписка**: «больше не присылай». В консоли:

```text
Подписка: запускаем таймер
Тик 1
Тик 2
Тик 3
Отписка: останавливаем таймер
```

Так устроен и `HttpClient.get`: функция подписки отправляет запрос, а функция уборки его прерывает. Поэтому без подписки запроса нет, а отписка отменяет запрос, который ещё в пути, — мы видели это в главе 11.

## Холодные и горячие потоки

Подпишитесь на `ticks` дважды — и в консоли появятся два «Подписка: запускаем таймер» и два независимых счётчика. Функция подписки выполняется **для каждого подписчика заново**. Такой поток называют **холодным**: каждый подписчик получает свою работу.

`HttpClient.get` — тоже холодный. Мы проверили:

```ts
const game = inject(HttpClient).get('/api/games/1');
game.subscribe();
game.subscribe();
```

Во вкладке «Сеть» — два одинаковых запроса `GET /api/games/1`. Один объект Observable, но две подписки — два запроса.

`Router.events` устроен по-другому. Роутер шлёт события один раз — всем, кто подписан **в этот момент**, — и не ждёт подписчиков. Такой поток называют **горячим**. Опоздавший подписчик пропустит всё, что было до него. Проверьте сами — эксперимент ниже.

| | Холодный | Горячий |
|---|---|---|
| Когда начинается работа | при каждой подписке | независимо от подписчиков |
| Что получит второй подписчик | всё сначала, свою копию | то же, что и все, начиная с момента подписки |
| Примеры | `HttpClient.get`, `new Observable(…)` | `Router.events`, события DOM |

Этот вопрос — «холодный или горячий?» — стоит задавать каждому потоку. От ответа зависит, сколько раз уйдёт запрос и увидит ли подписчик событие, которое уже было.

## Эксперименты

**Свой поток.** Вставьте `ticks` и подписку с отпиской в конструктор `App` (импорт `Observable` — из `'rxjs'`) и посмотрите на консоль. Затем уберите `return` с функцией уборки, а в функцию таймера добавьте вывод: `setInterval(() => { console.log('таймер', n + 1); subscriber.next(++n); }, 1000)`. После отписки «Тик» больше не печатается: RxJS не передаёт значения тому, кто отписался. А «таймер 4», «таймер 5»… идут дальше. Подписчик ушёл, а работа продолжается, — функция уборки нужна, чтобы её остановить. Верните всё как было.

**Опоздавший подписчик.** Оберните подписку на события в таймер:

```ts
const router = inject(Router);
setTimeout(() => router.events.subscribe((event) => console.log(String(event))), 1000);
```

После запуска консоль пуста: первая навигация закончилась раньше, чем через секунду, и её события ушли, когда подписчика ещё не было. Нажмите «Каталог» — события второй навигации на месте. Верните подписку без таймера.

**Завершение.** Подпишитесь на запрос объектом с двумя функциями:

```ts
inject(HttpClient)
  .get('/api/games/1')
  .subscribe({
    next: () => console.log('Ответ'),
    complete: () => console.log('Завершён'),
  });
```

В консоли «Ответ» и сразу «Завершён»: запрос — поток из одного значения. Подпишитесь так же на `router.events` — «Завершён» не появится, сколько бы вы ни переходили по страницам.

::: deep Под капотом: откуда у Angular RxJS
Angular создавался, когда сигналов в нём не было. Для всего, что происходит во времени, — запросов, событий, ввода в формах — взяли RxJS: библиотеку, в которой любую последовательность событий можно описать одним типом и обработать одним набором инструментов. Поэтому `HttpClient`, роутер и реактивные формы построены на Observable.

Теперь основной инструмент для состояния — сигналы, и большую часть приложения можно написать без единого `subscribe`: в главе 11 мы так и сделали, кроме отправки отзыва. Но RxJS не исчез. В `package.json` пакета `@angular/core` `rxjs` указан обязательной зависимостью (peer dependency, в отличие от необязательного `zone.js`), а мост между двумя мирами — `@angular/core/rxjs-interop` — часть фреймворка. Его мы разберём в шаге 4.
:::
