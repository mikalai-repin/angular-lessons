Магазину нужна аналитика: какие страницы смотрят покупатели. Каждый **просмотр страницы** — запись в журнал аналитики. Источник у нас уже есть: события роутера. Но из 12 событий навигации просмотру соответствует одно — `NavigationEnd`, «навигация закончилась». А из него нужен только адрес.

Можно написать это внутри `subscribe` — с `if` и `instanceof`. Для одной подписки это нормально. Но в RxJS есть способ лучше: описать обработку потока цепочкой маленьких шагов — **операторов**.

## Операторы и pipe

**Оператор** — функция, которая принимает поток и возвращает **новый** поток. Исходный поток она не меняет. Два самых частых оператора делают с потоком то же, что одноимённые методы массива:

- `filter(условие)` — пропускает только значения, для которых условие истинно;
- `map(функция)` — заменяет каждое значение результатом функции.

На диаграмме потока:

```text
events:      -S--R--E----S--R--E---->
filter(End): -------E-----------E--->
map(url):    -------/-----------/catalog
```

Операторы соединяют методом `pipe` («труба»): значения входят слева, проходят операторы по очереди, выходят справа. `pipe` тоже возвращает новый поток, на который и подписываемся:

```ts app.ts {7-10}
import { filter, map } from 'rxjs';

constructor() {
  // Просмотр страницы — завершённая навигация. Из всех событий роутера берём NavigationEnd,
  // а из него — адрес, на котором покупатель оказался после всех переадресаций
  inject(Router)
    .events.pipe(
      filter((event) => event instanceof NavigationEnd),
      map((event) => event.urlAfterRedirects),
    )
    .subscribe((url) =>
      this.analytics().then((analytics) =>
        analytics.track('Просмотр страницы', url),
      ),
    );
}
```

Операторы импортируются из `'rxjs'`, как и `Observable`. `NavigationEnd` — класс события из `@angular/router`.

Обратите внимание на `map`: внутри него `event` уже не «любое событие роутера», а `NavigationEnd`, у которого есть `urlAfterRedirects`. TypeScript понял, что функция в `filter` — проверка типа, и сузил тип значений после неё. Каждый оператор знает тип того, что входит, и того, что выходит, поэтому ошибки в цепочке видны в редакторе.

**Аналитика** — сервис `Analytics` из главы 8: пока он просто пишет события в консоль. Его модуль загружается лениво, через `injectAsync`, как в `CartStore`:

```ts app.ts
// Аналитика загружается отдельно, при первом вызове — как в корзине
private readonly analytics = injectAsync(() =>
  import('./core/analytics').then((m) => m.Analytics),
);
```

`this.analytics()` возвращает промис сервиса — запись делаем в `then`.

::: task
1. Добавьте в `App` поле `analytics` с ленивой загрузкой `Analytics` через `injectAsync`, как в `CartStore`.
2. Замените вывод всех событий потоком просмотров: `pipe` с `filter` (только `NavigationEnd`) и `map` (адрес `urlAfterRedirects`). В `subscribe` записывайте `track('Просмотр страницы', url)`.
:::

## Что получилось

Вместо 12 строк на переход — одна:

```text
Аналитика: модуль загружен
Аналитика: экземпляр создан
Аналитика: Просмотр страницы — /
```

Походите по магазину: каждый переход — строка «Просмотр страницы» с адресом.

## Значения идут по одному

Цепочка операторов — не массив. Массив сначала целиком фильтруется, потом целиком преобразуется. Поток обрабатывает **каждое значение отдельно**, по мере появления: пришло событие — прошло `filter` — сразу попало в `map` — сразу в `subscribe`. Следующее событие ещё не случилось.

И ещё одно отличие от массива: цепочка ничего не делает, пока на неё не подписались. `pipe(filter(…), map(…))` только описывает обработку, как `HttpClient.get` описывает запрос. Работа начнётся с `subscribe` — и каждая подписка получит свою цепочку.

## tap: подсмотреть в поток

Отлаживать цепочку помогает оператор `tap` («кран»): он выполняет функцию для каждого значения и пропускает значение дальше без изменений. Поставьте его в начало цепочки:

```ts
.events.pipe(
  tap((event) => console.log(String(event))),
  filter((event) => event instanceof NavigationEnd),
  map((event) => event.urlAfterRedirects),
)
```

Теперь в консоли снова все события, а между ними — «Просмотр страницы». Перенесите `tap` после `filter` — останутся только `NavigationEnd`. Так видно, что именно проходит каждый участок трубы. `tap` удобен и для **побочных эффектов** посреди потока — в шаге 7 на нём будет держаться лог запросов. Уберите `tap` после эксперимента (и его импорт).

## Эксперименты

**Без фильтра.** Уберите строку с `filter`. Редактор подчеркнёт `urlAfterRedirects`: `Property 'urlAfterRedirects' does not exist on type 'Event'` — у события `NavigationStart`, например, такого поля нет. Превью всё равно запустится: ошибки типов не мешают выполнению. В консоли на каждый переход 12 строк «Просмотр страницы», то с адресом, то с `undefined`. Порядок операторов важен: верните `filter` перед `map`.

**Переадресация.** Введите в адресную строку превью `/account`. Роутер переадресует на `/account/favorites` (так настроено в главе 10), и в журнале — `Просмотр страницы — /account/favorites`. Замените `urlAfterRedirects` на `url` — и запишется `/account`, адрес, который покупатель не видел. Верните `urlAfterRedirects`.

**Отменённая навигация.** С пустой корзиной введите адрес `/checkout`. Гард не пустит на оформление и отправит в корзину: в журнале только `Просмотр страницы — /cart`. Навигация на `/checkout` закончилась не `NavigationEnd`, а `NavigationCancel`, и фильтр её не пропустил. Просмотра оформления не было — и в журнале его нет.

::: legacy Вы встретите в старом коде: операторы из rxjs/operators и цепочки через точку
До RxJS 7.2 операторы импортировали из отдельного пути:

```ts
import { filter, map } from 'rxjs/operators';
```

Этот путь работает и сейчас, но в `CHANGELOG` RxJS 7.2 сказано, что все операторы экспортируются из `'rxjs'` и импортировать их рекомендуется оттуда.

В совсем старом коде (RxJS 5) операторы добавлялись методами к самому Observable: `events.filter(…).map(…)`. В RxJS 6 такие операторы-методы убрали из основного пакета, остались функции внутри `pipe`.
:::
