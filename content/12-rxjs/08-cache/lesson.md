Посмотрите на лог при открытии страницы игры:

```text
GET /api/games/4 → 200, 315 мс
GET /api/games/4 → 200, 302 мс
GET /api/games/4/reviews → 200, 303 мс
```

Игра 4 загружается дважды. Мы заметили это ещё в шаге 11.5: резолвер хлебной крошки загружает игру ради названия, а через мгновение страница загружает её снова. На медленном сервере это заметно: поставьте задержку 1000 мс и откройте игру из каталога. Сначала секунду ничего не происходит — ждёт резолвер, — потом появляется страница с «Загружаем…» ещё на секунду. Мы замерили при задержке 1500 мс: страница появляется через 1,5 с, а игра на ней — только через 3,1 с.

Второй запрос не нужен: тот же ответ пришёл секунду назад. Нужен **кэш** — место, где хранятся недавние ответы. И удобнее всего сделать его интерцептором: он видит каждый запрос и может ответить сам, не вызывая `next`.

## Что изменилось в коде

В `core/cache-interceptor.ts` — заготовка интерцептора `cacheInterceptor` и готовый сервис `ResponseCache`: в нём `Map` «адрес → ответ и время ответа». `get(адрес)` вернёт ответ, если ему меньше `MAX_AGE` — 10 секунд, иначе `undefined`; `set(адрес, ответ)` запоминает ответ.

## Какие запросы кэшировать

Кэшировать все `GET` подряд опасно. Остаток на складе, корзина на сервере, список заказов должны быть свежими: ответ десятисекундной давности может оказаться неправдой. Пусть код сам решает, какой запрос можно взять из кэша, — **меткой** на запросе.

Для меток у запроса есть **контекст** — `HttpContext`. Это словарь, который едет вместе с запросом через все интерцепторы, но **на сервер не уходит**. Ключи словаря — токены `HttpContextToken` со значением по умолчанию:

```ts core/cache-interceptor.ts
// Метка запроса «ответ можно взять из кэша». Значение по умолчанию — нельзя
export const CACHE = new HttpContextToken<boolean>(() => false);
```

Поставить метку — передать контекст в запрос:

```ts
http.get<Game>(url, {
  context: new HttpContext().set(CACHE, true),
});
```

А интерцептор читает её: `req.context.get(CACHE)`. У запроса без метки — значение по умолчанию, `false`.

## Интерцептор кэша

```ts core/cache-interceptor.ts
export const cacheInterceptor: HttpInterceptorFn = (req, next) => {
  if (req.method !== 'GET' || !req.context.get(CACHE)) {
    return next(req);
  }
  // Интерцептор выполняется в контексте внедрения: inject работает
  const cache = inject(ResponseCache);
  const cached = cache.get(req.urlWithParams);
  if (cached) {
    // Поток из одного готового ответа — для того, кто подписан, это обычный ответ сервера
    return of(cached);
  }
  return next(req).pipe(
    tap((event) => {
      if (event instanceof HttpResponse) {
        cache.set(req.urlWithParams, event);
      }
    }),
  );
};
```

Три случая:

- запрос без метки или не `GET` — дальше по цепочке, как будто кэша нет;
- в кэше свежий ответ — `of(cached)`: поток из одного значения, ответа. `next` не вызывается, и запрос не уходит на сервер;
- ответа нет — запрос уходит, а `tap` запоминает ответ. `HttpResponse` — класс события-ответа: `instanceof` отделяет его от события `Sent`.

`inject` внутри интерцептора работает: Angular вызывает интерцепторы в контексте внедрения. Сервис `ResponseCache` один на приложение, поэтому кэш живёт между переходами по страницам.

Место в цепочке — после лога, но перед повтором:

```ts app.config.ts
withInterceptors([
  loggingInterceptor,
  cacheInterceptor,
  retryInterceptor,
]),
```

Лог выше кэша и увидит каждый ответ, в том числе из кэша. Повтор ниже: ответ из кэша повторять незачем.

## Метки

Метку ставят оба места, которые загружают игру, — резолвер:

```ts game/game-title.ts
http.get<Game>(`/api/games/${route.paramMap.get('id')}`, {
  // Ответ запомнит кэш: через мгновение ту же игру попросит страница
  context: new HttpContext().set(CACHE, true),
}),
```

и `httpResource` страницы. Функция запроса возвращает теперь не строку адреса, а объект запроса — как в главе 11 с `params`:

```ts game/game-page.ts
protected readonly game = httpResource<Game>(() => ({
  url: `/api/games/${this.id()}`,
  context: new HttpContext().set(CACHE, true),
}));
```

::: task
1. Допишите `cacheInterceptor`: `GET` с меткой `CACHE` — свежий ответ из `ResponseCache` через `of`, иначе запрос и сохранение ответа (`tap`, `HttpResponse`). Остальные запросы — `next(req)`.
2. Подключите его в `app.config.ts` между `loggingInterceptor` и `retryInterceptor`.
3. Поставьте метку `CACHE` на запрос игры в резолвере (`game-title.ts`) и в `httpResource` страницы игры.
:::

## Что получилось

```text
GET /api/games/4 → 200, 319 мс
GET /api/games/4 → 200, 0 мс
GET /api/games/4/reviews → 200, 303 мс
```

Вторая строка — ответ из кэша: 0 мс, и в «Сети» его нет — запрос на сервер не уходил. Перейдите в каталог и через несколько секунд вернитесь на игру: обе строки с `0 мс`. А медленный сервер теперь выглядит так: страница появляется вместе с игрой, без второго «Загружаем…». При задержке 1500 мс мы замерили 1,56 с от щелчка до названия игры — вместо 3,1 с.

## Эксперименты

**Срок жизни.** Откройте игру, перейдите в каталог, подождите больше 10 секунд и вернитесь. Первый запрос — снова на сервер (`303 мс`), второй — из кэша: ответ устарел, и кэш его не отдал.

**Без метки.** Уберите `context` из `httpResource` страницы. Снова два запроса к серверу: резолвер положил ответ в кэш, но страница о кэше не просила. Верните метку.

**Кэш выше лога.** Переставьте `cacheInterceptor` первым в списке. Ответы из кэша пропали из лога: кэш отвечает раньше, чем запрос дошёл до лога. Верните порядок.

::: warning Кэш — это устаревшие данные
Ответ из кэша — снимок прошлого. Здесь это безопасно: за 10 секунд название и описание игры не изменятся, а цену и остаток всё равно сверит сервер при оформлении заказа. Но каждый кэш требует ответа на вопрос «когда он устаревает». Слишком долгий срок — покупатель видит старое; изменения через `POST`/`PUT` должны очищать связанные ответы. Поэтому кэш здесь — по метке и на 10 секунд.
:::

::: tip Как в настоящем проекте
Кэш бывает и у браузера: по заголовкам ответа (`Cache-Control`) он сам хранит ответы, и такой запрос может не дойти до сервера. Это настраивают на сервере, а не в Angular. А в приложениях с серверной отрисовкой (глава 20) у Angular есть встроенный кэш для другой задачи: ответы, полученные на сервере, передаются в браузер вместе со страницей, чтобы браузер не повторял те же запросы, — его настраивают `withHttpTransferCacheOptions`.
:::
