Форма собирает данные, но принимает что угодно: пустой e-mail, `user@`, пароль из одной буквы. Нужны **правила проверки**, и нужно показывать покупателю, что не так, — под тем полем, где ошибка.

## Схема: правила для полей

Правила передают вторым аргументом `form` — функцией **схемы**:

```ts login/login.ts {1-8}
protected readonly loginForm = form(this.model, (login) => {
  required(login.email, { message: 'Введите e-mail' });
  email(login.email, { message: 'Похоже, в адресе опечатка' });
  required(login.password, { message: 'Введите пароль' });
  minLength(login.password, 4, {
    message: 'Пароль — не короче 4 символов',
  });
});
```

Функция схемы выполняется **один раз** — при создании формы. Её аргумент `login` похож на форму, но это не поля, а **пути схемы**: `login.email` означает «поле `email`, каким бы ни было его значение». Значений у путей нет — ни сейчас, ни потом. Функция не проверяет данные сама, а **описывает** правила: «к полю `email` — правило `required`». Проверять будет форма — каждый раз, когда значение поля изменится.

Готовые правила проверки — функции из `@angular/forms/signals`:

| Правило | Ошибка, если… | `kind` ошибки |
|---|---|---|
| `required(path)` | пусто: `''`, `null`, `undefined`, `false`, `NaN` | `'required'` |
| `email(path)` | строка не похожа на e-mail (пустая — подходит) | `'email'` |
| `minLength(path, n)`, `maxLength(path, n)` | строка или массив короче или длиннее `n` | `'minLength'`, `'maxLength'` |
| `min(path, n)`, `max(path, n)` | число меньше или больше `n` | `'min'`, `'max'` |
| `pattern(path, /…/)` | строка не подходит под регулярное выражение | `'pattern'` |

Обратите внимание на `email`: пустая строка для него — не ошибка. Обязательность — отдельное правило, `required`. Так правила складываются: e-mail может быть необязательным, но если его ввели — без опечаток.

Последний аргумент — настройки правила. `message` — текст ошибки для покупателя. Без него у ошибки будет только `kind`, а текста не будет: Angular не знает, на каком языке и каким тоном говорит ваш магазин.

## Ошибки и состояние поля

Состояние поля — набор сигналов. Для проверки нужны такие:

| Сигнал | Что значит |
|---|---|
| `errors()` | массив ошибок поля: `{ kind, message }` |
| `valid()`, `invalid()` | ошибок нет / есть |
| `touched()` | поле «тронуто»: покупатель побывал в нём и ушёл |
| `dirty()` | поле изменено: покупатель что-то напечатал |

У всей формы — те же сигналы: `loginForm().valid()` — верна ли форма целиком, вместе со всеми полями.

Когда показывать ошибку? Если сразу, страница входа откроется вся в красном: «Введите e-mail», «Введите пароль» — хотя покупатель ещё ничего не сделал. Обычно ошибки показывают, когда покупатель **закончил с полем** — ушёл из него. Это `touched()`. Удобно завести метод:

```ts login/login.ts
// Ошибки поля показываем, когда покупатель закончил с полем (ушёл из него), а не с первой буквы
protected showErrors(field: FieldTree<string>) {
  return field().touched() && field().invalid();
}
```

`FieldTree<string>` — тип поля со строковым значением. Метод получает поле, вызывает его и читает сигналы состояния — а значит, шаблон, который его вызвал, обновится, когда они изменятся.

В шаблоне — список ошибок под полем:

```html login/login.html {7-10,12-18}
<label class="field">
  E-mail
  <input
    type="email"
    autocomplete="email"
    [formField]="loginForm.email"
    [attr.aria-invalid]="showErrors(loginForm.email) || null"
    [attr.aria-describedby]="
      showErrors(loginForm.email) ? 'email-errors' : null
    "
  />
  @if (showErrors(loginForm.email)) {
    <ul id="email-errors" class="field-errors">
      @for (error of loginForm.email().errors(); track error.kind) {
        <li>{{ error.message }}</li>
      }
    </ul>
  }
</label>
```

Список ошибок видно глазами. Но покупатель с экранным диктором услышит только «E-mail, поле ввода» — красный текст под полем для него просто где-то на странице. Об ошибке ему сообщают два атрибута поля:

- `aria-invalid="true"` — «в поле ошибка»;
- `aria-describedby="email-errors"` — «описание поля — элемент с этим `id`»: диктор прочитает текст ошибки вместе с полем.

Это привязки атрибутов (`[attr.…]`) из главы 2. Когда ошибки не видны, значение `null`, и Angular убирает атрибут: `showErrors(…) || null` даёт `true` или `null`.

Красную рамку рисует глобальный стиль `.field [aria-invalid='true']`. Так у рамки и у диктора один источник правды: если рамка есть, диктор тоже знает об ошибке.

Отладочный JSON модели больше не нужен. Вместо него выведем состояние формы целиком:

```html login/login.html
<p class="debug">
  Форма {{ loginForm().valid() ? 'заполнена верно' : 'с ошибками' }}
</p>
```

::: task
1. Передайте в `form` вторым аргументом функцию схемы: e-mail обязателен и без опечаток, пароль обязателен и не короче 4 символов. Тексты ошибок — в `message`.
2. Добавьте метод `showErrors(field: FieldTree<string>)`: ошибки поля видны, когда поле тронуто и в нём есть ошибки.
3. Под каждым полем выведите список ошибок `<ul class="field-errors">` с `id` (`email-errors`, `password-errors`) — только когда `showErrors` для этого поля вернул `true`. Пока ошибки видны, у поля — `aria-invalid="true"` и `aria-describedby` с `id` списка.
4. Замените `<pre>` с моделью строкой состояния формы: «Форма заполнена верно» или «Форма с ошибками». `JsonPipe` из `imports` можно убрать.
:::

## Что получилось

Страница открывается спокойно: ошибок не видно, хотя оба поля пусты, а строка внизу — «Форма с ошибками». Щёлкните в поле e-mail и уйдите из него — «Введите e-mail». Напечатайте `user@` — сообщение сменилось на «Похоже, в адресе опечатка». Допишите `example.com` — ошибка исчезла, хотя вы ещё в поле: «тронутым» поле стало раньше, и теперь ошибки обновляются на каждую букву.

Нажмите «Заполнить тестовыми данными» — «Форма заполнена верно».

## Эксперименты

**Без `message`.** Уберите `message` у `minLength` и введите пароль `abc`. Под полем — пустая строка списка: ошибка есть (`kind: 'minLength'`), а текста нет. Выведите `{{ error.kind }}` вместо `{{ error.message }}` — появится `minLength`. Верните `message`.

**Что считается e-mail.** Введите `a@b` — ошибки нет. Правило `email` проверяет только форму адреса: имя, `@`, домен. Точка в домене не обязательна: `a@b` формально допустимый адрес. Есть ли у адреса почтовый ящик, знает только сервер.

**Атрибуты.** Посмотрите в инструментах разработчика на поле пароля: у него появились атрибуты `required` и `minlength="4"`. Уйдите из пустого поля — добавились `aria-invalid="true"` и `aria-describedby="password-errors"`. На вкладке Accessibility (в Chrome — панель Elements → Accessibility) у поля теперь есть описание — текст ошибки. Правила формы `[formField]` переносит и на элемент. Это помогает экранным дикторам и браузеру — но проверяет по-прежнему форма, а не браузер.

**`dirty` против `touched`.** Временно покажите ошибки по `dirty()` вместо `touched()`. Теперь «Похоже, в адресе опечатка» появляется с первой буквы — пока покупатель ещё печатает. А нажатие «Заполнить тестовыми данными» поле `dirty` не делает: `dirty` — это изменение **покупателем**, а не кодом. Верните `touched()`.

::: tip
Сравнение с React: в React форму обычно держат в `useState` и проверяют в обработчиках или берут библиотеку (React Hook Form, Formik). В Signal Forms правила проверки и состояние полей — часть самой формы, а пересчитываются они так же, как `computed`: сами, когда меняется значение.
:::
