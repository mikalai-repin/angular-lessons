Форма проверяет поля, но ничего не отправляет. Пора добавить кнопку «Войти» и отправить e-mail и пароль на сервер: `POST /api/login`. Учебный бэкенд отвечает так:

- верные e-mail и пароль (`user@example.com` / `user`) — `200` и `{ token, user }`;
- неверные — `401` и сообщение «Неверный e-mail или пароль».

У отправки формы много мелочей, и все они нужны покупателю:

- отправить можно и кнопкой, и клавишей Enter в любом поле;
- форму с ошибками не отправляем — показываем ошибки во всех полях, даже в тех, которые покупатель не трогал;
- пока ждём ответа, кнопка заблокирована: второй щелчок не должен отправить второй запрос;
- ошибку сервера показываем у формы и убираем, когда покупатель начал исправлять.

## Элемент form и FormRoot

Enter в поле отправляет форму — это поведение браузера, но только для полей внутри элемента `<form>`. Значит, поля и кнопку оборачиваем в `<form>`. У него есть своё поведение по умолчанию: при отправке браузер переходит по адресу формы и перезагружает страницу. Для приложения на Angular это не нужно.

Связывает `<form>` с формой Signal Forms директива `FormRoot` из `@angular/forms/signals`:

```html login/login.html
<form class="login-form" [formRoot]="loginForm">
  …поля…
  <button class="button">Войти</button>
</form>
```

Директива делает три вещи:

- ставит элементу атрибут `novalidate` — отключает проверку браузера: проверяет форма Angular, и сообщения у неё свои;
- при отправке (кнопка или Enter) отменяет поведение браузера по умолчанию — страница не перезагружается;
- вызывает отправку формы, если у формы задано, что делать при отправке.

Кнопка внутри `<form>` без `type` — кнопка отправки (`type="submit"` по умолчанию). Поэтому у учебной кнопки «Заполнить тестовыми данными» теперь `type="button"`: иначе она бы тоже отправляла форму.

## Что делать при отправке

Действие при отправке задают в **настройках формы** — третьем аргументе `form` (второй — схема):

```ts login/login.ts {7-10,13-31}
protected readonly loginForm = form(
  this.model,
  (login) => {
    // …правила, как в прошлом шаге
  },
  {
    // Что делать, когда форму отправили и в ней нет ошибок
    submission: { action: () => this.logIn() },
  },
);

// Отправка формы. Вернуть можно ошибки — Angular покажет их у формы, как ошибки проверки
private async logIn() {
  try {
    const response = await firstValueFrom(
      this.http.post<LoginResponse>('/api/login', this.model()),
    );
    this.userName.set(response.user.name);
    return undefined;
  } catch (error) {
    if (error instanceof HttpErrorResponse && error.status === 401) {
      return { kind: 'server', message: 'Неверный e-mail или пароль' };
    }
    return {
      kind: 'server',
      message: 'Не удалось войти. Попробуйте ещё раз',
    };
  }
}
```

`action` — асинхронная функция: она возвращает промис. Запрос мы отправляем через `HttpClient` и `firstValueFrom`, как в резолвере главы 11. Что делает отправка формы по шагам:

1. Помечает все поля «тронутыми». Поэтому ошибки появятся и в полях, которых покупатель не касался.
2. Если в форме есть ошибки — останавливается. `action` не вызывается, запроса нет.
3. Иначе включает `submitting()` и вызывает `action`.
4. Когда промис выполнился, выключает `submitting()`. Если `action` вернул ошибки, они становятся **ошибками отправки** — форма показывает их, как ошибки проверки.

Ошибка — объект, как в правилах: `{ kind, message }`. Без указания поля она попадает в ошибки **всей формы**: `loginForm().errors()`. (Можно привязать ошибку к полю — свойством `fieldTree: this.loginForm.password`, — тогда она будет в ошибках этого поля.) Ошибки отправки живут до первого изменения формы: покупатель исправил любое поле — ошибка сервера исчезла, она больше не про эти данные.

На время запроса форма в состоянии `submitting()`. Это сигнал — им удобно блокировать кнопку и менять её текст:

```html login/login.html
<!-- Ошибки всей формы: их вернула отправка -->
@for (error of loginForm().errors(); track error.kind) {
  <p class="error-message">{{ error.message }}</p>
}
<button class="button" [disabled]="loginForm().submitting()">
  {{ loginForm().submitting() ? 'Входим…' : 'Войти' }}
</button>
```

Что делать с токеном из ответа — запомнить вход, отправлять токен с запросами, выходить — это тема главы 14. Пока покажем приветствие вместо формы: `@if (userName())` — приветствие, `@else` — форма.

::: task
1. Оберните поля в `<form class="login-form" [formRoot]="loginForm">` (вместо `<div>`) и добавьте `FormRoot` в `imports`.
2. Добавьте в `form` третий аргумент — `{ submission: { action: () => this.logIn() } }` — и метод `logIn`: `POST /api/login` с моделью формы. При `401` верните ошибку «Неверный e-mail или пароль», при любой другой ошибке — «Не удалось войти. Попробуйте ещё раз».
3. При удачном входе запишите имя пользователя (`response.user.name`) в сигнал `userName` и покажите вместо формы «Здравствуйте, {{ userName() }}! Вы вошли.».
4. Над кнопкой выведите ошибки всей формы. Кнопка «Войти» заблокирована и пишет «Входим…», пока форма отправляется. Учебной кнопке — `type="button"`. Отладочную строку состояния формы уберите.
:::

## Что получилось

Нажмите «Войти» с пустыми полями — ошибки появились под обоими полями, а во вкладке «Сеть» пусто: форма с ошибками не отправляется. Введите `user@example.com` и пароль `wrong` — «Неверный e-mail или пароль» над кнопкой, в «Сети» — `POST /api/login` с ответом `401`. Начните исправлять пароль — сообщение исчезло.

Нажмите «Заполнить тестовыми данными» и Enter в поле пароля — «Здравствуйте, Пользователь! Вы вошли.».

## Эксперименты

**Медленный сервер.** Во вкладке «Сеть» поставьте задержку 3000 мс и войдите. Три секунды кнопка серая и пишет «Входим…». Щёлкайте по ней сколько угодно — запрос один. Кнопку блокирует `[disabled]`, но и без него второй отправки бы не было: пока форма в состоянии `submitting()`, повторная отправка сразу возвращает `false` и `action` не вызывает.

**Без FormRoot.** Уберите `[formRoot]="loginForm"` у `<form>`, заполните поля и нажмите «Войти». Превью запустилось заново: поля пустые, в консоли — строки запуска приложения, в «Сети» нет `POST /api/login`. Браузер отправил форму сам — как обычную HTML-форму: перешёл по адресу страницы, и приложение загрузилось с нуля. Именно это поведение по умолчанию и отменяет `FormRoot`. Верните директиву.

**Ошибка у поля.** Добавьте к ошибке `401` свойство `fieldTree: this.loginForm.password`. Ошибка переехала под поле пароля: она теперь в `loginForm.password().errors()`, а под формой ничего нет. Так делают, когда сервер точно знает, какое поле неверно (например, «такой e-mail уже зарегистрирован»). Для входа это плохая идея: подсказка «неверен именно пароль» помогает подбирать пароли к чужим адресам. Верните как было.

::: tip
Отправить форму можно и без `FormRoot` — функцией `submit(loginForm)` из `@angular/forms/signals`, например в обработчике щелчка. `FormRoot` вызывает именно её. А действие можно передать прямо в вызов: `submit(loginForm, () => this.logIn())` — оно заменит действие из настроек формы.
:::

::: deep Под капотом: submit
Функция `submit` — около 30 строк в `@angular/forms/fesm2022/_validation_errors-chunk.mjs`. Сначала она проверяет, не отправляется ли форма уже: если `submitting()` включён, сразу возвращает `false`. Затем вызывает `markAsTouched()` у корня формы (он помечает и всех потомков), решает, можно ли отправлять, и вызывает `action` внутри `untracked` — чтобы чтения сигналов в вашей функции не стали чьими-то зависимостями. Ошибки, которые вернул `action`, раскладываются по полям: у ошибки без `fieldTree` поле — то, которое отправляли. `submitting()` выключается в блоке `finally`: даже если `action` бросил исключение, форма не застрянет в состоянии отправки.

Можно ли отправлять, решает настройка `ignoreValidators`. По умолчанию (`'pending'`) мешают только ошибки: если какая-то проверка ещё ждёт ответа сервера, отправка всё равно пойдёт. `'none'` — ждать и такие проверки, `'all'` — отправлять всегда.
:::
