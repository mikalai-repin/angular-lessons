Форма входа — разминка. Главная форма магазина — оформление заказа. Курьеру и менеджеру нужно знать, кто покупатель и как с ним связаться. Начнём с контактов: имя, телефон, e-mail.

Чтобы открыть оформление, корзина не должна быть пустой: положите в неё любую игру и перейдите в корзину → «Оформить заказ».

## Что изменилось в коде

Страница оформления уже стала формой — всё это вы умеете по прошлым шагам:

- модель `CheckoutData` с **вложенным объектом**: `contacts: { name, phone, email }` и `comment`. Поля формы повторяют вложенность: `checkoutForm.contacts.name`, `checkoutForm.contacts.phone`. Группа `checkoutForm.contacts` — тоже поле, со своим состоянием;
- имя обязательно (`required`);
- комментарий — тоже поле формы. Черновик сохраняется, как в главе 12, только поток теперь строится из сигнала значения поля: `toObservable(this.checkoutForm.comment().value)`;
- поля сгруппированы в `<fieldset>` с подписью «Контакты».

И новый компонент — `FieldErrors` (`shared/field-errors/`). Писать под каждым полем `@if (…touched() && …invalid())` и `@for` по ошибкам, как в форме входа, долго. Компонент делает это сам:

```html shared/field-errors/field-errors.html
@let state = field()();
@if (state.touched() && state.invalid()) {
  <ul class="field-errors">
    @for (error of state.errors(); track error.kind) {
      <li>{{ error.message }}</li>
    }
  </ul>
}
```

Вход `field` — поле формы любого типа: `input.required<FieldTree<unknown>>()`. Двойные скобки — не опечатка: `field()` читает вход и возвращает поле, а второй вызов — состояние поля. В шаблоне формы под каждым полем — `<app-field-errors [field]="checkoutForm.contacts.name" />`.

А как же `aria-invalid` и `aria-describedby` из формы входа? Писать их у каждого поля ещё скучнее. Это делает директива `FieldAria` (`shared/field-aria.ts`):

```ts shared/field-aria.ts
@Directive({
  selector: '[formField]',
  host: {
    '[attr.aria-invalid]': 'showErrors() || null',
    '[attr.aria-describedby]': 'showErrors() ? errorsId() : null',
  },
})
export class FieldAria {
  // Директива FormField на том же элементе: её предоставляет токен FORM_FIELD
  private readonly formField = inject(FORM_FIELD);
  protected readonly showErrors = computed(() => {
    const state = this.formField.state();
    return state.touched() && state.invalid();
  });
  protected readonly errorsId = computed(() =>
    fieldErrorsId(this.formField.state().name()),
  );
}
```

Селектор у неё тот же, что у `FormField`, — `[formField]`: на одном элементе могут работать несколько директив (глава 7). Если `FieldAria` есть в `imports` компонента, она встаёт на каждое поле формы рядом с `FormField`. Само поле она берёт через токен `FORM_FIELD` — его предоставляет директива `FormField` своего элемента (как `TABS` предоставляли вкладки в главе 8). `id` списка ошибок строится из имени поля: имя уникально (`ng.form0.contacts.phone`), и `FieldErrors` ставит списку тот же `id`, что `FieldAria` — в `aria-describedby`.

## Проверка своей функцией

Встроенных правил для контактов не хватает. Телефон покупатель напишет как угодно: «+7 (900) 123-45-67», «8 900 1234567», «89001234567». Правило `pattern` с одним регулярным выражением на все варианты получится нечитаемым. Проще посчитать цифры: их должно быть 11, первая — 7 или 8.

Своё правило — функция `validate`:

```ts checkout/checkout.ts {1-5,9-17}
// Телефон пишут по-разному: «+7 (900) 123-45-67», «8 900 1234567». Считаем только цифры:
// их 11, первая — 7 или 8
function isPhone(text: string) {
  return /^[78]\d{10}$/.test(text.replace(/\D/g, ''));
}

form(this.model, (checkout) => {
  const contacts = checkout.contacts;
  // Своя проверка: функция получает контекст поля и возвращает ошибку или undefined
  validate(contacts.phone, ({ value }) =>
    value() && !isPhone(value())
      ? {
          kind: 'phone',
          message: 'Номер — 11 цифр, например +7 900 123-45-67',
        }
      : undefined,
  );
});
```

Функция правила получает **контекст поля** и возвращает ошибку — объект `{ kind, message }`, массив ошибок или `undefined`, если всё в порядке. `kind` придумываем сами: по нему ошибки различают в коде.

Самое полезное в контексте:

- `value` — сигнал значения поля;
- `valueOf(путь)` — значение другого поля по пути схемы;
- `state` — состояние поля (`touched`, `dirty`…);
- `fieldTree` — само поле.

Правило выполняется не один раз, а как `computed`: когда изменился сигнал, который оно прочитало, Angular вычислит его заново. Поэтому `value()` — вызов сигнала, а не готовое значение.

Обратите внимание на `value() &&`: пустой телефон — не ошибка формата. Обязателен ли он — другой вопрос, о нём ниже.

## Перекрёстная проверка

Ни телефон, ни e-mail по отдельности не обязательны: кто-то не любит звонков, у кого-то нет почты. Но хотя бы что-то одно нужно — иначе с покупателем не связаться. Это правило про **два поля сразу** — **перекрёстная проверка**.

Правило вешают на то поле, под которым должна появиться ошибка, — на e-mail. А соседнее поле читают через `valueOf`:

```ts checkout/checkout.ts {3}
email(contacts.email, { message: 'Похоже, в адресе опечатка' });
// Перекрёстная проверка: правило поля e-mail читает и соседнее поле — телефон
validate(contacts.email, ({ value, valueOf }) =>
  !value().trim() && !valueOf(contacts.phone).trim()
    ? {
        kind: 'contact',
        message: 'Укажите телефон или e-mail, чтобы мы могли связаться с вами',
      }
    : undefined,
);
```

`valueOf(contacts.phone)` читает сигнал значения телефона. Значит, правило поля e-mail зависит и от телефона: напечатали телефон — Angular пересчитал правило e-mail, и ошибка исчезла. Ничего связывать вручную не нужно.

::: task
1. Добавьте функцию `isPhone(text)`: в тексте 11 цифр, первая — 7 или 8 (остальные символы не считаются).
2. Добавьте правило телефона через `validate`: непустой телефон, который не проходит `isPhone`, — ошибка «Номер — 11 цифр, например +7 900 123-45-67».
3. E-mail — без опечаток: правило `email` с сообщением «Похоже, в адресе опечатка».
4. Перекрёстная проверка: если пусты и телефон, и e-mail, у поля e-mail ошибка «Укажите телефон или e-mail, чтобы мы могли связаться с вами».
:::

## Что получилось

Пройдите по всем полям контактов клавишей Tab, ничего не вводя, и выйдите из e-mail. Под именем — «Как к вам обращаться?», под e-mail — «Укажите телефон или e-mail…». Начните вводить телефон `+7 (900) 123-45` — ошибка под e-mail исчезла сразу, а под телефоном, когда вы уйдёте из него, — «Номер — 11 цифр…». Допишите `-67` — ошибки нет. `8 900 1234567` тоже подходит.

## Эксперименты

**Правило на группе.** Повесьте перекрёстную проверку не на e-mail, а на всю группу: `validate(contacts, ({ value }) => !value().email.trim() && !value().phone.trim() ? … : undefined)`. Правило читает значение группы — объект с тремя полями. Пройдите по полям: сообщения «Укажите телефон или e-mail» нигде нет. Ошибка есть — в `checkoutForm.contacts().errors()`, и форма из-за неё неверна, — но `<app-field-errors>` стоят только у полей, а у группы нет. Правило группы — правильное место, когда ошибка про группу целиком; тогда и выводить её нужно у группы. Верните правило на e-mail.

**Неверный путь.** В `valueOf` можно передать только путь схемы. Напишите `valueOf(this.checkoutForm.contacts.phone)` — поле вместо пути. TypeScript подчеркнёт вызов: `TS2345: Argument of type 'FieldTree<string, string, "writable">' is not assignable to parameter of type 'SchemaPath<…>'`. Путь схемы и поле — разные вещи: путь описывает место в форме ещё до её создания, поле — живое состояние. Верните `contacts.phone`.

::: tip
Когда одно правило проверяет несколько полей и должно поставить ошибки **разным** полям, есть `validateTree(path, fn)`: в каждой ошибке, которую возвращает функция, можно указать `fieldTree` — поле, к которому она относится.
:::
