Промокоды магазина до сих пор лежат списком в коде — в `core/promo-codes.ts`. Это плохо по двум причинам. Код приложения скачивает браузер, значит, все промокоды может прочитать любой покупатель. И чтобы завести новый промокод, нужно выпускать новую версию приложения.

Правильное место для промокодов — сервер. Учебный бэкенд знает те же два:

- `GET /api/promo/KNIGHT10` — `200` и `{ code: 'KNIGHT10', percent: 10 }`;
- `GET /api/promo/CHESS500` — `200` и `{ code: 'CHESS500', amount: 500, minTotal: 3000 }`;
- любой другой код — `404`.

Проверим промокод, пока покупатель печатает: «Нет такого промокода» появится до того, как он нажмёт «Применить». Это **асинхронная проверка**: ответ правила приходит не сразу, а когда ответит сервер.

## Что изменилось в коде

- `core/promo-codes.ts` удалён. Тип `Promo` переехал в `core/models.ts` — рядом с остальными типами данных сервера;
- `CartStore.applyPromo` принимает не текст, а промокод, который прислал сервер: `applyPromo(promo: Promo): boolean`. Порог `minTotal` хранилище по-прежнему проверяет само;
- поле промокода на странице корзины — форма из одного поля `code` с правилом `required`. В шаблоне — `<form [formRoot]="promoForm">`, поле `[formField]="promoForm.code"`, кнопка «Применить» заблокирована, пока форма не верна. Под полем — строка «Проверяем промокод…», пока `promoForm.code().pending()`, и ошибки поля. Ошибки здесь видны сразу, без `touched()`: покупатель ждёт ответа на свой ввод. Поэтому `aria-invalid` и `aria-describedby` у поля промокода — вручную, как в форме входа, по `invalid()`: `FieldAria` показывает ошибки по `touched()`;
- у правил и у `applyPromo` — заготовки `// TODO`.

## validateHttp

Правило с запросом к серверу — `validateHttp`:

```ts cart/cart-page/cart-page.ts {1-5,9-30}
// Промокод проверяет сервер: GET /api/promo/KNIGHT10 → промокод или 404
const promoUrl = (code: string) =>
  `/api/promo/${encodeURIComponent(code.trim())}`;
// Метка CACHE: «Применить» возьмёт из кэша ответ, полученный при проверке
const cached = () => new HttpContext().set(CACHE, true);

(promo) => {
  required(promo.code);
  validateHttp(promo.code, {
    request: ({ value }) => ({
      url: promoUrl(value()),
      context: cached(),
    }),
    // Не спрашивать сервер на каждую букву: запрос — после паузы в наборе
    debounce: 300,
    // Промокод есть. Хватает ли суммы товаров — узнаём только теперь
    onSuccess: (found: Promo) =>
      'minTotal' in found && this.cart.subtotal() < found.minTotal
        ? {
            kind: 'min-total',
            message: 'Сумма товаров меньше, чем нужно для этого промокода',
          }
        : undefined,
    onError: (error) =>
      error instanceof HttpErrorResponse && error.status === 404
        ? { kind: 'unknown', message: 'Нет такого промокода' }
        : { kind: 'server', message: 'Не удалось проверить промокод' },
  });
}
```

Внутри `validateHttp` — знакомый `httpResource` из главы 11. Отсюда и поведение:

- **`request`** — функция запроса, как у `httpResource`: адрес или объект запроса. Она читает значение поля, поэтому новое значение — новый запрос, а прежний, если не успел, **отменяется**;
- **`onSuccess(ответ, контекст)`** превращает ответ сервера в ошибки — или в `undefined`, если всё хорошо. Здесь ответ `200` ещё не значит «подходит»: у `CHESS500` есть порог суммы;
- **`onError(ошибка, контекст)`** — то же для ошибок запроса: `404` значит «нет такого промокода», а всё остальное — сбой, о котором честно скажем;
- **`debounce`** — пауза в миллисекундах: запрос уходит, когда покупатель перестал печатать, как `debounced` в каталоге (глава 11) и `debounceTime` в быстром поиске (глава 12).

Метка `CACHE` из главы 12 здесь не случайна. Ответ на проверку попадёт в кэш, и когда покупатель нажмёт «Применить», мы попросим тот же промокод снова — и получим его из кэша, без второго запроса.

**Асинхронная проверка выполняется, только когда синхронные правила поля уже прошли.** Пока поле пустое, `required` не проходит — и запроса нет. Поэтому `request` не проверяет пустую строку.

## Ожидание проверки

Пока ответа нет, поле в состоянии **ожидания проверки**: `pending()` — `true`. Ошибок у него нет, но и верным его назвать нельзя. Отсюда тонкость, которую стоит запомнить:

- `valid()` — `true`, только когда ошибок нет **и** ничего не ждём;
- `invalid()` — `true`, только когда ошибки **есть**.

Пока идёт проверка, оба — `false`. Поэтому кнопка «Применить» заблокирована по `!promoForm().valid()`, а не по `promoForm().invalid()`. Это важно: по умолчанию отправка формы ждущие проверки **не учитывает** — мешают ей только ошибки (настройка `ignoreValidators`, шаг «Отправка формы»). А заблокированная кнопка закрывает и Enter: браузер не отправляет форму по Enter, если её кнопка отправки заблокирована.

## Применить промокод

```ts cart/cart-page/cart-page.ts
private async applyPromo() {
  const promo = await firstValueFrom(
    this.http.get<Promo>(promoUrl(this.promoModel().code), {
      context: cached(),
    }),
  );
  this.cart.applyPromo(promo);
  // Промокод применён — поле снова пустое и нетронутое
  this.promoForm().reset({ code: '' });
}
```

`reset(значение)` записывает значение в модель и снимает с формы «тронуто» и «изменено». Без аргумента `reset()` снимает только состояния, а значение не трогает.

## Что получилось

Положите в корзину «Остров сокровищ» и «Драконью почту» (3 280 ₽). Напечатайте `nope` — сразу «Проверяем промокод…», через 300 мс после последней буквы во вкладке «Сеть» уходит один запрос `GET /api/promo/nope` с ответом `404`, и под полем — «Нет такого промокода». Сотрите и напечатайте `chess500` — ошибок нет, «Применить» активна. Нажмите — в итогах «Промокод CHESS500 −500 ₽», а поле снова пустое.

Посмотрите в консоль: журнал интерцептора из главы 12 показывает **два** запроса `GET /api/promo/chess500`, а «Сеть» — один. Второй — запрос из `applyPromo`: его ответ отдал кэш-интерцептор, до сервера запрос не дошёл, поэтому в журнале у него 0 мс.

## Эксперименты

**Порог суммы.** Уберите промокод (×), напечатайте `chess500` и, не применяя, удалите из корзины «Драконью почту». Под полем сразу появилось «Сумма товаров меньше…», а кнопка заблокировалась. Нового запроса нет: `onSuccess` прочитал сигнал `subtotal`, поэтому пересчитался сам, когда сумма изменилась, — с тем же ответом сервера.

**Без паузы.** Уберите `debounce: 300` и напечатайте `KNIGHT10`. Во вкладке «Сеть» — восемь запросов: `K`, `KN`, `KNI`… Семь из них отменены — новое значение поля отменяет прежний запрос, как в каталоге из главы 11. Сервер всё равно получил все восемь. Верните паузу.

**Медленный сервер.** Поставьте задержку 3000 мс и напечатайте `KNIGHT10`. Три секунды под полем «Проверяем промокод…», кнопка серая. Нажмите Enter в поле — ничего не происходит: кнопка отправки заблокирована.

::: tip
Если проверка не про HTTP — например, нужно спросить у сервиса, у которого нет адреса, — есть `validateAsync`: вместо `request` у него `params` (что проверять) и `factory` (создать ресурс, например через `resource` из главы 11). `validateHttp` — его частный случай для `httpResource`.
:::
