Посмотрите на `checkout.ts`. Половина файла — правила формы: контакты, доставка, открытки. Компонент должен заниматься страницей — данными, действиями, шаблоном, — а правила оформления заказа к странице не привязаны: их можно проверять отдельно, а то и переиспользовать. Например, правило «e-mail без опечаток» уже написано дважды: в форме входа и в форме заказа, с одним и тем же сообщением.

Функция схемы, которую мы передаём в `form`, — это код. Его можно вынести в отдельный файл и разбить на части, как любой код. Для этого есть **схема** — функция `schema`.

## schema и apply

```ts shared/form-rules.ts
import { email, schema } from '@angular/forms/signals';

// Правила, общие для форм магазина. Схема — набор правил для поля определённого типа:
// её применяют к любому полю с таким значением, в любой форме
export const emailRules = schema<string>((field) => {
  email(field, { message: 'Похоже, в адресе опечатка' });
});
```

`schema<T>(функция)` создаёт объект схемы для значений типа `T`. Внутри — такая же функция, как вторым аргументом `form`, только она ещё ни к чему не применена. Применяет схему к полю `apply`:

```ts login/login.ts
required(login.email, { message: 'Введите e-mail' });
apply(login.email, emailRules);
```

`apply(путь, схема)` — «примени все правила схемы к этому полю». Тип проверяет TypeScript: `emailRules` — схема для строки, и применить её к полю-числу не получится.

Готовую схему принимают и `form`, и `applyEach`: `form(this.model, checkoutSchema)`, `applyEach(checkout.postcards, postcardSchema)`.

## Схема оформления заказа

Разложим правила оформления по частям в новом файле `checkout/checkout-schema.ts`. Туда же переедут типы модели и константы — всё, что описывает данные заказа:

```ts checkout/checkout-schema.ts
// Контакты: как обращаться и как связаться
export const contactsSchema = schema<Contacts>((contacts) => {
  required(contacts.name, { message: 'Как к вам обращаться?' });
  validate(contacts.phone, …); // телефон — как в шаге «Свои проверки»
  apply(contacts.email, emailRules);
  validate(contacts.email, …); // телефон или e-mail
});

// Открытка: адресат обязателен, текст — не длиннее POSTCARD_TEXT_MAX
export const postcardSchema = schema<Postcard>((postcard) => {
  required(postcard.to, { message: 'Кому эта открытка?' });
  maxLength(postcard.text, POSTCARD_TEXT_MAX, { … });
});

// Вся форма оформления: схемы частей и правила, которые связывают части между собой
export const checkoutSchema = schema<CheckoutData>((checkout) => {
  apply(checkout.contacts, contactsSchema);
  applyEach(checkout.postcards, postcardSchema);
  // hidden, applyWhen и disabled для доставки — как в шаге «Условные поля»
});
```

Чтобы написать `schema<Contacts>`, у контактов нужен свой тип — выносим его из `CheckoutData` в интерфейс `Contacts`.

Правила доставки остались в общей схеме не случайно. Они связывают части формы: способ доставки решает, обязателен ли **телефон** из контактов. Схема контактов о доставке ничего не знает — её путь `contacts` начинается с группы контактов. Внутри неё можно читать только свои поля. Правила, которые касаются нескольких частей, живут в схеме, которая видит их все.

В компоненте от правил остаётся одна строка:

```ts checkout/checkout.ts
// Правила формы — в схеме: компоненту остаются данные и действия
protected readonly checkoutForm = form(this.model, checkoutSchema);
```

## Что получилось

Внешне — ничего: форма входа и форма заказа проверяют то же, что и раньше. Но `checkout.ts` стал короче вдвое, а правила оформления заказа можно читать — и в главе 16 проверять тестами — без компонента и шаблона.

## Эксперименты

**Чужой путь.** Внутри схемы можно использовать только её собственные пути. Добавьте в `checkoutSchema` вложенную схему, которая обращается к пути общей схемы:

```ts
apply(checkout.contacts, schema<Contacts>(() => required(checkout.comment)));
```

Откройте оформление — в консоли:

```text
ERROR RuntimeError: NG01908: A FieldPath can only be used directly within the Schema that owns it, **not** outside of it or within a sub-schema.
```

Путь `checkout.comment` принадлежит общей схеме, а правило оказалось внутри вложенной. Angular проверяет это при создании формы. Уберите строку.

**Сколько раз выполняется схема.** Добавьте в начало функции `contactsSchema` строку `console.log('Схема контактов')`. Откройте оформление — строка одна. Печатайте в полях — новых строк нет: функция схемы только описывает правила, а проверяют правила, а не она. Уйдите в корзину и вернитесь — строка снова: новый компонент создал новую форму, и схема применилась к ней заново. Уберите строку.

::: deep Как в настоящем проекте: схемы из библиотек
Правила данных часто уже описаны в библиотеке схем — например, в Zod — для проверки ответов сервера или для общего кода с сервером на Node. Писать их второй раз для формы не нужно: `validateStandardSchema(путь, схемаБиблиотеки)` превращает ошибки такой схемы в ошибки формы. Подходит любая библиотека, которая реализует общий стандарт **Standard Schema** (Zod 4 — одна из них). В превью курса библиотек схем нет, поэтому здесь только упоминание.
:::
