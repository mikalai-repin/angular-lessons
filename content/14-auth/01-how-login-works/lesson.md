В главе 13 форма входа научилась отправлять e-mail и пароль на сервер и показывать «Здравствуйте, Пользователь!». Но на этом всё: магазин тут же забывает, кто вошёл. Шапка не знает имени, отзыв по-прежнему подписан «Гость», а «Мои заказы» — заглушка. В этой главе вход заработает по-настоящему.

К концу главы у магазина появятся:

- «Войти» в шапке, а после входа — имя покупателя и «Выйти»;
- вход, который переживает перезагрузку страницы;
- отзывы и заказы от имени покупателя: каждый запрос несёт пропуск;
- выход, когда сервер перестал принимать пропуск;
- «Мои заказы» — только после входа, и после входа покупатель возвращается туда, куда шёл;
- админка, которую видит только администратор;
- незаметное обновление пропуска, когда его срок истёк.

## Как устроен вход

Сервер и браузер общаются запросами, и каждый запрос для сервера — сам по себе: он не помнит, что минуту назад этот же браузер присылал верный пароль. Поэтому после входа сервер выдаёт **токен доступа** (access token) — строку-пропуск. Дальше браузер прикладывает её к каждому запросу, а сервер по ней узнаёт покупателя:

```text
 магазин                      сервер
   │ POST /api/login             │
   │ { email, password } ───────►│ пароль
   │◄─────────── { token, user } │ верный
   │                             │
   │ GET /api/orders             │
   │ Authorization: Bearer … ───►│ токен
   │◄───────────────── заказы    │ верный
   │                             │
   │ …срок токена истёк…         │
   │ GET /api/orders ───────────►│
   │◄───────────────── 401       │
```

Здесь две разные задачи:

- **вход** (аутентификация) — узнать, кто это. Её решают пароль и токен;
- **права** (авторизация) — решить, что этому человеку можно. Покупателю — свои заказы, администратору — ещё и админка.

Обе задачи по-настоящему решает **сервер**. Код в браузере пользователь может прочитать и изменить, поэтому магазин только хранит токен, прикладывает его к запросам и показывает интерфейс по тому, что сервер о покупателе сказал. Скрыть кнопку — удобство, а не защита. К этой мысли мы вернёмся в шаге про роли.

Токен в этой главе — всегда токен доступа. Не путайте его с токеном внедрения зависимостей из главы 8: там «токен» — ключ, по которому DI ищет зависимость.

## Что умеет учебный бэкенд

- `POST /api/login` с `{ email, password }` — `{ token, refreshToken, user }` или `401` «Неверный e-mail или пароль». Учётные записи: `user@example.com` / `user` (покупатель) и `admin@example.com` / `admin` (администратор);
- `GET /api/me` — пользователь по токену или `401`;
- `GET /api/orders` — свои заказы, только с токеном;
- токен живёт час. Урок может сделать срок короче — так мы увидим, что бывает, когда он истёк. Истёкший или поддельный токен сервер не принимает: ответ `401` на любой адрес `/api/…`, кроме входа, обновления и выхода;
- `POST /api/refresh` и `POST /api/logout` — обновить токен и выйти. Они понадобятся в шаге про обновление токена.

Сервер учебный, но токены у него настоящие — в формате JWT. Что у них внутри, посмотрим в следующем шаге.

## Что изменилось в коде

Код — решение практикума главы 13 и две «закадровые» правки:

- в `core/models.ts` появился тип `User` — так сервер описывает пользователя: `id`, `email`, `name` и `role` (`'user'` или `'admin'`);
- новый файл `core/auth-store.ts` — заготовка сервиса `AuthStore`. Его мы и напишем;
- в `layout/header/header.css` — готовые стили для ссылки входа (`.account`) и кнопки «Выйти» (`.logout`): курс не про CSS.

## Хранилище входа

Кто вошёл — общее состояние приложения: его читают шапка, форма входа, страница игры, гарды. Мы уже знаем, где держать такое состояние, — в сервисе-хранилище, как корзину в главе 9:

```ts core/auth-store.ts {4-5,8-9,12-13}
@Service()
export class AuthStore {
  // Токен — пропуск, который сервер выдал при входе. Пока покупатель не вошёл — null
  private readonly tokenState = signal<string | null>(null);
  private readonly userState = signal<User | null>(null);

  // Снаружи — только чтение
  readonly token = this.tokenState.asReadonly();
  readonly user = this.userState.asReadonly();

  // Вошёл ли покупатель: сервер подтвердил, кто он
  readonly isLoggedIn = computed(() => this.user() !== null);
  readonly isAdmin = computed(() => this.user()?.role === 'admin');
}
```

Приёмы те же, что у `CartStore`:

- состояние — закрытые сигналы, а наружу — `asReadonly()`: войти и выйти можно будет только методами хранилища, и никакой компонент не запишет в `user` что попало;
- всё, что выводится из состояния, — `computed`: `isLoggedIn` и `isAdmin` пересчитаются сами, когда изменится пользователь.

Почему сигналов два, а не один объект «сессия»? Токен и пользователь появляются не всегда одновременно. После перезагрузки страницы токен у магазина уже есть — он сохранён, — а кто это, ещё неизвестно: сервер ответит через несколько сотен миллисекунд. Поэтому «вошёл» значит «сервер подтвердил пользователя», а не «есть какая-то строка-токен». Этот промежуток мы встретим в шаге про сессию.

## Шапка

Шапка берёт хранилище через `inject` и показывает одно из двух:

```html layout/header/header.html {1,3,6}
@if (auth.user(); as user) {
  <a class="account" routerLink="/account">
    {{ user.name }}
  </a>
} @else {
  <a class="account" routerLink="/login">Войти</a>
}
```

`@if (…; as user)` из главы 4: внутри блока `user` — уже не `User | null`, а `User`, и имя можно читать без проверок.

::: task
1. В `core/auth-store.ts` заведите закрытые сигналы `tokenState` (`string | null`) и `userState` (`User | null`), оба — `null`, и открытые `token` и `user` через `asReadonly()`.
2. Добавьте вычисляемые сигналы `isLoggedIn` (пользователь есть) и `isAdmin` (роль `'admin'`).
3. В `Header` внедрите хранилище: `protected readonly auth = inject(AuthStore)`.
4. В `header.html` после ссылки на корзину: вошёл — ссылка с именем на `/account`, не вошёл — ссылка «Войти» на `/login`. Обеим дайте `class="account"` и, как остальным ссылкам шапки, `routerLinkActive="active"` и `ariaCurrentWhenActive="page"`. Стили для `.account` уже в `header.css`.
:::

## Что получилось

В шапке справа от корзины — «Войти». Щелчок ведёт на страницу входа. Войдите тестовыми данными: «Здравствуйте, Пользователь!» — а в шапке по-прежнему «Войти». Форма входа и хранилище пока не знают друг о друге. Свяжем их в следующем шаге.

## Эксперименты

**Покупатель «уже вошёл».** Начните `userState` не с `null`, а с пользователя:

```ts
private readonly userState = signal<User | null>({
  id: 1, email: 'user@example.com', name: 'Пользователь', role: 'user',
});
```

В шапке — «Пользователь», щелчок ведёт в личный кабинет. Поменяйте `role` на `'admin'` — пока ничего не изменится: `isAdmin` ещё никто не читает. Верните `null`.

**Запись снаружи.** Попробуйте в `Header` выйти напрямую: `this.auth.user.set(null)`. Редактор подчеркнёт `set`: `Property 'set' does not exist on type 'Signal<User | null>'`. Так `asReadonly` защищает состояние входа: менять его будут только методы `AuthStore` — `logIn`, `logOut` и проверка сессии.
