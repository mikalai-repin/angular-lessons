Форма входа отправляет e-mail и пароль и получает от сервера токен и пользователя. Сейчас она показывает имя и выбрасывает ответ. В этом шаге ответ попадёт в `AuthStore`: шапка покажет имя, а «Выйти» вернёт «Войти».

## Кто отправляет запрос входа

Запрос можно оставить в компоненте `Login` и записывать результат в хранилище. Но у входа есть и другие участники: в следующих шагах хранилище будет сохранять токен, проверять его после перезагрузки, обновлять. Пусть весь разговор с сервером о входе ведёт `AuthStore`, а форма отвечает только за поля, ошибки и переход после входа:

```ts core/auth-store.ts {1,4-10,13-16}
private readonly http = inject(HttpClient);

// Вход: e-mail и пароль — на сервер, токен и пользователя — в хранилище
async logIn(credentials: Credentials) {
  const response = await firstValueFrom(
    this.http.post<LoginResponse>('/api/login', credentials),
  );
  this.tokenState.set(response.token);
  this.userState.set(response.user);
}

// Выход: магазин забывает токен и пользователя
logOut() {
  this.tokenState.set(null);
  this.userState.set(null);
}
```

`firstValueFrom` превращает Observable запроса в промис — так же, как в главе 13 в форме входа. Ошибку `logIn` не ловит: при неверном пароле `firstValueFrom` отклонит промис с `HttpErrorResponse` (статус `401`), строки с `set` не выполнятся, а ошибка дойдёт до того, кто вызвал `logIn`. Хранилищу нечего делать с неверным паролем, а форме есть: показать «Неверный e-mail или пароль».

Типы — рядом с хранилищем: `Credentials` (`email` и `password`) открыт, им пользуется и форма; `LoginResponse` закрыт — это подробность разговора с сервером.

## Форма входа

Форма больше не делает запрос сама. Её действие отправки вызывает `logIn` и после входа уводит на главную:

```ts login/login.ts {3,5}
private async logIn() {
  try {
    await this.auth.logIn(this.model());
    // Вошли — на главную
    this.router.navigateByUrl('/');
    return undefined;
  } catch (error) {
    // …401 → «Неверный e-mail или пароль», как в главе 13
  }
}
```

Модель формы теперь — `signal<Credentials>`: интерфейс `LoginData` больше не нужен. Приветствие «Здравствуйте, …» тоже: имя покажет шапка.

## «Выйти»

Кнопка выхода — во втором ряду шапки, рядом с быстрым поиском. Она видна только вошедшему:

```html layout/header/header.html
@if (auth.isLoggedIn()) {
  <button class="logout" (click)="auth.logOut()">Выйти</button>
}
```

Метод хранилища можно вызвать прямо из шаблона: `auth` — поле компонента. Стили `.logout` уже в `header.css`: кнопка выглядит как пункт меню.

::: task
1. В `AuthStore` внедрите `HttpClient` и напишите `logIn(credentials: Credentials)`: `POST /api/login` через `firstValueFrom`, из ответа — токен и пользователь в сигналы. Типы `Credentials` (`email`, `password`, с `export`) и `LoginResponse` (`token`, `user`) объявите в том же файле.
2. Напишите `logOut()`: оба сигнала — в `null`.
3. В `Login` замените запрос на `await this.auth.logIn(this.model())`, а после входа — `this.router.navigateByUrl('/')`. Уберите `HttpClient`, `LoginResponse`, `LoginData` (модель — `signal<Credentials>`) и сигнал `userName`; в шаблоне форма теперь без `@if`.
4. В шапке, после `<app-quick-search />`, — кнопка «Выйти» (`class="logout"`), только для вошедшего.
:::

## Что получилось

Нажмите «Заполнить тестовыми данными» и «Войти». Превью перешло на главную, а в шапке — «Пользователь» и «Выйти». Нажмите «Выйти» — снова «Войти», страница не сменилась.

Войдите с неверным паролем — под формой «Неверный e-mail или пароль», в шапке по-прежнему «Войти». Во вкладке «Сеть» — `POST /api/login` с ответом `401`.

Теперь войдите и нажмите ⟳ над превью. Приложение запустилось заново — и снова «Войти». Состояние хранилища живёт в памяти, пока работает приложение. Как пережить перезагрузку, разберём в следующем шаге.

## Эксперименты

**Что внутри токена.** Во вкладке «Сеть» щёлкните по `POST /api/login`: в ответе — `token` вида `eyJhbGci….eyJzdWIi….aAjp0B…` — три части через точку. Напечатайте среднюю часть в `logIn`, перед записью в сигналы:

```ts
const [, payload] = response.token.split('.');
console.log(atob(payload));
```

В консоли:

```text
{"sub":1,"role":"user","typ":"access","iat":1792328197,"exp":1792331797}
```

Это **данные токена**: `sub` — id пользователя, `role` — роль, `iat` и `exp` — когда токен выдан и когда истечёт (секунды с 1970 года; между ними — час). Их может прочитать любой, у кого есть токен: они не зашифрованы, а только записаны в Base64. Уберите строки.

**Ошибка не дошла до формы.** Оберните всё тело `logIn` в `try { … } catch {}` — «проглотите» ошибку. Войдите с неверным паролем: под формой ничего, кнопка снова активна, а превью перешло на главную, где по-прежнему «Войти». Для формы `logIn` завершился удачно. Поэтому хранилище и не ловит ошибку — решать, что сказать покупателю, должен тот, кто его о чём-то просил. Верните как было.

::: deep Под капотом: JWT
Токены учебного бэкенда — **JWT** (JSON Web Token), самый распространённый формат токенов. Три части через точку:

1. **Заголовок** — `{"alg":"HS256","typ":"JWT"}`: как подписан токен.
2. **Данные** (claims) — то, что мы напечатали: кто, с какой ролью, до какого времени.
3. **Подпись** — результат HMAC-SHA256 от первых двух частей и секретного ключа сервера.

Части записаны в Base64url — вариант Base64 для адресов. Подпись делает токен неподделываемым: поменяйте в данных `"role":"user"` на `"admin"` — и подпись перестанет сходиться. Ключа у браузера нет, правильную подпись для новых данных он не посчитает. Учебный бэкенд на такой токен отвечает `401` «Недействительный токен».

Из этого два следствия:

- сервер может **не хранить** выданные токены: достаточно проверить подпись и срок. Учебный бэкенд так и делает — поэтому выданный токен остаётся действительным даже после перезапуска превью, когда бэкенд начинает «с чистого листа». Это пригодится в следующем шаге;
- для магазина токен — непрозрачная строка. Читать из него роль и решать по ней, что показать, не нужно: пользователя с ролью сервер прислал отдельно. А секретов в данных JWT быть не должно — их прочитает любой.

Наш `logOut` только забывает токен в браузере. Сам токен остаётся действительным до `exp`: сервер его не хранит, значит, и «отменить» ему нечего. Поэтому токены доступа делают короткоживущими, а долгую сессию держат на втором токене — refresh-токене. Это шаг про обновление токена.
:::
