Покупатель вошёл, перезагрузил страницу — и снова «Войти». Хранилище живёт в памяти, пока работает приложение, а перезагрузка запускает приложение заново. Нужна **сессия** — вход, который переживает перезагрузку. В этом шаге магазин запомнит токен и при запуске спросит сервер, чей он.

## Где хранить токен

Что-то должно пережить перезагрузку. Вариантов у браузера несколько:

| Где | Переживает перезагрузку | Другие вкладки |
|---|---|---|
| память (поле, сигнал) | нет | нет |
| `sessionStorage` | да, пока открыта вкладка | нет |
| `localStorage` | да, пока не удалят | да |
| cookie | да, до срока cookie | да |

Корзину и избранное мы уже храним в `localStorage` (глава 9). Возьмём его и для токена. У этого выбора есть цена в безопасности: `localStorage` может прочитать любой скрипт на странице. Чем это опасно и чем хороши cookie, разберём в последнем шаге главы.

Сохраняем **только токен**. Пользователя — имя и роль — не сохраняем: при запуске о нём заново расскажет сервер. Так магазин не покажет устаревшую роль, если её поменяли, а подправленная в `localStorage` строка ничего не изменит: сервер ответит по токену.

```ts core/auth-store.ts {4,10}
async logIn(credentials: Credentials) {
  // …запрос…
  this.userState.set(response.user);
  localStorage.setItem(TOKEN_KEY, response.token);
}

logOut() {
  this.tokenState.set(null);
  this.userState.set(null);
  localStorage.removeItem(TOKEN_KEY);
}
```

В главе 9 корзину сохранял эффект: корзина меняется из многих мест. Вход меняют только два метода — `logIn` и `logOut`, поэтому запись прямо в них проще и понятнее.

## Восстановление входа

При запуске магазин берёт токен из `localStorage` и спрашивает сервер: `GET /api/me` — «кто это?».

```ts core/auth-store.ts {6,9-11,15-17}
async restore() {
  const token = localStorage.getItem(TOKEN_KEY);
  if (!token) {
    return;
  }
  this.tokenState.set(token);
  try {
    const user = await firstValueFrom(
      this.http.get<User>('/api/me', {
        headers: { Authorization: `Bearer ${token}` },
      }),
    );
    this.userState.set(user);
  } catch (error) {
    this.tokenState.set(null);
    if (error instanceof HttpErrorResponse && error.status === 401) {
      localStorage.removeItem(TOKEN_KEY);
    }
  }
}
```

Разберём по строкам:

- токена нет — покупатель не входил, спрашивать нечего;
- токен — сразу в сигнал, пользователь — когда ответит сервер. Это тот промежуток, ради которого в хранилище два сигнала: токен уже есть, а `isLoggedIn()` ещё `false`;
- запросу нужен токен. Сервер ждёт его в заголовке `Authorization` в виде `Bearer <токен>` («предъявитель»: кто предъявил токен, того сервер и считает вошедшим). `HttpClient` принимает заголовки в объекте `headers`. В следующем шаге это будет делать интерцептор — для всех запросов сразу;
- `401` — сервер токен не принял: истёк или подделан. Забываем его насовсем. Любая другая ошибка — сервер недоступен — тоже значит «не вошли», но токен остаётся: при следующем запуске магазин попробует снова. Выкидывать покупателя из-за минутного сбоя сервера незачем.

`restore` **не бросает ошибок** — почему это важно, увидим в экспериментах.

## Подождать до запуска

Когда вызвать `restore`? Если вызвать в конструкторе `App`, приложение отрисуется сразу, с «Войти», а через полсекунды «Войти» сменится именем. Хуже того, гард страницы «Мои заказы» (он появится в шаге 6) успеет решить, что покупатель не вошёл. Проверку входа нужно закончить **до** того, как приложение начнёт работать.

Для этого есть **инициализатор приложения** — `provideAppInitializer` из `@angular/core`:

```ts app.config.ts
providers: [
  provideBrowserGlobalErrorListeners(),
  // До запуска приложения — восстановить вход
  provideAppInitializer(() => inject(AuthStore).restore()),
  // …
],
```

Функция инициализатора выполняется в контексте внедрения — `inject` в ней работает. Если она вернула промис (или Observable), Angular ждёт его и только потом создаёт корневой компонент и запускает роутер. Первая навигация — после инициализаторов.

```text
bootstrapApplication
  │
  ├─ инициализаторы: restore() → GET /api/me
  │        …ждём ответа…
  ├─ App и шапка: уже «Пользователь»
  └─ роутер: первая страница
```

::: task
1. Заведите константу `TOKEN_KEY = 'hod-konem:token'`. В `logIn` сохраняйте токен в `localStorage`, в `logOut` — удаляйте.
2. Напишите `async restore()`: токена нет — выйти; есть — в `tokenState`, затем `GET /api/me` с заголовком `Authorization: Bearer <токен>`, ответ — в `userState`. При ошибке — `tokenState` в `null`, а при `401` ещё и удалить токен из `localStorage`.
3. В `app.config.ts` добавьте `provideAppInitializer(() => inject(AuthStore).restore())`.
:::

## Что получилось

Войдите и нажмите ⟳ над превью — в шапке по-прежнему «Пользователь». Во вкладке «Сеть» первый запрос — `GET /api/me`; щёлкните по нему: в заголовках запроса — `authorization: Bearer eyJ…`. Главная загрузила игры только после него.

Нажмите «Выйти» и ⟳ — «Войти», запроса `GET /api/me` нет: токена в `localStorage` больше нет.

## Эксперименты

**Медленный сервер.** Войдите, во вкладке «Сеть» поставьте задержку 3000 мс и нажмите ⟳. Три секунды превью пустое: ни шапки, ни страницы — Angular ждёт инициализатор. Потом всё появляется сразу, и уже с именем. Это цена надёжности: пока сервер не ответил, показывать нечего. Если такая пауза недопустима, приложение запускают без ожидания, а состояние «ещё проверяем» показывают явно — например, заглушкой вместо «Войти». Верните 300 мс.

**Без ожидания.** Уберите из инициализатора возврат промиса — пусть функция только вызывает `restore`:

```ts
provideAppInitializer(() => {
  inject(AuthStore).restore();
}),
```

Задержка 1000 мс и ⟳. Теперь шапка появилась сразу — с «Войти», и только через секунду «Войти» сменилось именем. Angular ждёт только то, что инициализатор **вернул**. Верните как было.

**Ошибка в инициализаторе.** Уберите из `restore` `try`/`catch` — оставьте только запрос и запись пользователя. Войдите, во вкладке «Сеть» включите «Ошибка 500» и нажмите ⟳. Превью пустое — навсегда: промис инициализатора отклонён, и Angular не запускает приложение. В консоли — ошибка `HttpErrorResponse`. Поэтому `restore` ошибок не бросает: недоступный сервер — не повод показывать пустую страницу. Верните `try`/`catch`.

**Сервер недоступен.** С «Ошибкой 500» и прежним `restore` нажмите ⟳: магазин работает, в шапке «Войти», а `GET /api/me` в «Сети» — трижды: повтор при `5xx` из главы 12. Выключите «Ошибку 500» и снова ⟳ — вы снова вошли: токен остался в `localStorage`.

::: legacy Вы встретите в старом коде: APP_INITIALIZER
До Angular 19 инициализатор подключали токеном-мультипровайдером:

```ts
{
  provide: APP_INITIALIZER,
  useFactory: (auth: AuthStore) => () => auth.restore(),
  deps: [AuthStore],
  multi: true,
}
```

`APP_INITIALIZER` помечен `@deprecated` с версии 19 — «use provideAppInitializer instead». `provideAppInitializer` делает то же самое: регистрирует функцию в этом токене.
:::
