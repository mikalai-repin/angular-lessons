Покупатель вошёл, но сервер об этом знает только в одном запросе — `GET /api/me`, где заголовок мы добавили руками. Напишите отзыв об игре: после ответа сервера он подписан «Гость». Оформите заказ: на сервере он ничей. Токен должен уходить с **каждым** запросом к нашему серверу.

Дописывать заголовок в каждый запрос — долго, и новый запрос легко забыть. В главе 12 у нас уже было место, через которое проходит каждый запрос `HttpClient`, — интерцептор. Именно эту задачу мы тогда и обещали: «добавить заголовок с токеном входа».

## Что изменилось в коде

Новый файл `core/auth-interceptor.ts` — заготовка интерцептора, который пока только передаёт запрос дальше. В `app.config.ts` он ещё не подключён.

## Интерцептор входа

```ts core/auth-interceptor.ts {5,7-9,11-15}
export const authInterceptor: HttpInterceptorFn = (
  req,
  next,
) => {
  const token = inject(AuthStore).token();
  // Не вошёл — пропуска нет. Чужой адрес — пропуск не отдаём
  if (!token || !req.url.startsWith('/api/')) {
    return next(req);
  }
  // Запрос менять нельзя — только сделать копию с новым заголовком
  return next(
    req.clone({
      setHeaders: { Authorization: `Bearer ${token}` },
    }),
  );
};
```

По строкам:

- `inject` в интерцепторе работает, как и в главе 12: Angular вызывает функцию интерцептора в контексте внедрения. Токен — текущее значение сигнала: интерцептор вызывается на каждый запрос и каждый раз читает свежий токен;
- **только свои адреса.** Токен — пропуск к нашему серверу. Если магазин когда-нибудь обратится к чужому API (карты, оплата, аналитика) — через тот же `HttpClient` и те же интерцепторы, — пропуск не должен уйти туда. Наш сервер — адреса `/api/…`;
- **запрос неизменяем.** У `HttpRequest` все поля `readonly`, а изменения делают копией: `req.clone({ … })`. `setHeaders` добавляет заголовки к уже имеющимся (или заменяет одноимённые). Неизменяемость защищает от сюрпризов: повтор из `retryInterceptor` отправляет тот же объект запроса, и никто по дороге не мог его испортить.

Интерцептор подключаем вторым — сразу после лога:

```ts app.config.ts {4}
provideHttpClient(
  withInterceptors([
    loggingInterceptor,
    authInterceptor,
    cacheInterceptor,
    retryInterceptor,
  ]),
),
```

Порядок здесь почти не важен: лог стоит первым, чтобы видеть общее время запроса, а токен нужен запросу до того, как он уйдёт на сервер, — это сделает любое место в цепочке. Кэш (`cacheInterceptor`) хранит ответы по адресу, без учёта того, кто спрашивал. Сейчас он кэширует только игры и промокоды — одинаковые для всех. Кэшировать так ответы «для этого покупателя» нельзя: другой покупатель на том же компьютере получил бы чужие данные.

`restore` больше не добавляет заголовок сам: `tokenState` записан до запроса, и интерцептор его найдёт.

::: task
1. Напишите `authInterceptor`: токен из `AuthStore`; нет токена или адрес не начинается с `/api/` — запрос как есть; иначе — копия с заголовком `Authorization: Bearer <токен>`.
2. Подключите его в `app.config.ts` вторым, после `loggingInterceptor`.
3. Уберите `headers` из запроса `GET /api/me` в `restore`.
4. В `GamePage` черновик отзыва подписан «Вы». Подпишите его так же, как сервер: `this.auth.user()?.name ?? 'Гость'` (внедрите `AuthStore`). Тогда черновик не сменит подпись, когда сервер ответит.
:::

## Что получилось

Войдите и откройте любую игру, вкладку «Отзывы». Напишите отзыв и отправьте — он подписан «Пользователь», и сразу, и после ответа сервера. Во вкладке «Сеть» щёлкните по `POST /api/games/…/reviews`: в заголовках запроса — `authorization: Bearer eyJ…`. Тот же заголовок теперь у всех запросов к `/api/…`: каталога, главной, промокода.

Выйдите и напишите ещё один отзыв — «Гость», а в заголовках запроса `authorization` нет.

## Эксперименты

**Проверка входа в конструкторе.** Вызовите `restore` не из инициализатора, а из конструктора хранилища:

```ts core/auth-store.ts
constructor() {
  this.restore();
}
```

и уберите `provideAppInitializer` из `app.config.ts`. Войдите и нажмите ⟳: «Войти». В «Сети» нет даже `GET /api/me`. Добавьте в `catch` метода `restore` строку `console.log(String(error))` и снова ⟳:

```text
Error: NG0200: Circular dependency detected for `AuthStore`. …
```

Круг из главы 8: `AuthStore` ещё создаётся, его конструктор отправляет запрос, запрос проходит через интерцептор, а интерцептор просит `AuthStore`, который ещё не готов. Ошибку проглотил наш же `catch` — и покупатель молча оказался «не вошедшим». Поэтому запросы — не в конструкторе сервиса, который нужен интерцептору. Инициализатор вызывает `restore` у уже созданного хранилища. Верните как было.

**Токен всем.** Уберите из условия `!req.url.startsWith('/api/')`. В магазине ничего не изменится: все запросы и так идут на `/api/…`. Но представьте, что каталог начнёт показывать карты пунктов самовывоза с чужого сервера через `HttpClient`. Тогда пропуск вашего покупателя уйдёт чужому серверу — а с ним можно делать от имени покупателя всё, что разрешено ему в магазине. Верните условие.

::: deep Под капотом: чей запрос
Учебный бэкенд узнаёт покупателя по заголовку `Authorization`. Нет заголовка — гость: отзыв от «Гостя», заказ с `userId: null`. Есть — сервер проверяет подпись и срок токена и находит пользователя по `sub`. Токен есть, но не годится — `401`, даже если адрес не требует входа: клиент должен узнать, что его пропуск больше не действует. Так устроены многие API, но не все: некоторые серверы на публичных адресах недействительный токен не замечают. Что делать магазину с таким `401` — в следующем шаге.
:::
