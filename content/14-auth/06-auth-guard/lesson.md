## Гард входа

Гарды мы писали в главе 10: функция, которую роутер спрашивает перед переходом. `CanActivateFn` получает маршрут и **состояние роутера** — снимок будущей страницы, в том числе её полный адрес `state.url`:

```ts core/auth-guards.ts {2,5-7}
export const authGuard: CanActivateFn = (_route, state) => {
  if (inject(AuthStore).isLoggedIn()) {
    return true;
  }
  return inject(Router).createUrlTree(['/login'], {
    queryParams: { returnUrl: state.url },
  });
};
```

Гард вернул `UrlTree` — роутер отменяет переход и начинает новый, на `/login?returnUrl=%2Faccount%2Forders`: адрес страницы, куда шёл покупатель, — в query-параметре. `createUrlTree` сам закодирует его: `/` превратится в `%2F`, `?` — в `%3F`.

Гард читает `isLoggedIn()` один раз, в момент перехода. Это сигнал, но гард — не шаблон и не `computed`: подписки не возникает, и выход на открытой странице заказов гард сам не перезапустит. Это задача практикума.

Подключаем гард к маршруту заказов в `account/account.routes.ts`:

```ts account/account.routes.ts {5}
{
  path: 'orders',
  component: OrdersPage,
  title: 'Мои заказы',
  canActivate: [authGuard],
},
```

«Избранное» остаётся открытым: оно хранится в браузере, и вход для него не нужен.

## Возврат после входа

Страница входа читает `returnUrl` так же, как каталог читал фильтры в главе 10: query-параметр попадает во вход компонента (`withComponentInputBinding`):

```ts login/login.ts
readonly returnUrl = input<string>();
```

Если параметра нет, во входе `undefined`. После входа переходим по нему:

```ts login/login.ts
await this.auth.logIn(this.model());
this.router.navigateByUrl(safeReturnUrl(this.returnUrl()));
```

`safeReturnUrl` — проверка адреса:

```ts login/login.ts
function safeReturnUrl(url: string | undefined): string {
  return url?.startsWith('/') && !url.startsWith('//') ? url : '/';
}
```

Зачем она? Ссылку `…/login?returnUrl=…` может составить кто угодно — и прислать покупателю в письме «от магазина». Если магазин после входа послушно переходит по любому адресу, получается **открытый редирект**: настоящая страница входа магазина отправляет только что вошедшего покупателя на сайт мошенника — например, на копию магазина, которая просит «ещё раз ввести данные карты». Поэтому возвращаем только на свои страницы: адрес начинается с `/`. Но не с `//`: адрес `//evil.example/x` браузер читает как «тот же протокол, другой сайт».

В нашем магазине роутер и сам не уведёт за пределы приложения — это видно в экспериментах. Но `returnUrl` часто доходит до кода, который уходит со страницы по-настоящему: `location.href = returnUrl` или переход на сервер для входа через внешний сервис. Проверка стоит одну строку и делает намерение явным.

Последнее: интерцептор после `401` тоже отправляет на вход — пусть передаёт и адрес текущей страницы, `router.url`:

```ts core/auth-interceptor.ts
router.navigate(['/login'], {
  queryParams: { returnUrl: router.url },
});
```

## Что получилось

Превью открыто на `/account/orders`, но в адресной строке — `/login?returnUrl=%2Faccount%2Forders`: гард не пустил гостя. Войдите — и вы на «Моих заказах». Страница пока пустая: её содержимое — в практикуме.

Перейдите на «Избранное» и обратно на «Заказы» — гард пускает. Выйдите, перейдите на «Избранное» и щёлкните «Заказы» — снова страница входа.

## Эксперименты

**Чужие адреса.** Временно уберите проверку — `this.router.navigateByUrl(this.returnUrl() ?? '/')`. Наберите в адресной строке превью `/login?returnUrl=https://evil.example/x` и войдите. Вы на странице «Нет такой страницы», а адрес — `/https:`. Роутер не уходит с сайта: он разбирает любую строку как путь внутри приложения. `//evil.example/x` даст `/evil.example/x` — тоже 404. Верните `safeReturnUrl`: теперь оба адреса ведут на главную.

**Гард раньше проверки входа.** Вспомните опыт из шага про сессию: уберите `return` из инициализатора — `provideAppInitializer(() => { inject(AuthStore).restore(); })`. Войдите, откройте «Мои заказы» и нажмите ⟳. Вы на странице входа, а в шапке — «Пользователь»: гард спросил `isLoggedIn()` раньше, чем сервер ответил на `GET /api/me`. Вот зачем инициализатор ждёт. Верните как было.

::: deep Под капотом: canActivate или canMatch
В главе 10 было два вида гардов на вход: `canActivate` и `canMatch`. Разница видна на кабинете. Откройте как гость «Избранное»: в консоли «Кабинет: модуль загружен» — маршруты кабинета загружены, гард `orders` спросят, только когда покупатель пойдёт на заказы.

`canMatch` работает раньше — при распознавании адреса: если гард вернул `false`, маршрут для роутера «не подходит», и роутер ищет следующий. Ленивый модуль такого маршрута даже не загружается. Это пригодится для админки в следующем шаге: код админки гостю и покупателю не нужен вовсе.

`canActivate` знает полный адрес будущей страницы (`state.url`) — удобно для `returnUrl`. `canMatch` получает маршрут, сопоставляемые куски адреса и частичный снимок (параметры, query-параметры), но не полный адрес будущей страницы.
:::
