Мы научились выходить, когда сервер перестал принимать токен. Но в этом шаге токен живёт **20 секунд** — и каждые 20 секунд покупателя выбрасывает на страницу входа. Почему бы не выдавать токен на месяц?

Потому что токен доступа нельзя отозвать. Сервер не хранит выданные токены — он проверяет подпись и срок (шаг про вход и выход). Украденный токен, выход, смена пароля — ничто не отменит токен до его `exp`. Чем дольше он живёт, тем дольше им может пользоваться тот, кто его украл.

Обычное решение — **два токена**:

- **токен доступа** (access token) — короткий: минуты. Уходит с каждым запросом;
- **refresh-токен** — длинный: дни. Уходит только в одном запросе — `POST /api/refresh` — и в ответ сервер выдаёт новую пару. Его сервер **запоминает** и может отозвать.

```text
 магазин                         сервер
   │ GET /api/games  (токен истёк) ─►│
   │◄────────────────────────── 401  │
   │ POST /api/refresh               │
   │ { refreshToken } ──────────────►│ отзывает
   │◄──── { token, refreshToken }    │ старый
   │ GET /api/games  (новый) ───────►│
   │◄────────────────────────── 200  │
```

Покупатель ничего не замечает: запрос лишь шёл чуть дольше.

## Что умеет учебный бэкенд

Вход уже давно отвечает `{ token, refreshToken, user }` — второй токен мы до сих пор не брали.

- `POST /api/refresh` с `{ refreshToken }` — новая пара `{ token, refreshToken }`. Старый refresh-токен при этом **отзывается**: каждый работает один раз. Это называется **ротацией**. Повторное обновление со старым токеном — `401` «Сессия истекла. Войдите снова»;
- `POST /api/logout` с `{ refreshToken }` — отзывает refresh-токен: по нему больше не получить новую пару. Отвечает `204` всегда.

## Хранилище

Refresh-токен хранится рядом с токеном доступа — в `localStorage`, иначе он не переживёт перезагрузку. Обе записи — в одном методе:

```ts core/auth-store.ts
private saveTokens({ token, refreshToken }: Tokens) {
  this.tokenState.set(token);
  localStorage.setItem(TOKEN_KEY, token);
  localStorage.setItem(REFRESH_KEY, refreshToken);
}
```

`logIn` вызывает его вместо прежних двух строк. `logOut` теперь сообщает серверу, чтобы тот отозвал refresh-токен, — и не ждёт ответа: выйти нужно сразу, даже если сервер недоступен. Пустой обработчик `error` нужен, чтобы ошибка этого запроса не попала в консоль как необработанная:

```ts core/auth-store.ts
this.http
  .post('/api/logout', { refreshToken }, { context: skipAuth() })
  .subscribe({ error: () => {} });
```

Само обновление — метод `refresh()`, который возвращает поток с новым токеном доступа:

```ts core/auth-store.ts {6,9-14}
private refreshing: Observable<string> | null = null;

refresh(): Observable<string> {
  const refreshToken = localStorage.getItem(REFRESH_KEY);
  // …нет refresh-токена — throwError…
  this.refreshing ??= this.http
    .post<Tokens>('/api/refresh', { refreshToken }, { context: skipAuth() })
    .pipe(
      map((tokens) => {
        this.saveTokens(tokens);
        return tokens.token;
      }),
      finalize(() => (this.refreshing = null)),
      shareReplay(1),
    );
  return this.refreshing;
}
```

Главная хитрость — **одно обновление на всех**. На главной два запроса: хиты и скидки. Токен истёк — оба получают `401` почти одновременно, и оба просят новый токен. Если каждый отправит свой `POST /api/refresh`, второй придёт со старым refresh-токеном, который первый уже израсходовал. Ротация ответит `401` — и покупателя выбросит, хотя всё было в порядке. Поэтому:

- `refreshing` — поток обновления, которое **уже идёт**. `??=` создаёт новый, только если его нет;
- `shareReplay(1)` делает поток общим. Поток `HttpClient` холодный: в главе 12 две подписки на `get` дали два запроса. После `shareReplay` запрос отправится один раз, при первой подписке, а все подписчики — и те, кто придёт позже, — получат тот же ответ;
- `finalize` выполняется, когда запрос закончился — удачно или с ошибкой. Он обнуляет `refreshing`: следующее истечение токена начнёт новое обновление.

## Метка «без токена»

Обновление и выход несут в теле refresh-токен, а токен доступа им не нужен. Более того, он вреден — интерцептор не должен обрабатывать `401` от самого обновления. Метку запроса мы уже делали для кэша в главе 12 — `HttpContextToken`:

```ts core/auth-store.ts
export const SKIP_AUTH = new HttpContextToken<boolean>(() => false);
const skipAuth = () => new HttpContext().set(SKIP_AUTH, true);
```

Метка объявлена в `auth-store.ts`, а не в интерцепторе: интерцептор импортирует хранилище, и если бы хранилище импортировало метку из интерцептора, получился бы круговой импорт. Превью его не поддерживает; в проекте CLI он бы собрался, но и там файлы, которые импортируют друг друга, лучше не заводить.

## Интерцептор

```ts core/auth-interceptor.ts {1,10-24}
if (!token || !req.url.startsWith('/api/') || req.context.get(SKIP_AUTH)) {
  return next(req);
}
return next(withToken(req, token)).pipe(
  catchError((error: unknown) => {
    if (!(error instanceof HttpErrorResponse) || error.status !== 401) {
      return throwError(() => error);
    }
    // 401: получаем новый токен и повторяем тот же запрос с ним
    return auth.refresh().pipe(
      catchError((refreshError: unknown) => {
        // Сервер обновления недоступен — не выходим
        if (refreshError instanceof HttpErrorResponse && refreshError.status !== 401) {
          return throwError(() => refreshError);
        }
        // Refresh-токен не принят — сессия закончилась
        if (auth.isLoggedIn()) {
          router.navigate(['/login'], { queryParams: { returnUrl: router.url } });
        }
        auth.logOut();
        return throwError(() => error);
      }),
      switchMap((fresh) => next(withToken(req, fresh))),
    );
  }),
);
```

`withToken` — маленькая функция над `req.clone`: копию с заголовком нужно сделать дважды.

На `401` интерцептор возвращает **другой поток**: обновление, а за ним — `switchMap` (глава 12) на тот же запрос с новым токеном. Тот, кто отправлял запрос, ничего не заметит: он получит ответ повторного запроса.

Порядок операторов важен. `catchError` стоит **до** `switchMap` и ловит только ошибку обновления. Если бы он стоял после, то ловил бы и ошибки повторного запроса — и, например, `409` при оформлении заказа превратился бы в выход из магазина.

Выход — только если сервер **не принял** refresh-токен (`401`) или его нет вовсе. Если сервер обновления недоступен (`500`, обрыв сети), ошибка уходит дальше, а покупатель остаётся вошедшим — как в шаге про сессию: выкидывать из-за минутного сбоя незачем. Сам выход — тот же, что был в шаге про `401`: на вход с `returnUrl`, если покупатель считался вошедшим. Проверка входа после перезагрузки теперь тоже обновляет токен: `GET /api/me` проходит через тот же интерцептор.

::: task
1. В `AuthStore`: константа `REFRESH_KEY = 'hod-konem:refresh-token'`, метка `SKIP_AUTH` (с `export`) и функция `skipAuth()`; тип `Tokens` (`token`, `refreshToken`), `LoginResponse extends Tokens`.
2. Закрытый метод `saveTokens` — оба токена в `localStorage`, токен доступа — в сигнал. `logIn` — через него.
3. `logOut`: если есть refresh-токен — `POST /api/logout` с `{ refreshToken }` и меткой `skipAuth()`, без ожидания ответа; затем очистить сигналы и оба ключа `localStorage`.
4. Метод `refresh()` — общий поток обновления, как в тексте.
5. В интерцепторе: запросы с меткой `SKIP_AUTH` — без токена; на `401` — `auth.refresh()`; если обновление ответило `401` или refresh-токена нет — выход (как раньше), другая ошибка обновления — дальше, без выхода; при успехе — тот же запрос с новым токеном (`switchMap`).
:::

## Что получилось

Выйдите и войдите снова: токен из прошлых шагов живёт час, а нам нужен 20-секундный — и refresh-токен к нему. Откройте каталог, подождите 20 секунд и щёлкните «Главная». Подборки загрузились, в шапке — «Пользователь». Во вкладке «Сеть»:

```text
GET  /api/games?sort=rating&size=4   401
GET  /api/games?onSale=true          401
POST /api/refresh                    200
GET  /api/games?sort=rating&size=4   200
GET  /api/games?onSale=true          200
```

Два ответа `401` — и **одно** обновление. Щёлкните по повторным запросам: в `authorization` — уже другой токен. А в консоли — три строки:

```text
POST /api/refresh → 200, 303 мс
GET /api/games?sort=rating&size=4 → 200, 909 мс
GET /api/games?onSale=true → 200, 909 мс
```

Обновление — обычный запрос `HttpClient`, и лог видит его отдельно. А запросы главной лог видит целиком: он стоит в цепочке перед интерцептором входа, и ошибка, обновление и повтор остались внутри — поэтому время втрое больше обычного.

Подождите ещё 20 секунд и нажмите ⟳: `GET /api/me` → `401`, `POST /api/refresh` → `200`, `GET /api/me` → `200`. Вход восстановлен и после перезагрузки.

Нажмите «Выйти»: в «Сети» — `POST /api/logout` → `204`. Этот refresh-токен больше ничего не обновит.

## Эксперименты

**Каждому своё обновление.** Замените в `refresh` `??=` на `=` — пусть каждый запрос получает новое обновление. Войдите, откройте каталог, подождите 20 секунд, «Главная». В «Сети» — два `POST /api/refresh`: первый `200`, второй `401` «Сессия истекла. Войдите снова». Вы на странице входа: второе обновление пришло с refresh-токеном, который первое уже израсходовало. Верните `??=`.

**Обновление без метки.** Уберите `{ context: skipAuth() }` у запроса `/api/refresh`, а вместо настоящего refresh-токена отправьте испорченный — как будто его отозвали: `{ refreshToken: 'broken' }`. Войдите, откройте каталог, подождите 20 секунд, «Главная». Восемь серых заглушек вместо игр — навсегда, а в шапке «Пользователь». Обновление получило `401`, и интерцептор… попросил обновление: тот же поток `refreshing`, который ещё не закончился, потому что ждёт ответа от этого самого интерцептора. Круг без выхода. Верните метку, оставив `'broken'`, — и вы окажетесь на странице входа, как и положено при отозванном refresh-токене. Верните настоящий `refreshToken`.

::: deep Как в настоящем проекте: где хранить refresh-токен
Refresh-токен ценнее токена доступа: по нему можно получать новые токены неделю. Поэтому в настоящих проектах его часто не отдают в JavaScript вовсе: сервер кладёт его в cookie с флагом `HttpOnly`, браузер сам отправляет её на `/api/refresh`, а код страницы её не видит. Об этом — последний шаг главы. Ещё бывает, что обновляют токен заранее, до `401`: по `exp` из данных токена ставят таймер. Это экономит один неудачный запрос, но `401` всё равно нужно обрабатывать — часы клиента и сервера могут расходиться.
:::
