Магазин хранит токены в `localStorage` и отправляет их в заголовке `Authorization`. Так устроены многие приложения, и для учебного магазина это удобно: всё видно во вкладке «Сеть» и в коде. Но у этого выбора есть цена, а у другого распространённого способа — cookie — своя. В этом шаге разберём обе, а заодно защиту от подделки запросов, которая уже встроена в `HttpClient`. Шаг без задания: код магазина не меняется, опыты — по желанию.

## Две угрозы

**XSS** (cross-site scripting, внедрение скрипта) — на странице магазина выполняется чужой код. Например, отзыв с `<script>`, который магазин вставил в страницу как HTML, или взломанная сторонняя библиотека. Такой код может всё, что может код магазина: читать `localStorage`, отправлять запросы, менять страницу.

**CSRF** (cross-site request forgery, подделка запроса) — чужой сайт заставляет браузер покупателя отправить запрос в магазин: форма на `evil.example`, которая сама отправляется на `https://hod-konem.example/api/orders`. Если браузер прикладывает к таким запросам что-то автоматически — cookie, — сервер примет запрос за настоящий.

## Токен в localStorage

`localStorage` читает любой скрипт со страницы магазина. Значит, при XSS украсть токены — одна строка. Особенно ценен refresh-токен: по нему можно получать новые токены доступа неделю.

Зато CSRF такому магазину не страшен. Токен браузер сам никуда не прикладывает: заголовок `Authorization` добавляет наш интерцептор, а чужой сайт прочитать токен из нашего `localStorage` не может.

Angular сильно усложняет XSS: интерполяция `{{ }}` экранирует текст, а `[innerHTML]` вырезает `<script>` и обработчики (глава 2). Но защита ломается, если её обойти (`bypassSecurityTrustHtml`), вставить HTML мимо Angular (`element.innerHTML = …`) или подключить скомпрометированный пакет.

## Сессия в httpOnly-cookie

Другой подход: токен вообще не попадает в JavaScript. При входе сервер отвечает заголовком:

```text
Set-Cookie: session=…; HttpOnly; Secure; SameSite=Lax; Path=/api
```

- `HttpOnly` — cookie не видна JavaScript: `document.cookie` её не покажет, и XSS её не украдёт;
- `Secure` — только по HTTPS;
- `SameSite=Lax` — на запросы с чужих сайтов (кроме обычного перехода по ссылке) браузер её не отправит. Это первая защита от CSRF;
- браузер сам прикладывает cookie к запросам на свой сайт. Интерцептор с токеном не нужен, а `AuthStore` хранит только пользователя.

Если API живёт на другом домене, браузер отправляет на него cookie, только когда запрос разрешает это явно — в `HttpClient` это параметр запроса `withCredentials: true` (или `credentials: 'include'`, как у `fetch`).

Цена: раз cookie уходит автоматически, возвращается угроза CSRF. `SameSite` закрывает большую часть случаев, но обычно добавляют и вторую защиту — XSRF-токен.

## XSRF-токен в HttpClient

Схема «двойной отправки»:

1. Сервер кладёт в **обычную** (не `HttpOnly`) cookie `XSRF-TOKEN` случайное значение.
2. Код магазина читает её и копирует в заголовок `X-XSRF-TOKEN` каждого изменяющего запроса.
3. Сервер сравнивает заголовок с cookie.

Чужой сайт может заставить браузер отправить cookie, но **прочитать** её не может — значит, не может и подставить правильный заголовок.

Второй пункт схемы `HttpClient` выполняет сам — это интерцептор, который включён по умолчанию (`xsrfInterceptorFn` в исходниках `@angular/common/http`). Он:

- пропускает `GET` и `HEAD` — запросы, которые ничего не меняют;
- пропускает запросы на другой сайт: токен — только своему серверу;
- берёт значение cookie `XSRF-TOKEN` и ставит заголовок `X-XSRF-TOKEN`, если cookie есть, а заголовка ещё нет;
- стоит в цепочке **первым** — раньше интерцепторов из `withInterceptors`.

Имена меняются настройкой — если сервер называет их иначе:

```ts app.config.ts
provideHttpClient(
  withXsrfConfiguration({ cookieName: 'CSRF', headerName: 'X-CSRF' }),
  withInterceptors([…]),
),
```

`withNoXsrfProtection()` выключает интерцептор совсем. Обе функции в одном `provideHttpClient` — ошибка: в dev-режиме приложение не запустится, а в консоли будет

```text
Error: Configuration error: found both withXsrfConfiguration() and withNoXsrfProtection() in the same call to provideHttpClient(), which is a contradiction.
```

## Опыты

**Заголовок из cookie.** Первой строкой в `main.ts` допишите:

```ts main.ts
document.cookie = 'XSRF-TOKEN=demo-123; max-age=60';
```

(`max-age=60` — cookie исчезнет через минуту: превью живёт на том же адресе, что и платформа курса, и вечная cookie досталась бы всем следующим главам.) Войдите. Во вкладке «Сеть» щёлкните по `POST /api/login`: в заголовках запроса — `x-xsrf-token: demo-123`. У `GET /api/games…` этого заголовка нет. Учебный бэкенд заголовок не проверяет — это делал бы настоящий сервер.

**Без защиты.** Добавьте в `provideHttpClient` первым аргументом `withNoXsrfProtection()` (импорт — из `@angular/common/http`) и войдите снова: у `POST /api/login` заголовка `x-xsrf-token` больше нет. Уберите и эту строку, и строку из `main.ts`.

**Что видит скрипт.** Добавьте в конструктор `App` строку `console.log(localStorage.getItem('hod-konem:refresh-token'));` и нажмите ⟳: в консоли — refresh-токен вошедшего покупателя. Ровно это сделал бы внедрённый скрипт — только вместо консоли отправил бы токен к себе. Уберите строку.

## Что выбрать

| | Токены в `localStorage` | httpOnly-cookie |
|---|---|---|
| XSS крадёт токен | да | нет (но может действовать от имени покупателя, пока открыта страница) |
| CSRF | не страшен | `SameSite` + XSRF-токен |
| Код в браузере | интерцептор, хранение, обновление | почти ничего: браузер всё делает сам |
| API на другом домене | без особых настроек | `withCredentials`, настройки CORS и cookie |

Однозначного ответа нет, и решает обычно бэкенд-команда. Распространённый компромисс — токен доступа в памяти приложения (в сигнале, без `localStorage`), а refresh-токен — в httpOnly-cookie, которую браузер отправляет только на `/api/refresh`.

## Вход через внешний сервис

«Войти через …» — это протоколы **OAuth 2.0** и **OpenID Connect**: магазин отправляет покупателя на страницу входа провайдера, тот возвращает его с одноразовым кодом, а код меняют на токены. Для одностраничных приложений рекомендуют поток Authorization Code с PKCE. В самом Angular модуля для этого нет — берут готовую библиотеку OpenID Connect или SDK провайдера. Всё, что мы сделали в главе, остаётся на месте: хранилище входа на сигналах, интерцептор, гарды, `returnUrl`, обработка `401`. Меняется только то, откуда берутся токены.
