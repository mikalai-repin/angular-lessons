`CartStore` — сердце магазина. В нём всё, что мы строили с главы 9: позиции корзины в сигнале, суммы в `computed`, промокод в `linkedSignal`, сохранение в `localStorage` эффектом, аналитика через `injectAsync`. Правил много, и все они видны только косвенно — через шапку, корзину и оформление. Тест проверит их напрямую, без единого экрана.

## Что изменилось в коде

- `testing/fake-game.ts` — помощник `fakeGame()`. Тестам нужны игры, а у `Game` полтора десятка полей. Помощник возвращает игру, где всё заполнено, а тест переопределяет только то, что ему важно: `fakeGame({ price: 500 })`, `fakeGame({ id: 2, inStock: 0 })`. Тест сразу показывает, от чего зависит результат.
- `core/cart-store.spec.ts` — набор `CartStore` с первым тестом.

## Сервис из `TestBed`

```ts core/cart-store.spec.ts
describe('CartStore', () => {
  let cart: CartStore;

  beforeEach(() => {
    localStorage.clear();
    cart = TestBed.inject(CartStore);
  });

  it('новая корзина пуста', () => {
    expect(cart.count()).toBe(0);
    expect(cart.total()).toBe(0);
  });
});
```

**`TestBed.inject(CartStore)`** просит сервис у стенда — так же, как `inject(CartStore)` в компоненте просит его у приложения. `CartStore` — `@Service()`, поэтому стенду не нужен провайдер: DI создаст корзину, как в магазине. Вместе с ней — всё, что она внедряет: `SHOP_CONFIG` со значениями по умолчанию.

После каждого теста стенд разбирается, а с ним и корзина. Следующий тест получит **новый** экземпляр — тесты не делятся состоянием.

Зачем `localStorage.clear()`? Корзина читает `localStorage`, когда создаётся (`loadCart` из главы 9), а эффект пишет туда после каждого изменения. Без очистки корзина, сохранённая одним тестом, попала бы в следующий. Хранилище в превью у тестов своё, в памяти: ваша корзина из магазина в тесты не попадёт, и тесты её не сотрут. Так же устроен `ng test`: там у тестов своё пустое хранилище.

## Сигналы читаются сразу

```ts
it('считает штуки и сумму', () => {
  const game = fakeGame({ price: 1000 });
  cart.add(game);
  cart.add(game);
  cart.add(fakeGame({ id: 2, price: 500 }));
  expect(cart.count()).toBe(3);
  expect(cart.subtotal()).toBe(2500);
});
```

Никаких ожиданий: `add` записал новый массив в сигнал, а `count()` и `subtotal()` — `computed`, они пересчитываются при чтении (глава 3). Тест на сервис с сигналами — просто вызовы методов и чтения.

## Эффекты — нет

Корзина сохраняет себя эффектом. Проверим:

```ts
it('сохраняет корзину в localStorage', () => {
  cart.add(fakeGame());
  const saved = localStorage.getItem('hod-konem:cart:v2');
  expect(JSON.parse(saved ?? '[]')).toEqual([
    { game: fakeGame(), quantity: 1 },
  ]);
});
```

Тест падает: `expected [] to deeply equal [ { game: { id: 1, …(12) }, …(1) } ]` — в хранилище ничего нет. Эффект не выполняется в момент записи в сигнал. Сигнал только помечает его: «пора». Выполнит его Angular, когда будет обновлять приложение. В магазине это происходит само, а в тесте синхронный код идёт дальше, и до обновления дело не доходит.

**`TestBed.tick()`** — обновить стенд прямо сейчас: выполнить ждущие эффекты и проверить компоненты, если они есть. Добавьте его после `add`, и тест пройдёт:

```ts {3}
it('сохраняет корзину в localStorage', () => {
  cart.add(fakeGame());
  TestBed.tick();
  // …
});
```

Матчер **`toEqual`** сравнивает содержимое: массив с одним объектом, у которого такие же поля. `toBe` здесь не подошёл бы: `JSON.parse` создаёт новые объекты.

## Что получилось — и что ещё

Все тесты ✓. Но под ними в отчёте — то, чего мы не ждали:

```text
Ошибки вне тестов: 9
Unhandled Rejection: Error: NG0205: Injector has already been destroyed.
```

Девять одинаковых ошибок — по одной на каждый `add`, который дошёл до аналитики. **Ошибка вне тестов** — исключение или отклонённый промис, который никто не обработал. Тест к этому моменту уже закончился, поэтому раннер не может приписать ошибку тесту и показывает её отдельно. Vitest считает такой прогон неудачным, даже если все тесты прошли: в `ng test` это раздел «Unhandled Errors» и строка `Errors  1 error` в итоге.

Почему там одна, а не девять? Ошибка случается не в тесте, а когда загрузится модуль. Прогон в `ng test` может закончиться раньше — и ошибка просто не успеет случиться. Превью в конце прогона ждёт, пока браузер освободится, и ловит все. Ошибка, которая то есть, то нет, — повод разобраться, а не отмахнуться.

Откуда они? Вот `add`:

```ts core/cart-store.ts
this.analytics().then((analytics) =>
  analytics.track('В корзину', game.title),
);
```

`this.analytics()` из главы 8 загружает модуль аналитики и потом просит у инжектора экземпляр `Analytics`. Загрузка — асинхронная. Тест тем временем кончился, стенд разобран, инжектор уничтожен. Модуль загрузился, `injectAsync` обращается к уничтоженному инжектору — `NG0205`, промис отклонён, и его никто не ловит.

Это не беда теста, а изъян магазина, который тест сделал видимым. Та же цепочка оборвётся в магазине, если модуль аналитики не загрузится — например, пропала сеть. Каждое «В корзину» оставит в консоли `ERROR` о необработанном промисе. А аналитика — не то, ради чего покупатель пришёл: её сбой не должен даже попадать в консоль как ошибка магазина.

Исправим в `CartStore`: отправка события — в одном методе, и её ошибки дальше не идут:

```ts core/cart-store.ts {1,4-10}
    this.track('В корзину', game.title);
  }

  // Событие — в аналитику. Аналитика не важнее покупки: модуль не загрузился или корзины
  // уже нет — событие пропадает, а ошибка не уходит дальше
  private track(event: string, details: string) {
    this.analytics()
      .then((analytics) => analytics.track(event, details))
      .catch(() => {});
  }
```

В `app.ts` та же запись — «Просмотр страницы». Тест `App` (его создаёт `ng new`) споткнулся бы о неё так же. Добавьте и там `.catch(() => {})` после `.then(…)`.

## Эксперименты

**Тесты зависят друг от друга.** Уберите `localStorage.clear()` из `beforeEach` и перенесите тест «сохраняет корзину в localStorage» в начало набора. Упали сразу три теста, которые идут после него: «новая корзина пуста» (`expected 1 to be +0`), «считает штуки и сумму» (`expected 4 to be 3`) и «доставка бесплатна от 5000 ₽». Корзина первого теста осталась в хранилище, и каждая новая корзина её прочитала. Тест, который проходит один, но падает после другого, — худший вид падения: искать причину приходится не там, где упало. Верните всё как было.

**Без `TestBed.tick()`.** Уберите `tick` из теста хранилища. Под сообщением `expected [] to deeply equal …` Vitest покажет разницу построчно: `- Expected` — чего ждали, `+ Received` — что получили. Обратите внимание на запись: для `toEqual` Vitest пишет «to deeply equal» — сравнение вглубь.

## Как в настоящем проекте

`ng generate service` создаёт рядом заготовку `x.spec.ts` с `TestBed.configureTestingModule({})`, `TestBed.inject(X)` и тестом `should be created` (`expect(service).toBeTruthy()`). Пустой `configureTestingModule({})` можно не писать: стенд с конфигурацией по умолчанию собирается и без него, как в нашем тесте.

::: deep Под капотом: почему computed сразу, а effect потом
`computed` — ленивый: его значение считается при чтении, если изменились источники (глава 3). Тест читает — значение актуально. `effect` — наоборот, «толкающий»: изменение сигнала только помечает эффект грязным и сообщает планировщику Angular. В приложении планировщик выполнит эффекты и проверит компоненты в ближайший кадр. В тесте синхронный код идёт без остановок, и планировщик не успевает. `TestBed.tick()` — это `ApplicationRef.tick()` стенда, та же работа, только синхронно и сейчас: корневые эффекты, проверка компонентов, функции после отрисовки. Раньше для эффектов был `TestBed.flushEffects()` — в Angular 22 он `@deprecated`: «use `TestBed.tick()` instead».
:::
