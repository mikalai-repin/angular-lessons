Оформление заказа — страница, где ошибка стоит дороже всего: заказ не ушёл, ушёл не тот или покупатель не понял, что случилось. Правил на ней много — с главы 13 они живут в схеме `checkoutSchema`, а отправку делает `Checkout`. Проверим и то и другое.

## Что изменилось в коде

- `checkout/checkout-schema.spec.ts` — набор `checkoutSchema`. В нём `validOrder()` — правильный заказ (имя, телефон, самовывоз) и `checkoutForm(order)` — форма по схеме без компонента. Один тест уже есть: «правильный заказ проходит».
- `checkout/checkout.spec.ts` — набор `Checkout`. В `beforeEach` — стенд с роутером и поддельным сервером, игра в корзине (без неё нечего оформлять) и страница оформления. Помощники: `type(селектор, текст)` — напечатать в поле (имя — `input[autocomplete="name"]`, телефон — `input[type="tel"]`, как в `checkout.html`), `submit()` — нажать «Оформить заказ» и дождаться отрисовки.

## Правила без компонента

В главе 13 мы вынесли правила формы в схему, чтобы их можно было читать — и проверять — без шаблона. Вот и пригодилось:

```ts checkout/checkout-schema.spec.ts
function checkoutForm(order: CheckoutData) {
  return TestBed.runInInjectionContext(() =>
    form(signal(order), checkoutSchema),
  );
}
```

`form()` внедряет `Injector` (глава 13), поэтому — в контексте внедрения стенда, как `PricePipe` в шаге 2. Дальше — всё, что вы знаете о полях: `f().valid()` — вся форма, `f.contacts.phone().errors()` — ошибки поля, массив `{ kind, message }`; `f.delivery.method().value.set('courier')` — поменять значение, как покупатель.

## Отправка и время

Тест страницы печатает в поля, нажимает «Оформить заказ», отвечает за сервер — и ждёт «Заказ №42 оформлен». И здесь `whenStable()` впервые не поможет. Отправку делает `placeOrder` — `async`-функция: дождалась ответа, записала номер заказа. Angular о ней не знает: это не отрисовка, не задача `PendingTasks` (тестовые запросы стабильность не держат, шаг 6), не `@defer`. Стенд «стабилен», а номер заказа ещё не записан.

Для такого случая в Vitest есть **`vi.waitFor(колбэк)`**: он вызывает колбэк снова и снова (по умолчанию — каждые 50 мс, не дольше секунды), пока тот не перестанет бросать ошибку:

```ts
request.flush({ id: 42 });
await vi.waitFor(() =>
  expect(page.querySelector('h1')?.textContent).toBe(
    'Заказ №42 оформлен',
  ),
);
```

Утверждение внутри — то же самое. `waitFor` только даёт ему время стать правдой.

::: task
**Схема** (`checkout-schema.spec.ts`), каждый тест портит правильный заказ в одном месте:

1. «без телефона и e-mail — „Укажите телефон или e-mail…“»: пустой телефон — форма не проходит, у поля e-mail ошибка вида `'contact'` (правило «Укажите телефон или e-mail…»).
2. «телефон — 11 цифр»: телефон `'+7 900 123'` — у поля телефона ошибка вида `'phone'`.
3. «курьеру нужен адрес»: выбрали курьера — у адреса ровно одна ошибка «Куда привезти заказ?».
4. «у открытки должен быть адресат»: открытка без `to` — форма не проходит, у поля `to` первой открытки ошибка `'required'`.

**Страница** (`checkout.spec.ts`):

5. «пустая форма не уходит на сервер»: нажали «Оформить заказ» с пустыми полями — запроса `/api/orders` нет (`server.expectNone(…)`), на странице — «Как к вам обращаться?».
6. «заказ оформлен — номер заказа, корзина пуста»: имя и телефон, «Оформить заказ» — ушёл `POST /api/orders` с игрой (`gameId: 4`, 1 шт.), контактами и суммой 3190; после ответа `{ id: 42 }` — «Заказ №42 оформлен», корзина пуста.
7. «на складе не хватило — сообщение сервера»: ответ 409 с `{ message: 'На складе только 0 шт.' }` — сообщение сервера на странице (`.error-message`).
:::

::: hint Подсказка 1: испортить заказ
`validOrder()` каждый раз возвращает новый объект — его можно менять до создания формы: `const order = validOrder(); order.contacts.phone = ''; const f = checkoutForm(order);`. Ошибка поля — `f.contacts.email().errors()[0]?.kind`. Для курьера удобнее менять уже созданную форму: `f.delivery.method().value.set('courier')` — правила `applyWhen` включатся, как у покупателя.
:::

::: hint Подсказка 2: открытки
Поле-массив перебирается, как массив (глава 13): первая открытка — `f.postcards[0]`, её адресат — `f.postcards[0].to`. Открытку добавьте в заказ до создания формы: `order.postcards = [{ to: '', text: 'С днём рождения!' }]`.
:::

::: hint Подсказка 3: что ушло на сервер
`request.request.body` — объект, который `Checkout` отправил. Целиком сравнивать его с `toEqual` неудобно: там адрес, открытки, комментарий, промокод. **`toMatchObject`** сравнивает только названные поля, в том числе вложенные: `expect(request.request.body).toMatchObject({ items: [{ gameId: 4, quantity: 1 }], contacts: { name: 'Аня', phone: '+7 900 123-45-67' }, total: 3190 })`.
:::

::: hint Подсказка 4: ответ 409 и время
Ответ с ошибкой — `flush(тело, { status: 409, statusText: 'Conflict' })`. Сообщение появится после того, как `placeOrder` разберёт ответ, — поэтому и здесь `await vi.waitFor(() => expect(…).toContain(…))`. Корзину после успешного заказа спросите у стенда: `TestBed.inject(CartStore).count()`.
:::

## Проверьте себя

Нажмите «Проверить»: проверка запустит тесты и посмотрит, что в наборе схемы не меньше пяти тестов, в наборе страницы — не меньше трёх, все проходят, а ошибок вне тестов нет. Качество тестов проверка не оценит — это ваша работа. Убедитесь сами, что тесты ловят ошибки:

- В `checkout-schema.ts` временно уберите правило `required` у адреса курьера — тест «курьеру нужен адрес» должен упасть. Верните.
- В `checkout.ts` временно уберите `this.cart.clear()` после заказа — должен упасть тест оформления. Верните.
- В `checkout.ts` замените сообщение 409 на своё (`message: 'Ошибка'`) — должен упасть тест 409. Верните.

Тест, который не падает, когда ломаешь то, что он проверяет, ничего не проверяет.

## Итоги главы

- **Тест** — код, который проверяет код: `describe` (набор), `it` (тест), `expect(…)` с матчерами (`toBe`, `toEqual`, `toContain`, `toMatchObject`, `toHaveBeenCalledWith`), для промисов — `rejects`. Раннер в Angular CLI 22 — Vitest, файлы `*.spec.ts` лежат рядом с кодом.
- **`TestBed`** — Angular для тестов: `configureTestingModule({ providers, imports })` — конфигурация стенда вместо `app.config.ts`, `inject` — сервис, `runInInjectionContext` — код с `inject()` внутри, `createComponent` — компонент. После каждого теста стенд разбирается. Конфигурация — до первого `inject`.
- **Сигналы** читаются в тестах сразу, **эффекты** — после `TestBed.tick()`.
- **Компонент**: фикстура, `componentRef.setInput`, `nativeElement`, щелчки DOM и `await fixture.whenStable()` после каждого действия. Тест читает то, что видит покупатель.
- **Подмена** — провайдер в `configureTestingModule`: `useValue` с шпионом `vi.fn()` или своими настройками. Подменяйте мешающее и постороннее, а не проверяемое.
- **HTTP**: `provideHttpClientTesting()` и `HttpTestingController` — `expectOne`, `flush`, `verify`. Тест играет за сервер, включая ошибки.
- **Маршруты**: `RouterTestingHarness` с настоящими `routes` — гарды, переадресации, ленивые части.
- **Время**: `whenStable` ждёт только то, о чём знает Angular; остальное — `vi.waitFor`.
- **Ошибки вне тестов** — повод искать изъян: тесты нашли его в аналитике корзины.

В последнем шаге главы — без кода — разберём, чем превью отличается от `ng test`, как CLI готовит стенд и почему в зонлесс-приложении нет `fakeAsync`. А в главе 17 соберём всё вместе в админке магазина — и для её таблиц и форм тесты понадобятся с первого дня.
