Страница редактирования сама отправляет `PUT`. Скоро запросы появятся у таблицы (удаление) и у формы новой игры. Соберём всё, что админка меняет на сервере, в одном сервисе — и заодно научим его помнить, что сделано за сеанс: на сводке будет журнал «Изменена игра „Ночной экспресс“».

## Что изменилось в коде

Новый файл `admin/admin-games.ts` — сервис `AdminGames`: метод `save(id, draft)` отправляет `PUT` и пишет запись в журнал, сигнал `changes` — сам журнал. Не хватает только декоратора.

## Где должен жить сервис

У журнала есть смысл только в админке. Покупателю он ни к чему, шапке магазина — тоже. Значит, сервис должен быть виден страницам раздела — и только им.

`@Service()` не подходит: он кладёт сервис в инжектор окружения `root`, и его может попросить любой компонент магазина. `providers` компонента (глава 8) — тоже: сервис создавался бы заново для каждой страницы, а нам нужен один журнал на сводку, таблицу и форму.

Третий вариант — **провайдеры маршрута**:

```ts admin/admin.routes.ts {4}
{
  path: '',
  component: AdminLayout,
  providers: [AdminGames],
  children: [ … ],
},
```

Для маршрута с `providers` роутер создаёт свой **инжектор окружения** — потомка того, в котором он сам. Его видят компоненты этого маршрута и всех его детей:

```
инжектор окружения root
│  AuthStore, CartStore, HttpClient…
│
├─ Header, Catalog, GamePage…
│
└─ инжектор маршрута admin/''
   │  AdminGames
   └─ AdminLayout
      ├─ AdminHome
      ├─ GamesTable
      └─ GameEdit
```

`GameEdit` просит `AdminGames` — поиск поднимается по элементам, доходит до инжекторов окружения и находит сервис в инжекторе маршрута. `Header` в этой ветке не живёт: его поиск идёт сразу в `root`, и `AdminGames` там нет.

А чтобы он там и не появился, у декоратора `autoProvided: false` — как у `ShopTitleStrategy` в главе 10:

```ts admin/admin-games.ts
@Service({ autoProvided: false })
export class AdminGames {
```

Класс — сервис: DI умеет его создавать и подставлять зависимости через `inject`. Но выдаёт его только тот инжектор, где он указан в `providers`.

## Журнал

```ts admin/admin-games.ts
private readonly changesState = signal<Change[]>([]);
readonly changes = this.changesState.asReadonly();

async save(id: number, draft: GameDraft) {
  const game = await firstValueFrom(
    this.http.put<Game>(`/api/games/${id}`, draft),
  );
  this.log(`Изменена игра «${game.title}»`);
  return game;
}
```

Закрытый записываемый сигнал и открытый только для чтения — как у корзины в главе 9. Название берём из ответа сервера: это игра, какой она стала.

::: task
1. Поставьте `AdminGames` декоратор `@Service({ autoProvided: false })`.
2. В `admin.routes.ts` добавьте маршруту макета `providers: [AdminGames]`.
3. В `GameEdit` замените `HttpClient` на `AdminGames` и сохраняйте через `admin.save(this.id(), this.draft())`.
4. На сводке (`AdminHome`) под списком — заголовок «Изменения за сеанс» и журнал `admin.changes()`: время (`date: 'HH:mm:ss'`) и текст; пустой журнал — «Пока ничего не меняли.».
:::

## Что получилось

Поменяйте цену «Ночного экспресса» и сохраните, затем откройте «Сводку»: «Изменения за сеанс» — время и «Изменена игра «Ночной экспресс»». Сходите в каталог магазина и вернитесь в админку: запись на месте. Журнал живёт в сервисе, а не на странице.

## Эксперименты

**Снаружи раздела сервиса нет.** Попросите `AdminGames` в шапке: `private readonly adminGames = inject(AdminGames);` в `Header`. Магазин не запустился, в консоли:

```
NG0201: No provider found for `AdminGames`. Source: Environment Injector.
```

Шапка ищет сервис в `root`, а он только в инжекторе маршрута. Не убирайте строку из шапки и замените декоратор на `@Service()`. Ошибки нет — и это хуже: у шапки теперь **свой** экземпляр из `root`, а у админки — свой из маршрута. Два журнала, и шапка никогда не увидит изменений. `autoProvided: false` превращает такую путаницу в понятную ошибку. Верните как было и уберите строку из шапки.

**Когда сервис создаётся.** Добавьте в `AdminGames` конструктор с `console.log('AdminGames: экземпляр создан')`. Откройте превью на главной, перейдите в админку: строка появилась после «Админка: модуль загружен» — инжектор маршрута создаёт сервис, когда его впервые попросили. Уйдите в каталог и вернитесь: второй строки нет. По умолчанию роутер не уничтожает инжектор маршрута, когда раздел закрыт: сервис живёт до конца работы приложения.

**Уборка инжекторов.** Добавьте в `provideRouter` в `app.config.ts` функцию `withAutoCleanupInjectors()` (импорт из `@angular/router`). Сохраните игру, уйдите в каталог и вернитесь: в консоли второй раз «экземпляр создан», журнал пуст. С этой функцией роутер после каждого перехода уничтожает инжекторы неактивных маршрутов, а с ними — их сервисы. Журналу админки это не подходит, поэтому верните как было и уберите конструктор.

::: deep Под капотом: инжектор маршрута
При распознавании адреса роутер для маршрута с `providers` вызывает `createEnvironmentInjector(route.providers, родитель)` и запоминает результат в самом объекте маршрута — поле `_injector` (функция `getOrCreateRouteInjectorIfNeeded` в `@angular/router`). Родитель — инжектор ближайшего маршрута выше, у которого он есть, а если таких нет — инжектор приложения. Компонентам маршрута и его детей роутер передаёт этот инжектор как инжектор окружения.

Уничтожить его может только `withAutoCleanupInjectors()` (`@publicApi 22.2`): после навигации роутер обходит карту маршрутов и для неактивных спрашивает у `RouteReuseStrategy` метод `shouldDestroyInjector` — стандартная стратегия отвечает `true`.
:::

::: legacy Вы встретите в старом коде: провайдеры ленивого модуля
До standalone-компонентов ленивый раздел был `NgModule` со своими `providers`: `loadChildren: () => import('./admin/admin.module').then((m) => m.AdminModule)`. У загруженного модуля был свой инжектор — это и был «инжектор раздела». Провайдеры маршрута делают то же без модуля.
:::
