В главе 12 мы завели кэш ответов на 10 секунд и честно предупредили: «изменения через `POST`/`PUT` должны очищать связанные ответы». Тогда магазин ничего не менял. Теперь меняет — и кэш начинает врать.

## Что изменилось в коде

В `ResponseCache` (`core/cache-interceptor.ts`) появился метод `clear()` — забыть все ответы. А `inject(ResponseCache)` в интерцепторе переехал в начало функции: кэш понадобится не только `GET`-запросам.

## Старая цена после сохранения

Откройте «Ночной экспресс» в админке, поставьте цену 2990 и сохраните. Сразу, в пределах 10 секунд, снова щёлкните его в таблице: в поле цены — **3190**. Откройте страницу игры в магазине: `/games/4` — тоже 3 190 ₽. Подождите 10 секунд и откройте снова: 2 990 ₽.

Посмотрите во вкладку «Сеть». После `PUT /api/games/4` повторное открытие игры не отправило ни одного запроса. Резолвер крошки и страница помечают запрос игры меткой `CACHE`, и кэш отдал им ответ, полученный **до** сохранения.

`PUT` прошёл мимо кэша: интерцептор пропускает не-`GET` запросы, ничего не трогая. Сервер изменил игру, а кэш об этом не узнал.

## Что забывать

Какие ответы устарели после `PUT /api/games/4`? Сама игра `/api/games/4`. Страницы каталога, где она есть, — с любым поиском и сортировкой. Подборки на главной. После `DELETE` — ещё и всё, где игра была. Интерцептор этого не знает: он видит адреса, а не смысл данных.

Поэтому правило — простое и надёжное: **любой успешный запрос, который меняет данные, очищает весь кэш.**

```ts core/cache-interceptor.ts {5-13}
export const cacheInterceptor: HttpInterceptorFn = (
  req,
  next,
) => {
  const cache = inject(ResponseCache);
  if (req.method !== 'GET') {
    return next(req).pipe(
      tap((event) => {
        if (event instanceof HttpResponse) {
          cache.clear();
        }
      }),
    );
  }
  if (!req.context.get(CACHE)) {
    return next(req);
  }
  // … дальше — как было
```

`next(req)` отправляет запрос дальше по цепочке, `tap` смотрит на события ответа, не меняя их. Очищаем на `HttpResponse` — когда сервер ответил успехом. Если сервер ответил ошибкой, `HttpClient` выдаёт её как ошибку потока, а не как `HttpResponse`: `PUT` с ответом `400` ничего не изменил, и кэш остаётся.

Цена простоты: кэш пустеет и после отзыва, заказа или входа. Это не страшно — кэш здесь лишь экономит повторный запрос. Хуже было бы показать старые данные.

::: task
В `cacheInterceptor` перед проверкой метки `CACHE`: запрос не `GET` — отправить дальше и после успешного ответа (`HttpResponse`) вызвать `cache.clear()`.
:::

## Что получилось

Повторите опыт: сохраните цену 2990 и сразу откройте игру снова. В поле — 2990, в магазине — 2 990 ₽. В «Сети» после `PUT` — один `GET /api/games/4`: его отправил резолвер крошки, кэш был пуст. Странице ответ достался уже из кэша — как и задумано в главе 12.

## Эксперимент

**Ошибка не очищает.** Введите цену 2990.5 и сохраните — сервер ответит `400`. Сразу откройте игру снова: в «Сети» нет `GET /api/games/4`, ответ из кэша. Сохранение не удалось, данные на сервере прежние — и кэш прав.

::: tip
Сбросить кэш целиком — самый грубый способ. В больших приложениях кэш делят по ключам («игры», «заказы») и после изменения сбрасывают только свой ключ. А ещё сервер может сам сказать, сколько хранить ответ, — заголовком `Cache-Control`; об этом мы говорили в главе 12.
:::
