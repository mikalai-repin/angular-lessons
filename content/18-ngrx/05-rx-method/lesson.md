Корзина хранит **снимки** игр: какой была цена и сколько было на складе, когда игру положили. Снимок живёт в `localStorage` днями, а за это время цена могла измениться, игра — закончиться или пропасть из каталога. Пока об этом узнаёт только сервер при оформлении заказа — ответом 409. Сделаем честнее: при каждом открытии корзины сверим её с сервером и обновим цены и остатки.

Это асинхронная работа внутри хранилища: запросы, ответы, ошибки. Посмотрим, как Signal Store делает её на RxJS.

## Что изменилось в коде

Ничего: код — решение прошлого шага.

## Что должна делать сверка

- для каждой игры в корзине — `GET /api/games/:id`, все запросы сразу;
- игра пропала (404) или закончилась — убрать позицию;
- иначе — свежий снимок игры, а количество — не больше остатка;
- пока идёт сверка — «Сверяем цены и остатки…», не удалась — сообщение и «Повторить»;
- корзину открыли снова, пока прошлая сверка не закончилась, — прошлую отменить: её ответ уже не нужен.

Последний пункт — то, ради чего в главе 12 появился `switchMap`. Промисом его не сделать: `async`-метод нельзя отменить. Значит, нужен метод на RxJS.

## `rxMethod`

**`rxMethod`** из `@ngrx/signals/rxjs-interop` превращает цепочку операторов RxJS в **метод**. Каждый вызов метода — новое значение на входе цепочки:

```ts
const log = rxMethod<number>(pipe(map((n) => n * 2), tap(console.log)));
log(1); // 2
log(2); // 4
```

Внутри — один поток на всё время жизни: `switchMap`, `exhaustMap`, `debounceTime` видят все вызовы и могут отменять, пропускать, ждать. Метод может принять и сигнал: тогда значение уходит в цепочку при каждом его изменении. Как `effect()`, `rxMethod` создают в контексте внедрения — например, в `withMethods`. Он отписывается сам, когда уничтожается его инжектор: у корзины — вместе с приложением.

Нашей сверке вход не нужен: `rxMethod<void>`, и вызов — `cart.refresh()`.

```ts core/cart-store.ts
withState<{ checkStatus: CheckStatus }>({ checkStatus: 'idle' }),
// …
withMethods((store, http = inject(HttpClient)) => ({
  refresh: rxMethod<void>(
    pipe(
      tap(() => patchState(store, { checkStatus: 'checking' })),
      switchMap(() => {
        const ids = store.ids();
        return forkJoin(ids.map((id) => loadGame(http, id))).pipe(
          tapResponse({
            next: (games) =>
              patchState(
                store,
                ...games.map((game, i) => refreshed(ids[i], game)),
                { checkStatus: 'idle' },
              ),
            error: () => patchState(store, { checkStatus: 'failed' }),
          }),
        );
      }),
    ),
  ),
})),
```

Разберём.

`withMethods((store, http = inject(HttpClient)) => …)` — зависимость прямо в параметрах: функция части выполняется в контексте внедрения, значение по умолчанию вычисляется в нём же. Так её показывает документация NgRx; можно и через `withProps`, как `_config`.

`checkStatus` — новое поле состояния: `'idle' | 'checking' | 'failed'`. Его читает страница корзины.

`switchMap` — новый вызов отменяет незаконченную сверку. `forkJoin` (глава 12) — все запросы сразу, ответ — массив, когда придут все. Порядок ответов — как у запросов, поэтому `ids[i]` — id игры, ответ которой `games[i]`. `ids` запоминаем до запросов: пока они идут, покупатель может убрать позицию.

`loadGame` и `refreshed` — обычные функции в конце файла. Первая превращает 404 в `null`, как на странице избранного. Вторая решает судьбу позиции:

```ts core/cart-store.ts
function refreshed(id: EntityId, game: Game | null) {
  return !game || game.inStock === 0
    ? removeEntity(id)
    : updateEntity<CartItem>(
        {
          id,
          changes: (item) => ({
            game,
            quantity: Math.min(item.quantity, game.inStock),
          }),
        },
        cartItems,
      );
}
```

Вне хранилища TypeScript не знает, какая у `updateEntity` сущность, поэтому `<CartItem>` указан явно. Все функции обновления уходят в **один** `patchState` — корзина меняется разом, вместе с `checkStatus`.

## `tapResponse`

`tapResponse` из `@ngrx/operators` — оператор для ответа сервера: `next` — что делать с ответом, `error` — с ошибкой, необязательный `finalize` — в любом случае в конце. Главное в нём — **ошибка не идёт дальше**: он ловит её и завершает внутренний поток. Почему это важно, покажет эксперимент.

constructor() {
  this.cart.refresh();

```html cart/cart-page/cart-page.html

  @case ('checking') {
    <p class="muted">Сверяем цены и остатки…</p>

  @case ('failed') {
    <p class="error-message">
      Не удалось сверить корзину с сервером.

    </p>
  }

```

1. В корзину: `type CheckStatus`, `withState` с `checkStatus: 'idle'` после `withStorage`, функции `loadGame` и `refreshed` в конце файла.

## Что получилось

Откройте корзину с играми: на мгновение — «Сверяем цены и остатки…», во вкладке «Сеть» — по запросу на игру. Чтобы увидеть сверку в деле, сделайте снимок устаревшим. Войдите администратором (`admin@example.com`, пароль `admin`), положите в корзину «Ночной экспресс», в админке найдите его поиском в таблице игр, поменяйте цену и сохраните. Вернитесь в корзину переходом по ссылке «В корзине»: новая цена. Не перезапускайте превью и не вводите адрес руками — учебный бэкенд при этом начнёт заново, со старыми ценами.

Мы проверили и другие случаи сценарием: подложили в `localStorage` позицию «7 штук по 7 ₽» для игры, которой на складе 3, и позицию с несуществующей игрой. После сверки — 3 штуки по настоящей цене, вторая позиция исчезла (сервер ответил 404).

## Эксперименты

**Повтор отменяет прошлую сверку.** Положите две игры, поставьте задержку 1500 мс во вкладке «Сеть». Откройте корзину, сразу щёлкните «Главная» и снова корзину. В «Сети» первые два запроса — «отменён», вторые — `200`. А если просто уйти из корзины, не возвращаясь, запросы дойдут до конца: `rxMethod` живёт в хранилище, а не на странице. Отменяет только следующий вызов — так работает `switchMap`.

**Без `tapResponse`.** Замените `tapResponse({ next: …, error: … })` на `tap({ next: … })` — без `error`. Включите ошибку 500 во вкладке «Сеть» и откройте корзину. «Сверяем цены и остатки…» висит, «Повторить» не появляется, в консоли — `ERROR` с `HttpErrorResponse`. Выключите ошибку, уйдите на главную и вернитесь в корзину: опять «Сверяем…», и **ни одного запроса** в «Сети».

Ошибка внутреннего потока пробилась наружу, через `switchMap`, в поток самого `rxMethod` — и завершила его. Поток один на всё время жизни хранилища, и мёртвым он останется до перезапуска. Поэтому ошибку ловят **внутри** `switchMap` — это и делает `tapResponse`. Верните как было.

::: tip Как в настоящем проекте
Три способа асинхронности в Signal Store:

- **`async`-метод** с `await firstValueFrom(…)` и `patchState` до и после — когда отмена и гонки не важны. Так делает документация NgRx в простых примерах;
- **`rxMethod`** — когда нужны операторы RxJS: отмена, задержка ввода, очередь, повтор;
- **`signalMethod`** из `@ngrx/signals` — то же без RxJS: принимает значение или сигнал и вызывает обычную функцию на каждое новое значение. Он меньше и проще, но отменять и ждать не умеет. Его попробуем в практикуме.

И помните про главу 11: если данные нужны одной странице, а не всему приложению, `httpResource` проще хранилища.
:::

::: deep Под капотом: `rxMethod`
`rxMethod(generator)` при создании заводит `Subject`, пропускает его через вашу цепочку и подписывается на результат — один раз. Подписку он отменяет, когда уничтожается инжектор, в котором создан. Вызов с обычным значением — `subject.next(значение)`. Вызов с сигналом создаёт `effect`, который на каждое новое значение сигнала делает `next`. Вызов с потоком — подписку, которая передаёт его значения в тот же `Subject`. Отсюда и поведение из эксперимента: ошибка завершает единственную подписку, и следующие `next` уходят в никуда.
:::
