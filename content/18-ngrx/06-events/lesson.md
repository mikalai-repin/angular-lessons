Что происходит, когда заказ оформлен? Сейчас — то, что написано в `Checkout.placeOrder`: страница сама очищает корзину (`this.cart.clear()`). Завтра добавится «обновить „Мои заказы“», послезавтра — «сообщить аналитике», «показать опрос». И каждый раз правка — в странице оформления: она должна знать всех, кого касается заказ, и звать каждого.

Есть другой способ, о котором мы говорили в главе 9: страница **сообщает, что произошло**, — «заказ оформлен», — а кого это касается, сами слушают и решают, что делать. Отправитель не знает получателей. В Signal Store для этого есть дополнение **events**.

## Что изменилось в коде

Новый файл `checkout/checkout-events.ts` — заготовка группы событий оформления заказа.

## Событие

**Событие** (event) — объект с типом и данными: `{ type: '[Checkout] orderPlaced', payload: { orderId: 42 } }`. Тип в квадратных скобках начинается с **источника** — где это произошло, — дальше идёт что. Так советует документация NgRx: по типу сразу видно, откуда событие.

События одного источника объявляют группой — `eventGroup`:

```ts checkout/checkout-events.ts
export const checkoutEvents = eventGroup({
  source: 'Checkout',
  events: {
    orderPlaced: type<{ orderId: number }>(),
  },
});
```

`checkoutEvents.orderPlaced` — **создатель события**: функция, которая из данных делает объект события, `checkoutEvents.orderPlaced({ orderId: 42 })`. Тип данных снова задаёт `type<…>()`. Событие без данных — `type<void>()`.

Имя события — в прошедшем времени: «заказ оформлен», а не «очистить корзину». Событие — это факт, а не команда. Что с ним делать, решают получатели: корзина — очиститься, аналитика — записать, а страница оформления об этом знать не должна.

## Отправить

```ts checkout/checkout.ts
private readonly dispatch = injectDispatch(checkoutEvents);

// в placeOrder, после ответа сервера:
this.orderId.set(order.id);
this.dispatch.orderPlaced({ orderId: order.id });
```

`injectDispatch(группа)` возвращает объект с методом на каждое событие группы: вызов создаёт событие и **отправляет** его. Внутри — сервис `Dispatcher` с методом `dispatch(событие)`; `injectDispatch` избавляет от его внедрения и вызова руками. Как и `inject`, он работает в контексте внедрения — в поле класса.

`this.cart.clear()` из `placeOrder` уходит. Корзина в `Checkout` остаётся: состав заказа берут из неё.

## Получить: редьюсер

Корзина должна стать пустой, когда пришло событие. Изменение состояния по событию описывает **`withReducer`**:

```ts core/cart-store.ts
withReducer(
  on(checkoutEvents.orderPlaced, () => [
    removeAllEntities(),
    { promo: null },
  ]),
),
```

`on(создатель события, функция)` — «на такое событие — такие изменения». Функция получает событие и текущее состояние и возвращает то же, что принимает `patchState`: часть состояния, функцию обновления или массив из них. **Редьюсер** (reducer) — общее имя для таких функций «состояние и событие → изменения». Слово придёт к нам ещё раз — в классическом Store.

## Получить: обработчик

Аналитике корзина сообщала «В корзину» из метода `add`. Теперь пусть сообщает и о заказе. Это не изменение состояния, а побочный эффект — для него есть **`withEventHandlers`**:

```ts core/cart-store.ts
withEventHandlers((store, events = inject(Events)) => ({
  trackOrder$: events
    .on(checkoutEvents.orderPlaced)
    .pipe(
      tap(({ payload }) =>
        store._track('Заказ оформлен', `№${payload.orderId}`),
      ),
    ),
})),
```

Сервис `Events` — поток всех отправленных событий. `events.on(создатель…)` — только события нужных типов, как поток RxJS. Функция части возвращает объект потоков-**обработчиков**: хранилище подпишется на них само при создании и отпишется при уничтожении.

`_track` — закрытый метод: чтобы обработчик мог его вызвать, в `withMethods` корзины функция `track` теперь возвращается под этим именем. Обработчик стоит после `withMethods` — иначе `_track` ему не виден.

## Кто первый

Редьюсеры и обработчики слушают разные потоки: редьюсеры — служебный `ReducerEvents`, обработчики — `Events`. `Dispatcher` отдаёт событие сначала первому, потом второму. Поэтому обработчик, получив событие, видит состояние **после** редьюсера: корзина уже пуста.

```
Checkout
   │ dispatch(orderPlaced)
   ▼
Dispatcher
   ├─▶ ReducerEvents ─▶ withReducer
   │                    корзина пуста
   └─▶ Events ────────▶ withEventHandlers
                        аналитика
```
::: task
1. В `checkout/checkout-events.ts` добавьте событие `orderPlaced` с данными `{ orderId: number }`.
2. В `Checkout` — поле `dispatch = injectDispatch(checkoutEvents)`; в `placeOrder` вместо `this.cart.clear()` — `this.dispatch.orderPlaced({ orderId: order.id })`.
3. В корзине: в `withMethods` верните `_track: track`; перед `withHooks` — `withReducer` с `on(checkoutEvents.orderPlaced, …)` и `withEventHandlers` с `trackOrder$`.
:::

## Что получилось

Положите игру в корзину и оформите заказ. «Заказ №1 оформлен», в шапке «В корзине: 0», в консоли:

```
Аналитика: Заказ оформлен — №1
Корзина: пусто
```

Страница оформления больше не знает, что корзину надо очищать. Тест оформления из главы 16 («заказ оформлен — номер заказа, корзина пуста») это подтверждает: мы прогнали его — проходит, а в его выводе — «Аналитика: Заказ оформлен — №42».

## Эксперименты

**Журнал событий.** Подпишитесь на все события в `App` — в начале конструктора:

```ts app.ts
inject(Events)
  .on()
  .subscribe((event) =>
    console.log('Событие:', event.type, JSON.stringify(event.payload)),
  );
```

`on()` без аргументов — все события. Оформите заказ: в консоли `Событие: [Checkout] orderPlaced {"orderId":1}`. Это третий получатель, о котором ни корзина, ни оформление не знают. Так устроены инструменты отладки: им достаточно слушать поток событий. Уберите подписку.

**Типы данных.** Отправьте номер без объекта: `this.dispatch.orderPlaced(order.id)`. TypeScript:

```
Argument of type 'number' is not assignable to parameter of type '{ orderId: number; }'.
```

Создатель события знает тип данных, который мы описали в группе. Верните объект.

::: tip Как в настоящем проекте
События — для связей **между** частями приложения: заказ оформлен, пользователь вышел, данные устарели. Документация NgRx прямо говорит: обычного Signal Store с методами хватает в большинстве случаев, а события хороши там, где хранилища должны согласовываться друг с другом или нужна развязка отправителя и получателей. Если корзину очищает только оформление, `cart.clear()` проще и понятнее. Ещё у событий есть **области** (scope): `provideDispatcher()` в `providers` компонента создаёт свои `Dispatcher` и `Events` — события, отправленные внутри, не выходят наружу, если не отправить их с `{ scope: 'parent' }` или `{ scope: 'global' }`.
:::

::: deep Под капотом: события — это потоки
`Events` и `ReducerEvents` — сервисы с `Subject` внутри, `on(...)` — `filter` по типу. `Dispatcher.dispatch` делает `next` в `ReducerEvents` сразу, а в `Events` — через `queueScheduler` RxJS: если событие отправлено из обработчика другого события, оно подождёт, пока тот закончит. `withReducer` — это `withEventHandlers`, подписанный на `ReducerEvents`, где каждый обработчик вызывает `patchState`. А если в момент отправки хранилища ещё нет, оно события не получит: потоки не хранят прошлых значений. Корзину создаёт шапка задолго до заказа, поэтому для нас это не проблема.
:::
