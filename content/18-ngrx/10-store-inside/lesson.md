Мы пользовались Signal Store девять шагов, и почти всё в нём казалось знакомым: сигналы, `computed`, `effect`, `linkedSignal`, DI. Это не совпадение. Заглянем в исходники `@ngrx/signals` и `@ngrx/store` 22.0.1 и посмотрим, из чего они сделаны. Кода в шаге нет — только эксперимент.

## Класс, который собирается в конструкторе

`signalStore(настройки, ...части)` объявляет внутри себя класс `SignalStore` с декоратором `@Injectable({ providedIn })` и возвращает его. Отсюда имя в ошибке `NG0201` из шага 1 и то, что хранилище выдаёт DI, как любой сервис.

Всё интересное — в конструкторе. Он берёт пустую **заготовку** хранилища:

```
{ [STATE_SOURCE]: {}, stateSignals: {},
  props: {}, methods: {}, hooks: {} }
```

и пропускает её через части по очереди: каждая часть — функция «заготовка → новая заготовка».

- `withState({ ids: [] })` кладёт в `STATE_SOURCE` по `signal` на каждое поле, а в `stateSignals` — сигналы для чтения;
- `withComputed` и `withProps` дописывают `props`: функции из `withComputed` оборачиваются в `computed`;
- `withMethods` дописывает `methods`;
- `withHooks` склеивает `onInit` с уже имеющимися: хуки выполнятся в порядке частей;
- `signalStoreFeature` — просто несколько частей, применённых подряд.

Каждая часть получает заготовку, собранную частями выше, — поэтому видит только их. Когда части кончились, конструктор копирует все члены в экземпляр и вызывает `onInit`. Конструктор работает в контексте внедрения — поэтому `inject`, `effect`, `rxMethod` в частях работают.

## Состояние — это сигналы по полям

Состояния как одного объекта в Signal Store нет. Есть **отдельный `signal` на каждое поле** — у корзины это `entityMap`, `ids`, `checkStatus`, `promo` (последнее — `linkedSignal` из `withLinkedState`). Они лежат в свойстве с символом `STATE_SOURCE`.

`patchState` собирает новое состояние из всех переданных обновлений, сравнивает **каждое поле** со старым через `!==` и вызывает `set` только у изменившихся. Поэтому в шаге 3 `ids` не сообщил об изменении количества: `updateEntity` поменял только `entityMap`, и в новом состоянии остался прежний массив `ids`. После записи `patchState` вызывает функции `watchState` — синхронно, сразу.

`getState` идёт в обратную сторону: читает сигналы всех полей и собирает обычный объект. Внутри `effect` или `computed` это чтение — зависимость от **всех** полей.

Поля-объекты становятся **`DeepSignal`**: у сигнала есть свойства-сигналы для вложенных полей. Если бы состояние было `{ filter: { query: '', order: 'asc' } }`, можно было бы прочитать `store.filter.query()`. Внутри — `Proxy`, который при первом обращении создаёт `computed(() => filter().query)`.

## Защита — это типы

**Эксперимент.** Добавьте в `Header` конструктор:

```ts layout/header/header.ts
constructor() {
  console.log('Члены:', Reflect.ownKeys(this.cart).map(String).join(', '));
  console.log('Состояние:', Object.keys(getState(this.cart)).join(', '));
  patchState(this.cart as never, { promo: { code: 'ВЗЛОМ', percent: 99 } });
  console.log('Промокод:', this.cart.promo()?.code);
}
```

(`getState` и `patchState` — из `@ngrx/signals`.) В консоли:

```
Члены: entityMap, ids, checkStatus, promo, entities, _config, _analytics, subtotal, …, _track, add, …, refresh, Symbol(STATE_SOURCE)
Состояние: entityMap, ids, checkStatus, promo
Промокод: ВЗЛОМ
```

Три вывода:

- закрытые `_config`, `_analytics`, `_track` лежат в экземпляре, как и всё остальное, — их прячет только тип;
- состояние — четыре поля, всё остальное — производные и методы;
- `patchState` снаружи сработал. Запрет из шага 1 — заслуга TypeScript: снаружи тип говорит «сигналы только для чтения», а внутри — те же самые записываемые сигналы. `as never` обманул проверку типов, и JavaScript ничего не заметил.

Это не дыра, а решение NgRx: защита ничего не стоит во время выполнения, а от случайных ошибок спасает. В тестах, где снаружи нужно поставить хранилище в нужное состояние, для этого есть честный способ — `unprotected(store)` из `@ngrx/signals/testing`. Уберите конструктор.

## Сравните с главой 9

Корзина главы 9 — класс с закрытым `signal`, `asReadonly()`, `computed`, `linkedSignal` и `effect` в конструкторе. Корзина этой главы — те же сигналы, только разложенные по частям, которые собирает библиотека. Ничего нового Angular для Signal Store не делает: обнаружение изменений, шаблоны, `effect` работают с его сигналами так же, как с нашими. Signal Store — это **договорённость, оформленная кодом**: где состояние, где производные, где меняют, плюс готовые части для частых задач.

## Классический Store внутри

Классический Store устроен по-другому — вокруг потоков RxJS:

- всё состояние — **один объект** в `BehaviorSubject` (класс `State`);
- действия — поток `ActionsSubject`. На каждое действие Store вызывает общий редьюсер (редьюсеры всех частей, обёрнутые мета-редьюсерами) и кладёт результат в `State`;
- эффекты слушают поток действий уже после редьюсеров и отправляют свои действия обратно;
- `selectSignal(селектор)` — это `computed(() => селектор(state()))`, где `state` — то же состояние, превращённое в сигнал через `toSignal`;
- при разработке Store замораживает состояние и действия (`Object.freeze`) — так в шаге 7 и поймалось изменение на месте.

Один объект и один поток действий дают то, ради чего классический Store выбирают: каждое изменение — запись «действие → состояние», которую можно записать, показать и воспроизвести.

## Когда библиотека не нужна

Теперь, когда видно, что внутри, вопрос главы 9 решается спокойнее.

**Сервиса на сигналах достаточно**, если хранилищ немного, правила помещаются в методы, а команда пишет их одинаково. Signal Store не делает ничего, чего не сделал бы ваш класс: он добавляет договорённость и готовые части.

**Signal Store стоит взять**, когда хранилищ много и их хочется писать по одним правилам, когда повторяются одни и те же задачи (коллекции, состояние загрузки, сохранение) и их удобно оформить расширениями, когда нужна асинхронность на RxJS.

**Классический Store** — когда важен полный журнал изменений и отладка «действие за действием», когда много частей приложения реагируют на одни и те же события и когда проект уже на нём. За это платят количеством кода: действие, редьюсер, селектор и эффект там, где у Signal Store — один метод.

И правило, которое не зависит от библиотеки: данные сервера — ресурсам (`httpResource`), фильтры и страницы — адресу, а хранилищу — то, что создаёт сам пользователь.
