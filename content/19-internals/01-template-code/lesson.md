«Ход конём» готов: каталог, корзина, оформление заказа, вход, админка, NgRx. Начинается последняя часть курса — **«Глубже»**. В ней мы перенесём магазин в настоящий проект Angular CLI (глава 20) и прочитаем код большого приложения (глава 21). А сначала посмотрим, как Angular устроен изнутри.

Всю дорогу мы опирались на правила: «шаблон — это код», «сигнал помечает свой шаблон», «OnPush пропускает компонент». В этой главе увидим механизм за каждым из них:

- какой JavaScript компилятор строит из шаблонов — в новой вкладке превью **«Шаблон»**;
- где живут компоненты во время работы: **представления** `LView` и `TView` — во вкладке **«Дерево»** и в журнале по Alt + щелчку;
- обнаружение изменений изнутри: флаги представлений, планировщик, два режима обхода дерева, причина каждой проверки;
- **zone.js** — как Angular работал раньше: переведём на него магазин и сравним;
- сигналы, собранные из **примитивов** Angular, — версии, эпохи, «грязные» узлы;
- что делает **AOT-компилятор** и почему настоящие приложения собирают только так;
- практикум: найти в магазине лишние проверки и убрать их.

Код магазина в этой главе почти не меняется: появятся только помощники для исследования в папке `debug/`. Всё, что мы будем трогать, — **внутреннее API** Angular (буква `ɵ` в именах). Оно меняется между версиями без предупреждения. Факты главы проверены на Angular 22.2.1, в своём коде на них не опирайтесь.

## Вкладка «Шаблон»

В главе 1 мы печатали функцию шаблона `App` через `console.log`, в главе 2 — читали её блок обновления. Теперь у превью есть вкладка для этого. Под приложением рядом с «Консолью» и «Сетью» появились **«Шаблон»** и **«Дерево»**.

Вкладка «Шаблон» показывает код, который JIT-компилятор сгенерировал за этот запуск для **ваших** классов: компонентов, директив, пайпов и сервисов. Сотни классов самого Angular в список не попадают. Класс компилируется, когда он понадобился впервые. Поэтому компоненты ленивых маршрутов (страница игры, админка) появятся в списке, когда вы их откроете. Код отформатирован, кнопка ▴ справа от вкладок разворачивает панель повыше.

## Что внутри

Код — тот же, что AOT-компилятор записал бы в собранный файл `game-card.js` (в главе 1 мы сравнили их по функции шаблона `App`). Отличаются только имена: JIT передаёт функции Angular в сгенерированный код как аргументы и называет их `jit___elementStart_4`, а AOT импортирует как `i0.ɵɵelementStart`. Ниже мы пишем их короче — `elementStart`.

Сокращённо файл выглядит так:

```js
var _c0 = ['cover'];
var _c1 = [[['', 'sticker', '']]];
var _c2 = ['[sticker]'];
var _c3 = (a0) => ['/games', a0];
function GameCard_Conditional_0_Template(rf, ctx) { … }
function GameCard_Conditional_1_Template(rf, ctx) { … }
function GameCard_Case_3_Template(rf, ctx) { … }
// … ещё десять функций
var $def = defineComponent({
  type: GameCard,
  selectors: [['app-game-card']],
  viewQuery: function GameCard_Query(rf, ctx) { … },
  hostAttrs: ['role', 'article'],
  hostVars: 2,
  hostBindings: function GameCard_HostBindings(rf, ctx) { … },
  inputs: { game: [1, 'game'], priority: [1, 'priority'] },
  ngContentSelectors: _c2,
  decls: 36,
  vars: 28,
  consts: [ … ],
  template: function GameCard_Template(rf, ctx) { … },
  styles: [ … ],
});
```

Каждая часть декоратора `@Component` стала полем определения:

- `selectors` — селектор, уже разобранный на части (глава 7);
- `viewQuery` — запрос `viewChild('cover')`, а `_c0` — то, что он ищет: локальное имя `cover`;
- `hostAttrs`, `hostVars` и `hostBindings` — поле `host` (глава 5): статический атрибут `role` и привязка класса `sold-out`;
- `inputs` — входы. `1` — флаг «сигнальный вход» (`InputFlags.SignalBased` в исходниках);
- `ngContentSelectors` и `_c1` — слот `<ng-content select="[sticker]">`: селектор как написан и разобранный;
- `decls: 36` и `vars: 28` — сколько ячеек нужно под узлы шаблона и под значения привязок. В следующем шаге мы увидим эти ячейки в живом массиве;
- `consts` — атрибуты элементов: `[1, 'title-link', 3, 'routerLink']` — класс `title-link` (`1` — «дальше классы») и привязка `routerLink` (`3` — «дальше имена привязок»: по ним сопоставляются директивы).

Определение кладётся в статическое поле `GameCard.ɵcmp`. Ниже во вкладке — вторая часть, `ɵfac`, **фабрика**. Это функция, которая создаёт экземпляр: `new GameCard()`. Все `inject()` в полях карточки выполняются внутри этого `new` (глава 8).

## Одна функция на каждый блок

Над определением — тринадцать функций с именами вроде `GameCard_Conditional_27_Template`. Это **встроенные шаблоны**: тело каждой ветки `@if`, `@else`, `@case` компилятор вынес в отдельную функцию шаблона со своими блоками создания и обновления. Число в имени — номер узла, на месте которого блок стоит в шаблоне карточки.

В блоке создания карточки на месте `@if (priority()) … @else …` нет ни одного `<img>`. Есть только объявление мест:

```js
conditionalCreate(0, GameCard_Conditional_0_Template, 2, 2, 'img', 1)
                 (1, GameCard_Conditional_1_Template, 2, 2, 'img', 2);
```

Узлы 0 и 1 — два места для веток. Для каждого записаны функция шаблона, сколько у неё узлов и привязок (`2, 2`) и номер атрибутов в `consts`. Создаёт ветку блок обновления:

```js
conditional(ctx.priority() ? 0 : 1);
var category_r2 = ctx.game().category;
advance(3);
conditional((tmp_2_0 = category_r2) === 'family' ? 3
  : tmp_2_0 === 'strategy' ? 4 : /* … */ tmp_2_0 === 'kids' ? 7 : -1);
```

Весь `@if … @else` превратился в одно выражение, которое выбирает **номер места**: `0`, `1` или `-1` («ничего»). `conditional` сравнивает его с номером из прошлой проверки. Совпал — не делает ничего. Не совпал — уничтожает прежнюю ветку вместе с её DOM и создаёт новую по функции шаблона. Вот почему `@if` пересоздаёт элементы, а `[hidden]` — нет (глава 4). `@switch` стал цепочкой сравнений через временную переменную `tmp_2_0`, а `@let category` — обычной переменной `category_r2`.

## Свой контекст у встроенного шаблона

Откройте функцию ветки «Все N шт. в корзине»:

```js
function GameCard_Conditional_27_Template(rf, ctx) {
  if (rf & 1) {
    elementStart(0, 'p', 12);
    text(1);
    elementEnd();
  }
  if (rf & 2) {
    var ctx_r0 = nextContext();
    advance();
    textInterpolate1(' Все ', ctx_r0.game().inStock, ' шт. в корзине ');
  }
}
```

Номера узлов здесь снова с нуля: у встроенного шаблона свой массив ячеек. И `ctx` у него свой — **контекст встроенного представления**, а не карточка. Чтобы добраться до полей карточки, код берёт контекст на уровень выше: `nextContext()`. Посмотрите и на ветку цены со скидкой, `GameCard_Conditional_25_Template`. В ней `@if (game().oldPrice; as oldPrice)` превратился в `pipeBind1(2, 1, ctx)`: контекст этой ветки — само значение `oldPrice`.

## Массив, который не создаётся заново

Привязка `[routerLink]="['/games', game().id]"` в блоке обновления выглядит так:

```js
property('routerLink', pureFunction1(26, _c3, ctx.game().id));
```

Если бы компилятор оставил литерал массива как есть, каждая проверка карточки создавала бы новый массив. `property` сравнивает значения через `===`: новый массив всегда «другой», и `RouterLink` получал бы новый вход при каждой проверке. Поэтому литерал вынесен в функцию `_c3`, а `pureFunction1` запоминает аргумент и результат в ячейках привязок (смещения 26 и 27). Пока `id` прежний, возвращается тот же массив.

**Эксперимент.** Замените привязку строкой: `[routerLink]="'/games/' + game().id"`. Во вкладке «Шаблон» — `property('routerLink', '/games/' + ctx.game().id)`, функция `_c3` исчезла, а `vars` стало 26: две ячейки памяти больше не нужны. Строки сравниваются по значению, запоминать нечего. Верните массив.

## `domElementStart` и `elementStart`

У карточки элементы создаёт `elementStart`, обработчики — `listener`. Выберите теперь `Rating`: в строке звезды — `domElementStart` и `domListener`. Чем они отличаются?

`elementStart` при первом создании шаблона сверяет элемент с селекторами всех директив из `imports` и создаёт экземпляры подошедших (глава 7). На `<a>` карточки так появляется `RouterLink`, на `<app-rating>` — `Rating` и `Tooltip`. У `Rating` в `imports` ничего нет: сопоставлять не с чем. Поэтому компилятор выбрал режим «только DOM», `DomOnly`. Его инструкции создают элементы и слушатели и не тратят время на директивы.

**Эксперимент.** Добавьте в `shared/rating/rating.ts` пайп, которым шаблон не пользуется: `imports: [PricePipe]` (импорт — из `'../price-pipe'`). Во вкладке «Шаблон» у `Rating` снова `elementStart` и `listener`: JIT выбирает `DomOnly`, только когда `imports` пуст. AOT решает точнее. Мы собрали тот же код `ngc`: у `Rating` остались `domElementStart` и `domListener` — пайпы не в счёт, учитываются только директивы, которые шаблон действительно использует. Вдобавок `ngc` предупредил `NG8113: All imports are unused`. Уберите `PricePipe`.

## Как в настоящем проекте

В проекте Angular CLI этот код лежит в собранных файлах. Мы собрали магазин командой `ng build --configuration development` (сборка без оптимизации): в `dist/` нашлась та же `function GameCard_Template(rf, ctx)` с теми же номерами и `consts`, только инструкции записаны как `ɵɵelementStart(2, "span", 3)` — сборщик записал букву `ɵ` её кодом. В обычной сборке код ещё и сжат: имена укорочены. Чем ещё сборка отличается от превью — в шаге «JIT и AOT» этой главы: AOT строит этот код при сборке, и сам компилятор в приложение не попадает.

В следующем шаге посмотрим, что получается, когда функция шаблона выполняется: куда она складывает узлы и значения привязок.
