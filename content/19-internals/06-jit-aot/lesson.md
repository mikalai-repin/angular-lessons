Всё, что мы видели в этой главе, превью получает от **JIT-компилятора**: он работает в браузере и строит код шаблона при первом обращении к `ɵcmp`. Настоящие приложения собирают иначе: **AOT-компилятор** делает ту же работу при сборке. В главе 1 мы сравнили их по одной функции шаблона — она совпала инструкция в инструкцию. Но AOT делает и то, чего JIT не умеет. В этом шаге кода нет: разберём, что происходит при `ng build`, и посчитаем, сколько это стоит. Цифры мы получили, собрав магазин в настоящем проекте Angular CLI 22.2.1.

## Что делает ngtsc

AOT-компилятор Angular называется **ngtsc**. Это надстройка над компилятором TypeScript: его запускают команда `ngc` и сборщик Angular CLI. Работает он в четыре этапа:

```
ngtsc
1 анализ    декораторы → метаданные:
            селектор, шаблон, входы
2 связи     imports → какие директивы
            и пайпы в каждом шаблоне
3 типы      шаблоны → TypeScript,
            проверка вместе с кодом
4 генерация ɵcmp, ɵfac… в .js,
            декораторы удаляются
```

Этап 4 — то, что мы видели во вкладке «Шаблон». Посмотрим на этапы 2 и 3.

## Связи — при сборке

Мы собрали `GameCard` компилятором `ngc`. В определении появилось поле, которого нет во вкладке «Шаблон»:

```js
dependencies: [NgOptimizedImage, Rating, RouterLink, Tooltip,
  DecimalPipe, DurationPipe, PlayersPipe, PricePipe],
```

Это `imports` карточки, уже разобранные: какие классы — директивы, какие — пайпы. AOT находит их по исходникам, при сборке. JIT делает то же в браузере, читая метаданные декоратора `@Component`. Поэтому в превью декораторы остаются в коде, а в сборке AOT их нет. Компилятору нужен **только** код самого компонента и его `imports` — это называют **локальностью** компиляции. Поэтому библиотеки можно компилировать заранее: пакеты Angular поставляются частично скомпилированными (в `@angular/router` — вызовы `ɵɵngDeclareComponent`), и сборщик проекта доводит их до готовых определений.

## Типы — в шаблонах

На этапе 3 ngtsc переводит каждый шаблон в TypeScript-функцию — **блок проверки типов** (type-check block, TCB) — и проверяет его вместе с остальным кодом. Мы получили такой блок для `Rating` через API компилятора (сокращено, без служебных комментариев с позициями в шаблоне):

```ts
function _tcb1(this: i0.Rating) {
  for (const _t1 of this.stars!) {
    var _t8 = document.createElement('span');
    _t1 <= this.value();
    _t1 - 0.5 <= this.value() && this.value() < _t1;
    _t8.addEventListener('click', ($event): any => {
      this.select(_t1, $event);
    });
  }
  // … блок для host: role, aria-label, слушатели клавиш
}
```

`@for` стал `for…of`, привязки класса — выражениями, `(click)` — слушателем с типизированным `$event`. Этот код никогда не выполняется. Он нужен только TypeScript, а позиции в комментариях позволяют вернуть ошибку в нужное место шаблона.

**Эксперимент.** Сделайте опечатку в `game-card.html`: `{{ game().titel }}`. В превью ошибок нет — у всех карточек просто пустые заголовки: `undefined` в интерполяции — пустая строка (глава 2). Тот же шаблон в `ngc`:

```
src/shared/game-card/game-card.html:49:15 - error TS2551: Property 'titel' does not exist on type 'Game'. Did you mean 'title'?

49     {{ game().titel }}
                 ~~~~~
  Error occurs in the template of component GameCard.
```

Отсюда все различия JIT и AOT, которые мы отмечали по курсу: `@let` до объявления (глава 2), `@default never` (глава 4), вход без `()` (глава 3) — их видит только проверка типов. В превью шаблон проверяет лишь сам JIT-компилятор при разборе (`@for` без `track`) и рантайм (`NG0303`, `NG0304`). Исправьте опечатку.

## Сборка без компилятора

Раз код шаблонов готов при сборке, компилятор Angular в приложение не попадает. В превью он есть: `@angular/compiler` — 1,2 МБ, 226 КБ в gzip, его загружает каждый запуск. Мы собрали магазин обоими способами:

| Сборка | Начальные файлы | При передаче |
|---|---|---|
| `ng build` (AOT) | 515,57 kB | 142,04 kB |
| `ng build --aot=false` (JIT) | 1,33 MB | 321,49 kB |

Вторая сборка даже не завершилась: бюджет проекта по умолчанию — ошибка при 1 MB. Компилятор оказался в файле `polyfills` (512,41 kB): так в исходниках сборщика — «Angular JIT mode requires the runtime compiler». И чанка `game-reviews` в ней нет: JIT не выносит зависимости `@defer` в отдельный файл (глава 15).

Сам код рантайма тоже выигрывает от AOT. Каждая инструкция — отдельная экспортируемая функция (`ɵɵelementStart`, `ɵɵconditional`), и сгенерированный код импортирует только нужные ему. Что не импортировано — например, инструкции `i18n` в приложении без перевода, — сборщик может выбросить (**tree-shaking**): приложение платит только за то, что использует.

## Режим разработки

Наконец, превью всегда работает в **режиме разработки**: `ngDevMode` включён, есть глобальный `ng`, профайлер, повторная проверка `checkNoChanges`, подробные тексты ошибок. Все наши журналы в этой главе на этом и держались. `ng build` по умолчанию собирает **режим продакшена**: проверки и тексты режима разработки вырезаются при сборке, текст ошибки — только код вида `NG0201`, без пояснений и ссылки. Так что поведение приложения у пользователя — это поведение без журналов, без повторной проверки и без `ng.*`.

## Как в настоящем проекте

В следующей главе вы создадите проект Angular CLI и перенесёте в него магазин. Все различия из этого шага там станут видны: ошибки шаблонов — при сборке, размеры — в отчёте `ng build`, `@defer` — отдельными чанками. А проверку типов шаблонов можно сделать строже опцией `strictTemplates`.

Что запомнить:

- AOT (ngtsc) не только строит код шаблонов, но и связывает `imports` и проверяет шаблоны как TypeScript;
- JIT в превью проверяет шаблоны только при разборе и во время выполнения: опечатки в именах видны лишь как пустые места;
- сборка AOT не содержит компилятора и в несколько раз меньше; инструкции, которые шаблоны не используют, выбрасываются.
