Документ для того, кто пишет курс: человека или модели в новом чате. Здесь описан **процесс** написания главы, обязательные проверки и ловушки. Процесс перенесён из курса PixiJS (`../pixi-js/docs/authoring-process.md`), где по нему написаны 11 глав и найдено несколько десятков ошибок в черновиках. Прочитайте этот документ целиком перед началом работы вместе с `CLAUDE.md`, `docs/writing-guide.md` и `docs/modern-angular.md`.

# Процесс написания главы

## 0. Подготовка

```bash
npm install
npm run dev           # dev-сервер на http://localhost:5180 — нужен для всех проверок
node tools/e2e/checks/platform.mjs   # платформа в порядке? должно быть «Всё прошло»
```

Прочитайте:

- строки главы в `docs/course-plan.md` — план шагов (ориентир, а не закон);
- что глава добавляет в магазин — `docs/project-app.md`;
- **последний шаг предыдущей главы** целиком (`content/<глава>/<последний шаг>/solution/*`) — стартовая точка новой главы;
- раздел «Проверить при написании…» в `docs/modern-angular.md` — пункты, относящиеся к главе.

## 1. Сверка API до написания кода

Никаких утверждений об API по памяти. В интернете и в памяти модели много Angular 2–17. Перед главой выпишите все API, которые она вводит, и проверьте каждое:

```bash
T=node_modules/@angular/core/types        # типы: core.d.ts и чанки _*-chunk.d.ts
F=node_modules/@angular/core/fesm2022     # код — для поведения и значений по умолчанию
# экспорты собраны списками `export { … }`: искать «declare function X», а не «export declare function X»
python3 -c "…"                            # для поиска удобнее Python + re, чем grep в zsh
```

Что проверять:

- сигнатуры и названия параметров;
- **стабильность**: теги `@publicApi <версия>`, `@experimental`, `@developerPreview`, `@deprecated` в JSDoc;
- **значения по умолчанию** — в v22 многое поменялось (OnPush, зонлесс, standalone);
- **поведение** — читать реализацию в `fesm2022`, а не только комментарии;
- **поведение в JIT** — если API связан с компилятором (`@defer`, сигнальные входы, `host`, `templateUrl`), проверить запуском в превью, а не только по документации.

Новые проверенные факты записывайте в `docs/modern-angular.md`.

## 2. Код шагов

**Шаг хранит только изменения** — правила цепочки (`startFrom`, `base`/`baseHash`, `removedIn…`) описаны в `lesson-format.md`. Код главы, пока она пишется, генерирует Python-скрипт `tools/authoring/chNN-gen.py` (образец — `ch16-gen.py`): общие куски — строковые константы, шаги — **полные снимки** кода. Полный код прошлой главы он читает через `step_dir(путь)` и правит помощниками `rep` (замена, которая обязана найти якорь) и `cut` из `tools/authoring/steps.py` — код прошлой главы не перенабирается. Запись — только через `write_steps(ROOT, steps, base='09-app-state/05-practice')`: он форматирует снимки, сам вычисляет, что изменилось, пишет только это, ставит `base`/`baseHash` первому шагу и подсказывает, какие `removedIn…` нужны во frontmatter. Целиком посмотреть шаг — `npm run step <…/шаг/solution>`.

Когда глава готова, источник правды — `content/`, правки готовых глав — прямо в нём. Генераторы глав 1–15 удалены (они есть в истории git: главы 1–9 — последний раз в коммите `6624d67`, главы 10–15 — до коммита следующей главы); `ch16-gen.py` оставлен образцом для следующей главы (генератор главы 15 — в истории git до коммита главы 16): снимки шагов строятся цепочкой правок `edit(снимок, файл, (старое, новое), …)` поверх предыдущего, новые файлы — `put(снимок, **{'путь': код})`, удалённые — `drop(снимок, 'путь')`, заготовки — строками с `// TODO`. `python3 tools/authoring/chNN-gen.py dump <папка>` пишет полные отформатированные снимки шагов (`<папка>/<шаг>/<start|solution>`) — их сразу можно гонять `run-dir.mjs`/`exp.mjs`, не записывая главу в `content/`.

Правила:

- первый шаг главы — `startFrom: custom`, его старт — очищенное решение последнего шага прошлой главы; `write_steps` пишет в `start/` только отличия, а в `lesson.md` — `base` и `baseHash`. Правка прошлой главы ломает хеш: `npm run validate` скажет, какую главу пересобрать (`python3 tools/authoring/format-content.py <глава>`). Что убрали или вынесли в файлы, объясняется в тексте первого шага;
- если старт отличается от прошлого решения хотя бы строкой `// TODO`, шаг тоже `custom` (и только тогда у него есть `start/` — с изменёнными файлами; если `write_steps` не записал `start/` у шага `custom` или записал у `previous`, валидатор скажет об этом);
- новый файл, появившийся в шаге, — тоже `custom`; в старте лежит заготовка с `// TODO`;
- интерфейс магазина должен помещаться в превью **500 × 600** без растягивания панелей;
- после генерации: `npm run validate` — полный код всех шагов собирается и проверяется по настоящим типам `@angular/*` (в `.content-check/`);
- правка файла в шаге N действует во всех следующих шагах главы, которые этот файл не меняют. Это удобно (исправил один раз), но изменение расходится молча: после правок старых шагов — `npm run validate`, `run-chapter` и `checks/*` главы.

## 3. Проверка запуском до текста

```bash
node tools/e2e/run-dir.mjs content/03-signals/02-signal/solution          # консоль, запросы, адрес, текст, скриншот
node tools/e2e/run-dir.mjs content/10-routing/03-params/solution /games/8  # с начального адреса
```

Обязательно:

- консоль без ошибок и без предупреждений Angular (`NG0xxx`) — кроме тех, что шаг показывает намеренно;
- текст страницы — тот, что обещает урок;
- скриншот — откройте и посмотрите глазами (вёрстка в 500 px, переполнение, пустые места).

Для экспериментов из текста создайте временную папку (scratchpad) с копией шага и правкой и запустите её тем же `run-dir.mjs`; сценарий действий (клики, ввод, переходы) — через `tools/e2e/exp.mjs`:

```js
// сценарий.mjs
export default async ({ page, pageText, navigate, wait }) => {
  await page.type('.search', 'шах');
  await wait(500);
  console.log(await pageText());
  await navigate('/cart');
};
```

В `tools/e2e/lib.mjs` есть всё для своих проверок:

- чистое превью: `compileDir`, `openPreview(browser, compiled, { url, backend, waitMs })`, `collect` (ошибки среды и запросы бэкенда), `pageText`, `appUrl`, `navigate`; образец — `checks/preview.mjs`;
- интерфейс платформы: `openCourse('/chapter/step', { onDialog, ignoreConsole })` открывает платформу с чистым прогрессом и возвращает помощники проверки главы — `expect`, `frame()` (iframe превью, после перезапуска — последний), `consoleText`, `title`, `count`, `showSolution`, `nextStep`, `checkConsoleClean`, `runWithCode` (код эксперимента подкладывается в сохранённый прогресс шага), `finish`; `clean()` — текст без неразрывных пробелов; образцы — `checks/platform.mjs` и `checks/chNN-*.mjs`.

## 4. Текст уроков

По `docs/writing-guide.md`. Структура шага: зачем → объяснение → код с подсветкой строк → `::: task` → «Что получилось» → эксперименты → «Как в настоящем проекте» → `::: deep` / `::: legacy`. Практикум: `::: task` со списком, `::: hint` от общего к конкретному, «Проверьте себя», «Итоги главы» с мостиком к следующей главе.

## 5. Проверка каждого утверждения в тексте

Самый важный этап. Каждое фактическое утверждение и **каждый предложенный эксперимент** («уберите X — увидите Y») проверяется кодом или исходниками. Особенно:

- тексты и коды ошибок (`NG0xxx`) — только увиденные в консоли;
- «Angular обновит / не обновит экран» — проверить запуском (OnPush по умолчанию меняет многие привычные ответы);
- «этот запрос отменится / не отменится» — по вкладке «Сеть» или логу учебного бэкенда;
- порядок хуков и эффектов — логом в консоли.

## 6. Регистрация и прогон в платформе

```bash
# добавить папку главы в content/course.json → chapters
npm run validate                                  # структура, цепочка start/solution, YAML, типы
node tools/e2e/run-chapter.mjs 03-signals         # все шаги в интерфейсе: «Решение», консоль, ошибки
```

`run-chapter` должен закончиться строкой `Ошибки страницы: []`. Если в главе есть взаимодействие (формы, роутинг, корзина), напишите проверку в `tools/e2e/checks/chNN-*.mjs` на `openCourse` из `lib.mjs`: клики, ввод, переходы, состояние после «перезагрузки». Числа из этих проверок можно цитировать в тексте («мы проверили: …»).

Переходы между шагами кнопкой «Далее» (а не только `goto`) — обязательно: в курсе PixiJS именно так нашлась гонка синхронизации TS-воркера Monaco.

**Практикум получает `check.ts`** (формат — `lesson-format.md`). Проверка проверяет каждый пункт задания по результату на экране. Готова, когда:

- `node tools/e2e/checks/step-checks.mjs <глава>` — старт не проходит с понятной подсказкой, решение проходит;
- «мутации» — решение с типичными ошибками (убрать привязку, границу, сброс, `providers` в компоненте вместо общего сервиса) не проходит, и подсказка указывает на ошибку. Удобно сценарием в scratchpad: полный код решения (`readDir`), замены, код в сохранённый прогресс шага (как `runWithCode`), щелчок «Проверить», текст `.check-result`. Мутация, которую проверка не ловит, — либо дыра в проверке, либо ошибка, которая в этом приложении не видна (тогда не делайте вид, что она проверяется: так убрана проверка `setQuantity` в 9.5 — границы держит `Quantity`).

## 6а. Квиз главы

`content/<глава>/quiz.yaml` — после текста всех шагов (формат — `lesson-format.md`, правила — `writing-guide.md`, «Квиз главы»). Для каждого вопроса — строка «на каком утверждении какого `lesson.md` основан ответ»; утверждения, которых в тексте нет, в квиз не попадают. Цитата нужна и против неверных вариантов, которые не очевидно неверны: вариант «неверен по смыслу», но текстом не опровергнут, — замените заблуждением, которое урок опровергает прямо. Код в вопросе — как в уроке: упрощённый код, который не запускали, может вести себя иначе. После — сверка вторым взглядом (свежий агент или вычитка): факты, однозначность, длина вариантов (правильный самый длинный не чаще чем в трети вопросов — проверяется скриптом по `options[0].length`). Затем `npm run validate` и `node tools/e2e/checks/quiz.mjs` (интерфейс квиза на главах 1–2; после правок в `src/quiz/` — обязательно). `npm run validate` не запускайте в нескольких процессах одновременно: он пересоздаёт общую папку `.content-check/` и падает с `ENOTEMPTY`/`TS2307`.

# Ловушки окружения

Перенесены из курса PixiJS и прототипа; дополнять по мере работы. Подводные камни кода платформы — в `architecture.md`, факты об Angular — в `modern-angular.md`.

- **`@angular/compiler-cli` — только ESM**: `require()` не работает, скрипты — `.mjs`. Трансформ: `import { angularJitApplicationTransform } from '@angular/compiler-cli'`.
- **Node 20** не запускает `.ts` напрямую: скрипты в `scripts/` и `tools/` — `.mjs`.
- **zsh**: `$x[?]`, `*.d.ts` без кавычек в аргументах интерпретируются как glob («no matches found»). Для поиска — Python.
- **Не пишите во временные файлы `/tmp`**: используйте папку scratchpad сессии или `tools/e2e/out/` (в `.gitignore`).
- **YAML во frontmatter**: `@`, `{`, `[`, `:` внутри списков — в кавычках.
- **Angular CLI 22 требует Node 22.22+ / 24.15+**, а по умолчанию в терминале автора Node 20.19 (nvm: есть 22.15, 24.15). Для `ng new` — `nvm use 24.15` или читать шаблоны из `@schematics/angular` (`npm pack @schematics/angular@<версия>`). Важно для главы 20: ученику нужен Node 22+.
- **Эксперименты «сломайте X»**: исключение в конструкторе компонента (вызов несуществующего метода) не даст отрисоваться шаблону — ошибок шаблона (NG0303) уже не будет. Для демонстрации ошибки TypeScript без падения — ошибка только в типах (`let n: number = 'строка'`).
- **Намеренно сломанный старт** (шаг про ошибки): frontmatter `brokenStart: true` — валидатор такой старт не собирает и не проверяет типы.
- **Формат кода уроков = кнопка «Формат».** Настройки — одни на всех: `shared/lesson-prettier.json` (ширина 64, одинарные кавычки, `trailingComma: all`; `.html` — парсер `angular`) читают редактор (`src/editor/monaco.ts`), `prettier.config.mjs` (код уроков; остальной код проекта — ширина 120) и `write_steps` (форматирует полные снимки шагов перед записью — генератору не нужен свой вызов Prettier). Исключения — в `.prettierignore` (сгенерированное, Markdown — Prettier развернул бы списки во frontmatter, — и сломанный старт шага 1.6). Поменяли настройки — `python3 tools/authoring/format-content.py` переформатирует все главы по цепочке (с новыми `baseHash`), затем `npm run validate`, `npx prettier --check .` и `checks/platform.mjs` (проверяет, что «Формат» не меняет файлы уроков). - **Объявления типов с `export {}`** превращают `declare module 'x'` в дополнение несуществующего модуля, а `skipLibCheck` прячет ошибку — тип молча становится `any` (так было с первым `shared/vitest.d.ts`). Глобальные объявления — без `import`/`export` на верхнем уровне.
