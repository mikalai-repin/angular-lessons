# Формат уроков

Формат взят из курса PixiJS (`../pixi-js/docs/lesson-format.md`) с дополнениями для Angular: файлы `.html` и `.css`, учебный бэкенд, начальный адрес в превью, тесты.

## Структура на диске

```
content/
  course.json                     — порядок глав
  01-first-app/
    chapter.json                  — название, описание, часть
    01-what-is-angular/
      lesson.md
      start/                      — первый шаг главы 1 (custom):
        main.ts                     полный код старта
        app.ts
        …
      solution/                   — только файлы, которые шаг
        app.ts                      изменил или добавил
    02-first-component/
      lesson.md                   — startFrom: previous: папки start/ НЕТ,
      solution/…                    старт = результат шага 01
      check.ts                    — необязательно
  02-templates/
    …
```

Правила именования:

- Папки глав и шагов: `NN-slug`, где `slug` — латиница в kebab-case. Номер задаёт порядок, slug идёт в URL (`/templates/property-binding`).
- Точка входа всегда `main.ts`. Импорты между файлами — **без расширения**: `import { GameCard } from './game-card'`.
- Файлы могут лежать в подпапках (`core/cart.ts`, `catalog/catalog.html`) — так же, как в проекте Angular CLI. В редакторе вкладка показывает путь.
- Имена файлов — по стилю Angular CLI 22 (`fileNameStyleGuide: 2025`, проверено по `@schematics/angular@22.2.1`): компонент `game-card.ts` + `game-card.html` + `game-card.css`, сервис `cart-store.ts`, без суффиксов `.component`/`.service`. Корень шага соответствует `src/app/` проекта CLI плюс `main.ts` и `styles.css` (в CLI они лежат в `src/`).
- `styles.css` в корне шага — **глобальные стили** (в превью вставляются `<style>` до запуска, как `styles` в `angular.json`). Стили компонентов — через `styleUrl`.
- Вкладки идут в порядке `files` из frontmatter, иначе: `main.ts`, затем по алфавиту; `.ts`, `.html`, `.css` одного компонента — рядом.

## `lesson.md`

### Frontmatter

```yaml
---
title: Привязка свойств
files: [main.ts, app.ts, app.html]   # видимые вкладки и их порядок (необязательно)
readonly: [main.ts]                  # видны, но не редактируются
focus: app.html                      # какая вкладка открыта при входе
startFrom: previous                  # previous (по умолчанию) | custom
api: ['[property]', 'DOM-свойство']  # что вводит шаг — для оглавления и поиска
noSolution: true                     # шаг без задания (теория, демо): папки solution/ нет
brokenStart: true                    # старт намеренно с ошибками (шаг про отладку): валидатор его не собирает и не проверяет типы
removedInStart: [dom-watch.ts]       # файлы результата прошлого шага, которых нет в custom-старте (редко)
removedInSolution: [old.ts]          # файлы старта, которые ученик удаляет в шаге (редко)
base: 07-directives-pipes/07-practice # только у первого шага главы: от результата какого шага прошлой главы start/
baseHash: '7d600b7605a6'             # хеш полного кода base; пишет write_steps, сверяет валидатор
url: /catalog?category=family        # начальный адрес приложения в превью (по умолчанию /)
backend: { latency: 800, failRate: 0 }   # учебный бэкенд: задержка (по умолчанию 300 мс), доля ответов 500, tokenTtl — срок токена доступа, с (по умолчанию 3600)
preview: tests                       # app (по умолчанию) | tests — превью запускает *.spec.ts вместо main.ts (глава 16)
---
```

YAML: элементы с фигурными или квадратными скобками, `@`, `:` — в кавычках: `api: ['@if', 'input.required()']` (ловушка из курса PixiJS).

**Шаг хранит только изменения** (так решено после главы 6: в 812 файлах шагов было меньше 250 разных). Здесь правила цепочки описаны полностью, остальные документы ссылаются сюда. Полный код шага собирает `shared/step-chain.js` — один модуль для платформы (`src/content/course.ts`), валидатора, `tools/e2e` и генераторов глав (через `scripts/step-files.mjs`):

- **старт** шага `startFrom: previous` — результат предыдущего шага главы (его решение, а у шага `noSolution` — его старт). Папки `start/` у такого шага нет;
- **старт** шага `startFrom: custom` — результат предыдущего шага + файлы своей папки `start/` (новые и изменённые) − `removedInStart`. У первого шага главы предыдущий шаг — **база** из прошлой главы, она записана во frontmatter: `base: 07-directives-pipes/07-practice` (результат этого шага) и `baseHash: '…'` (хеш его полного кода). Хеш сверяет валидатор: если прошлая глава изменилась, `npm run validate` скажет «база … изменилась» — проверьте, что изменения подходят главе, и пересоберите её: `python3 tools/authoring/format-content.py <глава>` перепишет `start/` и `baseHash`. Так правка в прошлой главе не протекает в следующую молча. Без `base` (глава 1) `start/` первого шага — полный снимок. `custom` — в начале главы или когда между шагами есть «закадровая» подготовка (новый файл с заготовкой, вынесенный код, `TODO`). Подготовка обязательно описывается в тексте шага;
- **решение** — старт + файлы папки `solution/` (новые и изменённые) − `removedInSolution`.

Валидатор считает ошибкой папку `start/` у шага `previous`, файл в `start/` или `solution/`, совпадающий с тем, что было до шага (копию), `custom`-старт без отличий и решение без отличий от старта (нужен `noSolution`).

Посмотреть полный код шага целиком: `npm run step content/06-lifecycle/05-content-children/solution` → `tools/e2e/out/step/` (`…/result` — результат шага: решение или, у шага без решения, старт). Пути `…/<шаг>/start` и `…/<шаг>/solution` в `run-dir.mjs`, `exp.mjs` и `readDir` тоже дают полный код, в Python — `step_dir()` из `tools/authoring/steps.py`. Копировать папку шага напрямую нельзя — получите только изменения. Редактор в IDE в частичной папке `solution/` может подчёркивать импорты файлов, которых в ней нет, — это нормально.

### Тело

Markdown и контейнеры (как в курсе PixiJS) плюс один новый:

```md
::: tip
Короткий совет.
:::

::: warning
Частая ошибка или ловушка.
:::

::: deep Под капотом: как работает track
Необязательный подробный блок. По умолчанию свёрнут.
:::

::: legacy Вы встретите в старом коде: *ngFor
Как то же самое писали раньше. По умолчанию свёрнут. Только для чтения, не для повторения.
:::

::: task
Что ученик должен сделать в редакторе в этом шаге.
:::

::: hint Подсказка 1: где хранить выбранную категорию
Сворачиваемая подсказка к практикуму. Подсказки идут от общей к конкретной.
:::
```

Блоки кода с указанием файла и выделением строк:

````md
```ts app.ts {4}
export class App {
  protected readonly title = 'Ход конём';
  protected readonly price = 1290;
  protected readonly cover = '/assets/covers/treasure-island.svg';
}
```

```html app.html {1}
<img [src]="cover" alt="Обложка" />
```
````

Для шаблонов — язык `html` (подсвечивается грамматикой `angular-html` в Shiki).

Ссылки на API ведут на официальную документацию: `[signal](https://angular.dev/api/core/signal)`. Ссылку проверяем перед публикацией.

Внутренние ссылки на другие шаги: `[шаг про сигналы](step:03-signals/02-signal)`.

## `start/` и `solution/`

- Только изменения (см. выше): файл, который в шаге не меняется, лежит только там, где он появился или изменился в последний раз.
- `start/` — с чего ученик начинает. Места, которые нужно дописать, отмечаются комментарием `// TODO: …` (в `.ts`) или `<!-- TODO: … -->` (в `.html`) на русском.
- `solution/` вместе со стартом — эталон. Должен запускаться без ошибок, без предупреждений TypeScript и без ошибок шаблонов: `ngc --strictTemplates` пока прогоняется вручную (см. `authoring-process.md`), в валидаторе — этап 5.

## `check.ts` (необязательно; есть у всех практикумов)

Лежит рядом с `lesson.md` (не в `start/` и не в `solution/`), ученику не показывается. По кнопке «✓ Проверить» приложение запускается заново с начального адреса шага, и проверка выполняется внутри превью (устройство — `architecture.md`). Типы — `shared/course-check.d.ts`:

```ts
import type { Check, CheckStorage } from '@course/check';

// Необязательно: localStorage, с которым стартует приложение (данные ученика на время проверки убираются)
export const storage: CheckStorage = { 'hod-konem:cart:v1': '[{"id":4,"quantity":99}]' };

const check: Check = async ({ $, $$, text, click, fill, navigate, fail }) => {
  await navigate('/cart');
  const total = $('.total') ?? fail('На странице корзины нет итога (.total).');
  if (!text(total).includes('2 580')) fail('Итог не пересчитался: сумма должна зависеть от количества.');
  return { pass: true };
};

export default check;
```

Контекст: `document`, `$`/`$$` (с корнем вторым аргументом), `text` (текст одной строкой, неразрывные пробелы — обычные), `visible`, `click`, `fill` (поле или `select`: `input` + `change`), `setChecked`, `navigate`, `url()`, `settle(ms?)` — ждать отрисовки, `fail(hint)` — неудача с подсказкой, живые массивы `logs` (консоль с начала проверки), `requests` (бэкенд: метод, адрес, статус и `headers` — заголовки запроса, имена в нижнем регистре), `errors` (ошибки с начала запуска). Действия сами ждут отрисовки (`settle`).

- Проверяем **результат** (DOM, адрес, консоль, запросы к бэкенду), а не текст кода: ищем элементы по тому, что задано в задании или уже было в старте (классы, теги компонентов, тексты кнопок), а не по именам, которые выбирает ученик.
- Атрибуты `data-test` в коде уроков допустимы, когда без них проверка хрупкая; в тексте объясняем, зачем они.
- Каждый `pass: false` содержит `hint` на русском: что не так и куда смотреть, без готового ответа. Найти элемент или упасть — `$('…') ?? fail('…')`: TypeScript сужает тип по `never` только так (не через `if (!x) fail(…)` — `fail` из деструктуризации).
- Правила, которые держатся на `disabled`, проверяем и щелчком по кнопке, которой сняли `disabled`: граница должна держаться в коде.
- `IntersectionObserver` и всё, что зависит от высоты превью: высота у ученика своя. Нужна гарантия «элемент за краем экрана» — временный высокий блок над приложением (`document.body.prepend`), как в проверках 6.8 и 7.7.
- Проверка — тоже код, её проверяют: `node tools/e2e/checks/step-checks.mjs <глава>` (старт не проходит, решение проходит) и «мутации» — решение с типичной ошибкой должно не пройти с понятной подсказкой (см. `authoring-process.md`).

## Квиз главы — `quiz.yaml`

Квиз лежит в папке главы, рядом с `chapter.json`: `content/<глава>/quiz.yaml`. Формат и страница перенесены из курса `../react-learn`. Квизы есть у глав 1–12 и входят в критерий готовности новой главы; для платформы файл необязательный — глава без него просто не показывает квиз. Глава считается **пройденной**, когда квиз сдан: правильных ответов ≥ 85 % (`Math.ceil(0.85 × n)`: 10 → 9, 14 → 12, 15 → 13). Платформа: `/<глава>/quiz` (`src/quiz/QuizPage.tsx`). «Далее» с последнего шага главы становится «Квиз →», с квиза — переход к следующей главе (не блокируется). Лучший результат хранится в `progress.quizzes[slug главы]`, у главы и квиза в оглавлении — ✓.

```yaml
# Первый вариант в options — правильный: порядок вопросов и вариантов перемешивается при каждой попытке
questions:
  - question: |
      Какая из кнопок будет активной?

      ```html
      <button [disabled]="false">B</button>
      ```
    options:
      - Только B — в свойство записано логическое `false`
      - …
    explanation: |
      Почему верно (1–3 предложения), со ссылкой на шаг словами: «шаг „Привязка свойств“».
    step: 02-property-binding   # папка шага этой главы: ссылка «Повторить шаг» в разборе ошибок
```

- 10–15 вопросов, у каждого 3–5 разных вариантов (в курсе — 4), `explanation` и `step` — это проверяет `npm run validate`.
- `question` и `explanation` — markdown (код с подсветкой, врезки, ссылки `step:`), варианты — строчный markdown.
- YAML: вариант, который начинается с `` ` ``, `<`, `{`, `[`, `*`, `-`, `>` или содержит `: `, — в одинарных кавычках (одинарная кавычка внутри — `''`). Иначе YAML прочитает его как объект или список, и валидатор скажет «каждый вариант — непустая строка». Код с обратной кавычкой внутри — в двойных: ``` `` {{ `Цена: ${price}` }} `` ```. Теги в тексте варианта — в `` `…` ``, иначе markdown отрисует их как HTML.
- Правила содержания — `docs/writing-guide.md`, «Квиз главы».

## Тесты в шаге (глава 16)

Файлы `*.spec.ts` — тесты. У шага с `preview: tests` превью при входе и по «Проверить» запускает их вместо `main.ts` и показывает отчёт; над превью — переключатель «Приложение / Тесты» (он есть у любого шага с `*.spec.ts`). Синтаксис — Vitest 5 без импортов (`describe`, `it`, `expect`, `beforeEach`, `vi.fn` — глобальные, как в проекте Angular CLI); `import { … } from 'vitest'` тоже работает. Окружение — как у `ng test`: `TestBed` готов, очистка после каждого теста. Тесты курса переносятся в проект Angular CLI без изменений (проверка — `tools/e2e/ng-test.mjs`), отличия превью от `ng test` — `architecture.md`, «Тесты в превью».

`check.ts` такого шага получает результаты тестов ученика:

```ts
const check: Check = ({ tests, unhandled, fail }) => {
  const cart = tests.filter((t) => t.file === 'core/cart-store.spec.ts');
  if (cart.length < 3) fail('Напишите хотя бы три теста для CartStore.');
  if (cart.some((t) => t.state === 'fail')) fail('Тесты CartStore должны проходить.');
  return { pass: true };
};
```
